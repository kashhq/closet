# Integration tests: the harness, scratch databases, the authorization matrix

The Vitest integration tier (`test/integration/`) boots the real app in-process
on a scratch Postgres database per spec file and drives it through
`app.inject()`. The tiers, layout and other test gotchas are in
`test/AGENTS.md`. These rules apply when you change the harness, the scratch
databases or the authorization matrix.

## The harness

- **The integration harness configures the app explicitly.** `createTestApp(overrides)` builds `Config` with `loadConfig({ env: { ...BASE_ENV, ...database, DATA_PATH, ...overrides }, envFiles: [] })`: neither the process environment nor `.env.local` reaches a spec, and different overrides in one file are fine. Its logger writes JSON lines into `t.logs` (LOG_LEVEL `debug`, nothing on the console); `{ appLog: true }` gives the real stdout + `app.log` outputs instead (file-route.spec.ts reads app.log). The integration project runs `isolate: false` on the `forks` pool (2026-10-14): each worker imports the app's module graph once and runs many files in it, which halved the db tier. Each file still boots and closes its own app (its own rate-limit stores, metrics registry and error tracker), and nothing in `src/` reads `process.env` at import. What would leak is forbidden: `vi.mock`/`vi.doMock` in `test/integration/` (eslint; pass a stand-in through `createTestApp`'s options), timers left fake (`test/support/shared-worker-setup.ts` restores them, with stubbed envs and globals), and importing another spec file (Vitest never re-imports a test file, so it would collect nothing on its own turn). Never set `pool: 'threads'`: worker threads share the process's zone and environment.
- **The integration harness is signed in by default.** `createTestApp` registers `owner@example.com` at boot (with `ORDER_MAIL_JMAP_TOKEN` set, inserts it before the boot and signs it in after: the boot resolves `ORDER_MAIL_OWNER` to an account, #706) and `t.inject` sends that session (`t.owner.cookie`) unless the request has its own `cookie` header or passes `anonymous: true`. A test about signed-out behavior must say `anonymous: true`; one that forgets asserts on the owner's view.

## Scratch databases

- **A spec's database is a clone of the migrated template** (`closet_tpl_<12 hex>`, the hash of every file in `drizzle/`; `migratedTemplate()` in `test/support/scratch-database.ts`). The integration project's globalSetup makes it once per run, under an advisory lock on the admin connection, and every `createScratchDatabase('closet_it', { migrated: true })` is `create database ... template` from it, so the app's boot finds the schema up to date. It stays on the server across runs until `drizzle/` changes (the sweep drops the other builds' templates), so a new migration costs one template build, not one per file. A spec that builds a database from an older shape asks for an empty one: the harness does when a spec passes `beforeBoot`, and `migration-runner.spec.ts` calls `createScratchDatabase` directly. Lowering `PASSWORD_HASH_ROUNDS` to 4 (the harness's `BASE_ENV`) is the other half of the tier's speed: at 12, the owner each file registers and the auth specs' sign-ins were most of its time.
- **Scratch databases are named with their creation time** (`closet_it_<base36 seconds>_<hex>`). A killed test run (`npm run check` stops the tests when another check fails) never drops its databases; the integration project's globalSetup (`test/support/sweep-scratch-databases.ts`) drops idle ones older than an hour, never with FORCE, and leaves names it cannot date. **Both the name's time and the sweep's "now" are the Postgres server's clock**, never `Date.now()`: specs that fake Date to yesterday before `createTestApp` named a live database over an hour old, and another run's sweep dropped it between boot and the owner's registration (#249). A harness sign-in that sets no session throws with what the app logged at warn and above.
- **The sync triggers refuse an unlocked write** (#196a-2, `drizzle/0052_sync-triggers.sql`, so on every spec database): `owner lock not held: a write to <table> for owner <id>` when the write's transaction does not hold that owner's lock (`src/db/AGENTS.md`, The owner lock's statement). A spec fixture that writes a synced table directly goes through `asFixture(t.db, (tx) => ...)` (harness.ts: every account's lock, in id order); one that emulates a writer takes that writer's own lock (`ownerTransaction`), so an interleave still waits where the writer would. A constraint spec (`refuses ... = ...`) wraps its raw SQL the same way, or it meets the triggers before the check. A spec comparing a synced row before and after a write leaves out `revision` and `updated_at`, which every write stamps.

## The authorization matrix

- **The authorization matrix is split by route group so Vitest spreads it** (#113): each `authorization-<group>.spec.ts` hands its `ROUTES` to `describeMatrix` (`authorization-matrix.ts`), which boots its own app and fixture. A case compares one statement's md5 per table (and the stored file names) before and after the request, and fetches rows only to explain a difference; a clone's success alone compares every row. A new table a wardrobe request may write joins `TABLES` there, and a new route joins its group's file. A route that exists only behind a flag says `feature: 'weather' | 'orderMail'`, and its group's app boots with that feature on against its stand-in (`featureApp`).
- **A route that takes an id fails CI until the matrix requests it or it is exempt** (`authorization-coverage.spec.ts`, #182). The inventory (the every-feature boot, `ADDRESS`, the template router, the group loader) is `app-routes.ts`, shared with `api-parity.spec.ts`. The spec boots the app with every optional feature on and collects its routes through `createApp`'s `onRoute` option (a hook on the instance before anything registers; one added after boot sees nothing). An id route is one with a path parameter or wildcard, or a querystring or body schema with `ownerId`. It imports every group's route table from `authorization-<group>.routes.ts` (the group's spec only describes it, so no spec file is imported by another) and fails unless every `authorization-<group>.spec.ts` has one, evaluates each case's request on a stand-in fixture (`ADDRESS`), and resolves the URL with Fastify's own router over the app's templates. A route whose querystring takes `ownerId` must also be requested with it (the `ownerId` via). HEAD routes Fastify adds beside a GET count as the GET. The fix for a failure is a matrix case in the route's group. Only a route that needs none goes on `EXEMPT`, keyed `METHOD /template`, with its reason: public by design (a capability URL, whose token is the credential), or `covered by <spec> "<test name>"` when another spec owns its authorization. An exemption that goes stale (the route is gone, takes no id or has joined the matrix) fails too. A new `Fixture` field needs a stand-in value in `ADDRESS`, which typecheck enforces.
- **A matrix route with an API twin replays on it** (#191; `Route.api`, `src/web/api/AGENTS.md` Parity). A group with any `api` signs each actor's device in once (`deviceToken`, a bcrypt each), and each case runs again as `<name> (api)` through `t.api` with that token, none for anonymous. The outcome is the page's: `ok` is the twin's own `api.ok`, `login` a 401, a refusal the page's status; a page read's `shows` is not checked on the twin. A clone's twin answers the new garment with its `id`. The snapshots leave out `BOOKKEEPING` columns (a token's `last_used_at`, stamped on use), so a refused API request still changes nothing. `api-parity.spec.ts` fails when a twinned page write's matrix route has no `api`, or its `api` reaches another operation.
