# Agents from the phone: "Ask your agent" requests, then OAuth for /mcp (#681)

Status: design, 2026-11-27. Owner decisions on #681 (2026-11-27): Closet stays agent-agnostic. Agents
reach it only over `/mcp`, and no server-side runner is tied to one vendor. Both of these are required:

- **(b)** An "Ask your agent" request. A household member writes it on the phone, and the next agent
  that connects over MCP finds it and acts on it. It ships first, because today's token clients
  (Claude Code) can already use it.
- **(a)** OAuth for `/mcp`. Hosted MCP clients attach from a phone: the Claude app's custom
  connectors, ChatGPT's connectors, any spec-compliant client.

The agent is called "the agent" here, never by a product name (#1281, #1282). Decision record:
`docs/decisions.md` 2026-11-27, "Agents reach Closet only over MCP; phones attach with OAuth".

## 1. Goals and non-goals

**Goals**

- A person at the closet with only a phone can ask their agent for something, and see whether it
  is waiting, being worked on, answered or withdrawn. They get a push notification when it is
  answered. This works offline (queued) and with any agent that can call MCP tools.
- A household member with no laptop can connect a hosted agent to their own account from the phone:
  add a connector in the agent's app, approve it in Closet, done. The connection is an agent token
  like any other: scoped, listed in Agent Access, revocable, and ended by a new password.
- The MCP authorization spec is followed as it stands (revision 2026-07-28), within what the Claude
  apps support today (auth revisions up to 2025-11-25).

**Non-goals**

- A chat UI, or any server-side agent runner (the pushback list: a way to ask, not chat).
- Dynamic Client Registration (RFC 7591). The current spec deprecates it, and both Claude and
  ChatGPT prefer Client ID Metadata Documents (section 4.3). It is rejected for now, and would come
  back as its own issue only if a client we need registers no other way.
- OAuth for `/api/v1`. Native clients keep device tokens.
- A public sign-in page. The consent page stays on the tailnet (section 4.2).
- Token revocation by clients (RFC 7009) and token introspection. Revocation is Agent Access's job.
- **`/auth/tokens` copy**, including which clients can connect and how to word an OAuth connection.
  #1281 owns that; this PR changes no copy, and #681's last acceptance item lands with #1281.

## 2. What exists

- `POST /mcp` is a stateless Streamable HTTP endpoint on the `mcp` surface (`src/web/surface.ts`).
  It is gated by an agent token (`personal_access_token`, kind `mcp`, `closet_` + 32 random bytes,
  stored as SHA-256), read by `presentedBearer` in the bearer gate. A refusal is a 401 with
  `WWW-Authenticate: Bearer realm="closet"` (`src/web/mcp/reference.md`, Auth).
- A token is minted only at Agent Access, behind the current password (the step-up rule,
  `src/web/auth/AGENTS.md`), with `read_only` / `own_wardrobe_only` fixed at mint (#701).
  `MAX_ACTIVE_TOKENS` is 20 per user and kind. A new password revokes every token, and Sign out
  everywhere revokes none of the agent tokens.
- The token row's id is the agent's identity: the provenance of what it writes (`originOf(ctx)`,
  `agentLabelSql` reads the row's `name`), its feedback cursor (`feedback_read_at`) and its rounds
  (`muse_round.token_id`).
- Public reach: `https://closet-mcp.kashhq.com` goes Pangolin, then Newt, then homelab's
  `closet-mcp-gate` (Caddy), which forwards exactly `POST /mcp` and answers 404 to everything else.
  The canonical site (`SITE_URL`, https) resolves only on the tailnet.
  The MCP host is already an `ALLOWED_HOSTS` entry, and the gate's network is in `TRUSTED_PROXIES`.
- `GET /.well-known/*` answers `{}` to anything (`src/web/shell/routes.tsx`). A discovering OAuth
  client would read that as invalid metadata.

## 3. (b) "Ask your agent" requests

### 3.1 The row

`agent_request` is a **synced root table owned by the asker** (`owner_id`). It joins
`src/db/sync-tables.ts`, so every write takes the asker's owner lock first, and the feed carries it
as resource `agentRequest`. A request is the asker's alone, and is answered by any of the asker's own
agent tokens (kind `mcp`, static or OAuth). No other account's agent sees it. A partner who wants an
agent connects their own, which is what (a) is for.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | serial | |
| `owner_id` | integer FK user, cascade | the asker; leads `(owner_id, status, created_at)` |
| `client_id` | uuid, null | the outbox's idempotency key; unique `(owner_id, client_id)`; root-table rule |
| `body` | text, 1..500 | what they ask, trimmed |
| `garment_id` | integer FK garment, set null | subject; a garment the asker can see (own or shared) |
| `trip_id` | integer FK trip, set null | subject; the asker's own trip |
| `option_group_id` | integer FK option_group, set null | subject; one of the asker's wishlist needs |
| `status` | text check | `open`, `claimed`, `answered` or `withdrawn` |
| `claimed_by_token_id` | integer FK personal_access_token, set null | indexed |
| `claimed_at` | timestamptz | the lease clock |
| `answer` | text, null, 1..1000 | the agent's reply, shown as-is (escaped) |
| `answered_by_token_id` | integer FK personal_access_token, set null | provenance, through `agentLabelSql` |
| `answered_at`, `answer_seen_at`, `withdrawn_at` | timestamptz | |
| `revision`, `created_at`, `updated_at` | | stamped by the sync triggers, never by a writer |

Every FK column has an index. A check constraint allows at most one subject. Subjects are checked
again when read: the tool answers a subject only while the asker can still see it (a share ended or
a garment deleted leaves `subject: null`).

### 3.2 One state machine

Every transition goes through one domain module (`src/web/requests/request-actions.ts`) with a
typed `RequestTransition` and one `transitionRequest`. Each transition is a single guarded `UPDATE
... WHERE status IN (...) RETURNING` under the owner lock, so two agents can never both hold a
request.

| Transition | Who | From | To |
| --- | --- | --- | --- |
| `ask` | asker (page, API, outbox replay) | (insert) | `open` |
| `claim` | an agent token of the asker, with writes allowed | `open`, or `claimed` with an expired lease | `claimed` |
| `answer` | the claiming token | `claimed` by it, or `open` (claims and answers at once) | `answered` |
| `withdraw` | asker | `open`, `claimed` | `withdrawn` |
| `seen` | asker ("Got it") | `answered` | `answered`, with `answer_seen_at` set |

- **The lease** is `CLAIM_LEASE_MINUTES` (30). An expired claim reads as open to the next agent, so
  no timer is needed. A claim taken over stamps the new token. The old token's `answer` is refused
  with "Another agent took this request", a tool error.
- A second `claim` by another token while the lease holds is refused with "Another agent is working
  on this request". The same token's second claim renews the lease (it is idempotent).
- `answer` on `withdrawn` is refused with "The owner withdrew this request". Answering twice is
  refused with "Already answered".
- Each transition logs one `logOp` line from the action, with the request id, the owner, the token id
  on agent transitions and the surface. Never the body or the answer.

### 3.3 Entry points

There is one "Ask your agent" sheet (`AskAgentSheet`, `src/web/requests/`): a textarea, plus a
hidden subject. It is a `PostForm` to `POST /requests`, placed:

- **Today**: no subject. For "What should I wear to the dinner tonight?".
- **Wishlist**: on a need's card (`option_group_id`), e.g. "Find me three cheaper options".
- **A trip's page**: `trip_id`, e.g. "Pack me for this".
- **A garment's page**: `garment_id`, own or in a wardrobe shared with the asker, e.g. "What goes with
  this?".

When the asker has no active agent token, the sheet still sends, and says so:
"No agent is connected yet. It will wait until one connects." (copy through `t()`; wording with
#1281). A successful send lands on `/requests/:id` (`navigateTo`).

### 3.4 Offline

Creating a request is a new outbox kind, `request` (`QUEUEABLE_ROUTES.request = '/requests'`). This
is a recorded extension of the #178 exception (frontend-pwa.md: unreachable writes are disabled,
never dropped). It qualifies because a request is a create with nothing to conflict with:

- The sheet's form carries `data-offline-queue="request"` and a `clientId` minted when the sheet
  opens (`getRandomValues`, as the outbox does).
- The record key is `request:<clientId>`, so every request is its own key and nothing collapses.
- The replay is idempotent on `(owner_id, client_id)`. A replay of one already stored answers 204
  `unchanged`; a new one 204 `changed` (`answerReplay`).
- Offline, the asker sees "Waiting to sync" under the sheet's region (`OutboxPending`). Once synced,
  the request shows on Today.
- `withdraw` and `seen` stay `data-needs-network`: they act on a server row the page may hold stale.

### 3.5 How an agent finds and answers one

- **The server's `INSTRUCTIONS`** gain a first step: "Call `list_agent_requests` first in every
  conversation. Claim each open request you will act on, do the work with the usual tools, then
  answer it in one or two sentences saying what you did." The line stays static, so initialize runs
  no statement.
- **`list_agent_requests`** (read, `writes: false`) answers the caller's open requests, the ones its
  token holds, and those with expired leases, oldest first, capped at 20. Each has `id`, `body`,
  `createdAt`, `status`, `subject` (projected through the garment, trip or need resource's mapper,
  `X_FOR_MCP`), and `claimedByYou`. A read-only token lists requests but cannot claim them. Its
  instructions say so ("ask the owner to connect a token that can make changes").
- **`claim_agent_request(id)`** and **`answer_agent_request(id, answer)`** are `WRITES` tools. They
  are classified in `MCP_WRITES` with `attribution: stamps`, because they stamp the token as
  claimant and answerer. The suggestions, outfits and plans the agent makes meanwhile carry its token
  as ever, so the request page can show "Made by <agent>".
- A request answered without a round still notifies (3.6). A request answered by an agent that also
  calls `finish_round` gets both the round's card and the request's answer. They are separate
  things.

### 3.6 What the asker sees

- **Today**: one card per request that is open, claimed, or answered but not yet seen (at most 3, then
  "N more"). It shows "Waiting for your agent", "<agent label> is on it" (`AgentBadge`), or the
  answer with **Got it**. A withdrawn request leaves Today.
- **`/requests`** (Profile row, and the card's link) lists every request, newest first. Its detail
  page `/requests/:id` shows the body, its subject linked, the status, the answer with its agent, and
  either **Withdraw** (open, claimed) or **Got it** (answered). Another user's id is a 404 (refusals
  do not reveal ids).
- **Push**: `answer` sends one notification after its commit (`notifyRequestAnswered`, through
  `sendEach`). The body is "Your agent answered: <first 80 characters>", it opens
  `/requests/:id`, is tagged `agent-request-<id>` and has a 24 h TTL. It goes to the asker's devices
  with the per-device agent toggle on. This is the toggle the rounds use today
  (`user_device.muse_rounds`, renamed by #1282), so one toggle covers "your agent did something". A
  failed send is logged, and never undoes the answer.

### 3.7 API parity

| Domain action | Page | API (`src/web/requests/api-routes.ts`) | MCP |
| --- | --- | --- | --- |
| `askAgent` | `POST /requests` (outbox `request`) | `POST /api/v1/agent-requests` `createAgentRequest` | (agents do not ask) |
| list, read | `GET /requests`, `/requests/:id`, Today | `GET /api/v1/agent-requests` `listAgentRequests`, `/:id` `getAgentRequest` | `list_agent_requests` |
| `withdrawRequest` | `POST /requests/:id/withdraw` | `POST /api/v1/agent-requests/:id/withdraw` `withdrawAgentRequest` | (asker only) |
| `markAnswerSeen` | `POST /requests/:id/seen` | `POST /api/v1/agent-requests/:id/seen` `markAgentRequestSeen` | (asker only) |
| `claimRequest`, `answerRequest` | (agents only) | (agents only) | `claim_agent_request`, `answer_agent_request` |

- The page writes join `PAGE_WRITES` with their API twins.
- The agent-only actions are classified as MCP-only in `MCP_WRITES`, with the reason "an agent's
  side; the owner's app never claims".
- The changes feed carries `agentRequest`.
- The authorization matrix (`authorization-*.spec.ts`) gains the request routes: another user's
  request is a 404 on every surface.

## 4. (a) OAuth for `/mcp`

### 4.1 Where each piece lives

The issuer is the public MCP origin, `https://closet-mcp.kashhq.com`. It comes from a new
`MCP_PUBLIC_URL` (`https://closet-mcp.kashhq.com/mcp`). That URL is the canonical resource the spec
names, and Claude requires the resource to equal the URL the user enters. When it is unset, OAuth is
off: the discovery documents are 404, and the 401 carries no pointer. `loadConfig` refuses the boot,
naming the key, when:

- the URL is not `https`,
- its host is not `SITE_URL`'s or an `ALLOWED_HOSTS` entry, or
- `SITE_URL` is not `https` (every authorization server endpoint must be https).

| Endpoint | Host | Reached by | Surface |
| --- | --- | --- | --- |
| `POST /mcp` | public | the agent's cloud | `mcp` (exists) |
| `GET /.well-known/oauth-protected-resource/mcp`, and `/.well-known/oauth-protected-resource` | public | the agent's cloud | `oauth` (new) |
| `GET /.well-known/oauth-authorization-server` | public | the agent's cloud | `oauth` |
| `GET`, `POST /oauth/authorize` | **`SITE_URL`, tailnet only** | the phone's browser sheet | `page` |
| `POST /oauth/token` | public | the agent's cloud | `oauth` |

The authorization endpoint sits on another host than the issuer. RFC 8414 allows this, and only the
user's browser ever goes there, so the sign-in form never faces the internet. The phone already
reaches `SITE_URL` the way it reaches the PWA: Tailscale on iOS and Android routes every app, the
agent app's sheet included. This is the one assumption to prove on a device (issue A5). If a client
turns out to need a public authorization endpoint, the fallback is for the gate to forward
`/oauth/authorize` too. That puts a password form on the internet, held only by the sign-in budgets,
and is an owner decision then, not now.

### 4.2 The flow on a phone

1. In the Claude app (web or desktop is the primary path; mobile adding is in beta, and a connector
   added anywhere syncs to the phone), the user opens Settings › Connectors › Add custom connector
   and enters `https://closet-mcp.kashhq.com/mcp`. They leave the OAuth client on the default
   ("Use Claude's published identity", which is CIMD).
2. Claude's cloud POSTs `/mcp` with no token and gets a **401**:
   `WWW-Authenticate: Bearer realm="closet", resource_metadata="https://closet-mcp.kashhq.com/.well-known/oauth-protected-resource/mcp", scope="closet:read closet:write"`.
   It must be a 401, because Claude ignores the header on a 200.
3. It fetches the Protected Resource Metadata (RFC 9728):
   `{ resource: MCP_PUBLIC_URL, authorization_servers: [issuer], scopes_supported: ["closet:read", "closet:write"], bearer_methods_supported: ["header"], resource_name: "Closet" }`.
4. It fetches the Authorization Server Metadata (RFC 8414) at the issuer:
   - `issuer`
   - `authorization_endpoint: SITE_URL + /oauth/authorize`
   - `token_endpoint: issuer + /oauth/token`
   - `response_types_supported: ["code"]`
   - `grant_types_supported: ["authorization_code", "refresh_token"]`
   - `code_challenge_methods_supported: ["S256"]`
   - `token_endpoint_auth_methods_supported: ["none"]`
   - `client_id_metadata_document_supported: true`
   - `authorization_response_iss_parameter_supported: true`
   - the scopes

   It has no `registration_endpoint` and no `offline_access`: refresh tokens are always issued.
   `/.well-known/openid-configuration` is a 404 (JSON), never the `{}` catch-all.
5. The app opens a browser sheet on
   `SITE_URL/oauth/authorize?response_type=code&client_id=<https CIMD URL>&redirect_uri=https://claude.ai/api/mcp/auth_callback&code_challenge=<S256>&code_challenge_method=S256&state=...&scope=...&resource=MCP_PUBLIC_URL`.
6. **`GET /oauth/authorize`** validates the request before anything else:
   - `client_id` is an https URL. Its document is fetched through `createOutboundFetcher`, the
     document's `client_id` must equal the URL exactly, and `redirect_uri` must be one of its
     `redirect_uris`, an exact string match. A loopback `http://localhost` / `127.0.0.1` redirect
     matches with any port (RFC 8252, Claude Code).
   - `resource` equals `MCP_PUBLIC_URL`.
   - `code_challenge_method` is `S256`, and the challenge is 43 to 128 characters.
   - Until `redirect_uri` is proven it **never redirects**: a bad request is the 400 page naming the
     problem. After that, errors go to the redirect URI with `error`, `state` and `iss`.

   Then it renders the **consent page** (section 4.4), with the validated request in one signed
   hidden field. This is an HS256 JWT on the app's secret, audience `oauth-consent`, valid 10
   minutes. The POST trusts that field, not loose hidden inputs, and does not fetch the document a
   second time.
7. The user approves on the consent page with their email and password (4.4).
   **`POST /oauth/authorize`** verifies them and writes a one-time code (4.5), then answers a **303**
   to `redirect_uri?code=...&state=...&iss=<issuer>`. Deny is a 303 with `error=access_denied`.
8. Claude's cloud POSTs **`/oauth/token`** (form-urlencoded) with `grant_type=authorization_code`,
   `code`, `code_verifier`, `redirect_uri`, `client_id` and `resource`. Closet checks the PKCE
   verifier, the client, the redirect and the resource against the code, and mints the grant: an
   access token (1 h) and a refresh token. Both answers are `Cache-Control: no-store`.
9. Claude calls `/mcp` with the access token. Before it expires, or on a 401, Claude POSTs
   `/oauth/token` with `grant_type=refresh_token`. Closet rotates the token and answers both the new
   access token and the new refresh token.

### 4.3 Client registration: Client ID Metadata Documents only

- The 2026-07-28 spec says the authorization server SHOULD support CIMD, and calls DCR deprecated.
- Claude uses CIMD when the metadata advertises it together with `none`. ChatGPT names CIMD its
  preferred method. Claude Code has a published CIMD document.
- CIMD needs no registration endpoint, so there is no DCR spam surface and no client table.

The fetch is a **user-supplied URL**, so it goes through `createOutboundFetcher`, and that needs one
change. The fetcher today accepts a JSON body only from a fixed `hosts` list. CIMD needs **an untrusted
JSON document from any public host**:

- no redirects,
- `application/json`,
- at most 8 KB,
- a 5 s timeout,
- every resolved address public.

That is a new, reviewed option on the fetcher (A2), not a bare `fetch()`. The document is read on
every `GET /oauth/authorize` and never cached (a connect is rare). It is validated by a TypeBox
schema: `client_id`, `client_name` (shown trimmed to 60 characters), and `redirect_uris` (1 to 5,
each https or loopback). A client whose document cannot be fetched or validated gets the 400 page:
"This app's sign-in details could not be read".

### 4.4 Consent: email and password, no session

**Decision: the consent form asks for the account's email and password every time, reads no
session cookie, and sets none.**

- *The step-up rule.* Approving hands out a credential, and every route that hands one out asks for
  the current password.
- *The browser sheet is not the PWA.* An iOS home-screen app keeps its own cookie jar, apart from
  Safari's and the agent app's sheet. A session-based consent would therefore send the user through
  the sign-in page and then ask for the password again. Asking once in the consent form is one
  prompt either way.
- *Nothing lingers in the sheet.* There is no `returnTo` through `signInReturnTo` (an `/oauth`
  target with a code challenge looks like a credential), and no year-long cookie left in a browser
  the user never sees again.
- When a session is present (Android Chrome Custom Tabs share Chrome's jar), the email is prefilled.
  It is still not trusted.
- The check is the sign-in's own: the same lookup, one bcrypt comparison against the
  unknown-account hash for an unknown email, `markSecretChecked`, and the same refusal text. It
  counts on the sign-in budgets (`SIGN_IN_LIMIT` + `SIGN_IN_ACCOUNT_LIMIT`, one checker, the third
  door). A wrong password re-renders the form 400 with the email kept and the password never echoed
  or logged.

The page (phone first, `PageShell` without the tab bar) shows:

- **The redirect host** as the line the user must read: "Closet will send access to **claude.ai**".
  This is the spec's MUST.
- The client's name, as the client tells it ("Claude"), with the host its document lives on
  ("listed at claude.ai").
- A warning when the client's document host and the redirect host differ, and another when the
  redirect is loopback only ("only an app on this device").
- The token's scope, as Agent Access sets it: read-only unless "Can make changes" is ticked, which
  is unticked by default even when the client asked for `closet:write`; and "Only my wardrobe".
- **Name this connection**, defaulting to the client's name. This becomes the token's `name`, so it
  becomes the agent's label (`agentLabelSql`).
- The fields Email and Password, then Allow and Deny.

The route is `public: true`, `secretPath: true` (the query carries the challenge and the state) and
`no-store`. It runs on the page surface, so the same-origin hook holds the POST to `SITE_URL`'s
origin, as any form. It is not a `STATELESS_ROUTES` entry. The CSP's `frame-ancestors 'none'` stops
the page being framed.

**CSP gotcha**: `form-action 'self'` covers the redirects that follow a form's submission in
Chromium, so the POST's 303 to `claude.ai` would be blocked. The consent page's own response must
widen `form-action` to `'self'` plus the validated redirect URI's origin. That needs a per-response
CSP hook in `csp.ts`; only this route uses it, and `delivery.spec.ts` must still match.

### 4.5 Codes, grants and tokens on the existing model

**An OAuth connection is a `personal_access_token` row of kind `mcp`.** Static or OAuth, it is one
agent with one id. That id carries `originOf`, `agentLabelSql`, the feedback cursor, rounds,
request claims, `read_only` / `own_wardrobe_only` (fixed at consent, never changed),
`MAX_ACTIVE_TOKENS`, Agent Access's list and revoke, and the new-password revocation. Nothing
downstream of `authenticateToken` learns that OAuth exists.

| Change | Where |
| --- | --- |
| `oauth_client_id text null` | the CIMD URL; null for a static token. Agent Access shows its host instead of the prefix |
| `access_expires_at timestamptz null` | null for a static token (never expires) |
| `refresh_token_hash varchar(64) null`, unique | the live refresh token |
| `previous_refresh_token_hash varchar(64) null`, indexed | the one it replaced, for reuse detection |
| `token_hash` | now the **current access token's** hash, replaced on each refresh |
| new table `oauth_authorization_code` | `id`, `code_hash` (unique), `user_id` FK (indexed), `client_id`, `redirect_uri`, `code_challenge`, `resource`, `name`, `read_only`, `own_wardrobe_only`, `password_fingerprint`, `expires_at`, `used_at`, `token_id` FK null (indexed) |

- **Consent writes a code**, not a token. The code is `closet_code_` + 32 bytes, stored hashed, and
  lasts 2 minutes. The row is stamped with the password's fingerprint (`right(password, 8)`) read in
  the same statement that checked it.
- **The exchange mints the grant** through `createToken`, whose under-the-lock recheck takes a
  verified fingerprint as well as a verified password. A password changed between consent and
  exchange is `invalid_grant`, as a push subscribe and an invite recheck the session's stamp.
- The code is marked used in the same transaction. A **second use of a code** revokes the grant it
  minted (`token_id`) and is `invalid_grant` (RFC 6749 4.1.2).
- At `MAX_ACTIVE_TOKENS` the exchange is `invalid_grant`, and the consent page says beforehand that
  Agent Access is full.
- **A new consent for the same `client_id` revokes that user's earlier grant from it**, in the
  mint's transaction, so re-adding a connector leaves one live grant, not a pile of orphans. The new
  grant's feedback cursor starts empty: the agent is told everything once again, which is harmless.
- **Tokens.**
  - The access token keeps today's shape (`closet_` + 32 bytes), so `presentedBearer`, the hash
    lookup and the log assertions are unchanged. It lasts 1 h (`OAUTH_ACCESS_SECONDS`).
    `authenticateToken` adds `and (access_expires_at is null or access_expires_at > now())` to its
    one statement. An expired one is the 401 with `error="invalid_token"`, which tells Claude to
    refresh.
  - The refresh token is `closet_rt_` + 32 bytes. `scrubSecrets` and the never-logged assertions
    cover both new shapes.
- **Refresh rotates both tokens** in one statement keyed by `refresh_token_hash`:
  - The old refresh hash moves to `previous_refresh_token_hash`, and the old access token dies at
    once.
  - A presented refresh token that matches some row's `previous_refresh_token_hash` is **reuse**:
    the grant is revoked, a warn line names the token id, and the answer is `invalid_grant`. This is
    OAuth 2.1's public-client rule. A client that lost a rotation answer reconnects, which is the
    price of theft detection.
  - A revoked, idle or unknown refresh token is `invalid_grant`, which is what Claude expects.
- **Idle**: a grant unused for `OAUTH_IDLE_DAYS` (90) is refused as revoked, as device tokens are
  (`idleExpired`). Static agent tokens still never idle. An OAuth grant was minted for a hosted
  service from a sheet, and reconnecting takes half a minute.
- **Audience binding**:
  - `resource` must equal `MCP_PUBLIC_URL` at authorize and at token (`invalid_target`).
  - A token is kind `mcp`, so `/api` refuses it.
  - There is one resource, so the kind is the audience.
  - Closet never forwards a token anywhere (it passes nothing through).
- **`sv` and sessions**:
  - Sign out everywhere bumps `session_version` and, as today, revokes no agent token, OAuth ones
    included.
  - A new password revokes every token row, OAuth grants included. Outstanding codes die through
    their fingerprint stamp.
  - An OAuth grant never carries `sv`: it is not a session.
- **Maintenance**: the nightly job deletes `oauth_authorization_code` rows a day past `expires_at`.
- **Logs**, one `logOp` line from each action: consent granted or denied (user, client host, scope),
  grant minted (token id), refresh (token id, at debug: hourly per grant), reuse (warn), and the
  idle refusal. Never a code, token, verifier, challenge or state.

### 4.6 Routes, surfaces and the root hooks

- **New surface `oauth`** (`src/web/surface.ts`, set on the discovery and token routes):
  - It never resolves the cookie.
  - Errors are JSON. The token endpoint's are RFC 6749 section 5.2 (`{ error, error_description }`,
    400, or 401 for a client error); the discovery documents' 404 is `{ error: "not_found" }`.
  - The same-origin hook treats it like the bearer surfaces: a missing Origin passes (server to
    server), and a foreign one is a 403. No CORS: the clients we target call from their servers.
  - `assignSurface` refuses `oauth` outside `/.well-known/oauth-*` and `/oauth/token`.
- **Rate limits**:
  - `OAUTH_TOKEN_LIMIT` per address, for refusals only, like `BEARER_REFUSAL_LIMIT`, so a healthy
    client's hourly refresh never counts.
  - `OAUTH_AUTHORIZE_LIMIT` per address on `GET /oauth/authorize`, because each one makes an outbound
    fetch.
  - The consent POST uses the sign-in budgets.
  - The discovery documents share `HEALTH_LIMIT`'s shape: 60 a minute.
- **Host allowlist (#702)**: no change. The MCP host is already an entry. `/oauth/authorize`
  additionally 404s when the request's host is the MCP public host (defence in depth behind the
  gate).
- **`/.well-known/*`**: the specific routes win over the `{}` catch-all. `openid-configuration`, and
  the OAuth names while OAuth is off, are JSON 404s.
- **Request log**: `/oauth/authorize` and `/oauth/token` are `secretPath`. The token endpoint's body
  is never logged (it never is).
- **Homelab changes** (issue A5, homelab repo):
  - `closet-mcp-gate`'s Caddyfile forwards, as exact case-sensitive expressions like `@mcp`:
    - `GET /.well-known/oauth-protected-resource`
    - `GET /.well-known/oauth-protected-resource/mcp`
    - `GET /.well-known/oauth-authorization-server`
    - `POST /oauth/token`

    Its "NEVER add a route" comment and README gain this list and why. Still no access log: the
    token endpoint's body carries codes and refresh tokens.
  - The closet compose passes `MCP_PUBLIC_URL`.
  - The production host's Caddy needs no change: it already forwards everything on `SITE_URL`.
  - Anthropic reaches the public host from `160.79.104.0/21` on 443 (Pangolin's TLS), which already
    holds.

### 4.7 Threats

| Threat | Mitigation |
| --- | --- |
| Open redirect | Never redirect before `redirect_uri` exactly matches the client document's list; until then, the 400 page. The 303 target is the validated URI, never a parameter of the POST (it rides in the signed request). |
| Code interception | PKCE S256 only (`plain` refused). The code lasts 2 min, is single use, and is bound to the client, the redirect and the resource. Reuse revokes the grant. `iss` in the response (RFC 9207, mix-up). The code only ever travels to an https or loopback redirect. |
| Consent phishing (a crafted authorize link with a hostile CIMD client) | The redirect host is the headline. A host mismatch and loopback-only redirects warn. Email and password are required. Read-only is the default. The form is tailnet-only, so the link works only for a household member on the tailnet. The granted name and host show in Agent Access, revocable in one tap. |
| Token theft | Hashed at rest. The access token lasts 1 h. The refresh rotates with reuse detection. `no-store`. Never logged. A new password ends everything. Revocation in Agent Access. Kind-bound, so a stolen token opens `/mcp` only, within its scope. |
| Registration spam | No DCR. A CIMD fetch is limited per address, capped in size and time, SSRF-checked, and stores nothing. |
| SSRF through `client_id` | `createOutboundFetcher` only: public addresses, the dialled address checked, no redirects. |
| CSRF on consent | The same-origin hook, `SameSite=Lax`, and the signed request. The consent reads no cookie, so a forged POST would still need the password. |
| Password guessing through consent | Tailnet-only, plus the sign-in budgets shared with login (one checker). |
| Confused deputy | Not applicable: Closet calls no upstream API with a client's token. |

### 4.8 Offline and the PWA

- Consent happens in the agent app's browser sheet, online and on the tailnet. It is not a PWA
  screen and is never cached: `/oauth/*` is network-only in `src-sw.ts`, kept off the navigation
  handler and the warm list. Android's Custom Tabs share Chrome's service worker with the installed
  PWA, so without this the worker could answer the sheet's navigation from the page cache or the
  offline page.
- Agent Access in the PWA lists the OAuth grants (a cached read showing its freshness; revoking is
  `PostForm`, disabled offline). The new columns ride its existing statement. Copy is #1281's.
- Requests (section 3) are the offline half: a person can ask while offline, and any agent picks the
  request up once it syncs.

### 4.9 API parity

- OAuth is authentication plumbing, not a domain operation. `POST /oauth/authorize` is a page write
  classified in `operations.ts` as `STEP_UP`, like `POST /auth/tokens`: it hands out a credential
  and has no API twin. Native clients sign in with device tokens.
- `/oauth/token` and the discovery documents are on the `oauth` surface, outside `PAGE_WRITES` and
  `MCP_WRITES`.
- The grants' listing and revoking are Agent Access's existing routes (`AGENT_ACCESS`), unchanged.
