# JSON API: reference

Moved out of `AGENTS.md` (#723) so the auto-loaded doc keeps only invariants, gotchas and ownership. Not auto-loaded: read it before changing this area. Where it disagrees with the code or a spec, they win.

- **The credential** (continued)
  - A token in the query string is a 400 before anything reads it (`refuseQueryToken`): a key named `access_token` or `token` in any case, or any value holding `closet_`, repeated keys included. The value is never echoed. `loggableUrl` filters credential shapes on every surface (`scrubSecrets`).
  - Authentication happens once, at onRequest (after `refuseQueryToken`), before the body is read: an unauthenticated request is a 401 whatever its body (never a 400 or 413). A token revoked by another request mid-flight finishes that request; the next one is a 401 (the cookie's model).
- **Sign-in and sign-out** (`src/web/auth/api-routes.ts`, plan section 3):
  - `POST /api/v1/auth/token` takes `{ email, password, deviceName }` and answers 201 `{ token, tokenId }`, `Cache-Control: no-store`. It sets no cookie and is public.
    - It shares `checkSignIn` (`src/web/auth/sign-in.ts`) with the login page: `normalizeEmail`, then exactly one bcrypt comparison on every path, the unknown-account hash for an unknown email.
    - It mints through `createToken` with the hash it verified. A password changed (or an account deleted) under the lock is the same 401 "Incorrect email or password" as a wrong password, logged `password-changed`.
    - At the device cap the least recently used device is evicted, never an agent token (per kind, #189). The sign-in line names the evicted row.
  - A device token unused for `DEVICE_IDLE_DAYS` (90; `last_used_at`, else `created_at`, both stamped from the app's clock) is refused as revoked by `authenticateToken` on the row it already reads (#705): the 401, never the gate's 429. Agent tokens never idle out.
  - `DELETE /api/v1/auth/token` revokes the calling token only, 204. It is 204 too when something revoked the token since the request authenticated, logged `(already revoked)`.
  - `GET /api/v1/me` returns `{ id, email, timeZone, today, features: { weather, push }, version }`: `today` is `todayIn(APP_TIMEZONE)`, the day a wear or wash defaults to; `version` is `config.release`, the one `/health/ready` reports; `features` is what the server registered. It reads only the token's row. **A new optional feature** (routes registered only under a switch) adds a boolean to `Me.features` (`auth/api-routes.ts`) from the value `apiPlugin` registers on, and states the condition in each operation's description, as `weatherOnly` does (`weather/weather-resource.ts`); a client reads the flag, never a 404 (#715).
  - `createToken`'s device-cap eviction takes that kind's least recently used token with no exclusion, so a token-authenticated route that can mint needs one added, or a device evicts itself (decisions 2026-11-13, #189).
- **Limits**:
  - `SIGN_IN_LIMIT` is ONE checker for the login page and this sign-in (`signInLimits.address`, `createSignInLimits` in `webPlugin`), so an address gets 5 a minute in all and the 6th is a 429 at either door.
  - `SIGN_IN_ACCOUNT_LIMIT` (5 a minute per SHA-256 of the normalized email) caps guesses spread over addresses, ONE checker for both doors too (`signInLimits.account`, #705); both apply through `signInGuards`, so the doors cannot diverge.
  - `API_LIMIT` allows 120 a minute per token: one checker for the whole API, a preHandler after authentication. A route that serves private photo bytes sets `config: { apiPhotoBytes: true }` and counts on `API_PHOTO_LIMIT` (600 a minute per token) instead; the 401 is never counted on either: it counts on `BEARER_REFUSAL_LIMIT` (30 refusals a minute per address, shared with `/mcp`; past it a missing, malformed or unknown token is a 429, a revoked or agent token still the 401). The sign-in is public, outside that budget; an unknown path's 404 is never counted.
  - `WEATHER_SEARCH_LIMIT` and `WEATHER_LOCATION_LIMIT` are shared with the page twins, one checker each in `weatherLimits` (`createWeatherLimits`, built in `webPlugin`): the weather search (page and API), the home write, the phone-location write and a trip's destination (page and API each), keyed by the token's user or the session's, so a user's two doors are 20 searches and 10 of each write a minute in all. A trip page's own search stays a route config (decisions 2026-11-13, #195a).
  - `LINK_IMPORT_LIMIT` is ONE checker for the page's link import, its photo choice and `POST /garments/link-imports` (`linkImportLimit`, built in `webPlugin`), counted after the wardrobe is judged and the cheap body checks pass (a refused body spends none, at either door).
  - A 429 is a problem with `Retry-After`.
- **Errors are RFC 9457 problem+json** (continued)
  - `code` comes from `HttpError.code`. `NotFound`/`Forbidden` keep the page's message, which names no id.
  - A 500 has no `detail`. An unknown path's detail is "Not Found", never the URL.
  - A 503 `busy` (`OwnerLockTimeout`) carries `Retry-After`, as `HttpError.retryAfterSeconds` sets it.
- **Errors are RFC 9457 problem+json** (continued)
  - No CORS: no `Access-Control-*` header is ever sent, and a preflight is a problem 404.
- **The spec** (plan section 5):
  - `npm run api:spec` (`scripts/api-spec.ts`, the only importer of the devDependency `@fastify/swagger`) registers `apiPlugin` on a bare Fastify and writes `openapi.json` (OpenAPI 3.1). `info.version` is `v1`, never the sha.
  - `Problem` is one component (`addSchema`, named by its `$id`).
  - `nameSchemas` (`scripts/api-spec.ts`, #714) post-processes the emit for client generators, never the wire: every schema with a `title` becomes `components.schemas.<title>` and a `$ref` (a title on two different shapes fails the emit: rename one), an `anyOf` of single-value literals of one type (string, number, integer, boolean) becomes one `enum`, and the changes feed's item union is a `oneOf` (generators honour a discriminator only there) carrying `discriminator: { propertyName: 'resource', mapping }` (its branches are titled `<Resource>Change` for the mapping). A new resource schema needs a unique `title`.
  - `GET /api/v1/openapi.json` (public) serves the committed file, imported, so tsc copies it into `dist/`.
  - `scripts/api-spec.spec.ts` (unit) fails when the committed file is not what the routes generate. It validates the document (`@seriousme/openapi-schema-validator`) and asserts every operation's declarations.

- **Resources** (`resource.ts`): `ListOf(item, { title, description, extra })` answers `{ data, pagination: { nextCursor?, limit } }` (plus `extra`, the grid's `total`); `ListLimit(featurePage)` caps at 100; `ListCursor` is the query's opaque cursor, `idCursor`/`readIdCursor` the id keyset (a forged one is a 400 `validation`), `rankedIdCursor`/`readRankedIdCursor` a `(rank, id)` one whose rank 0 is spelled as the id cursor (the garments' keyword search); `offsetCursor`/`readOffsetCursor` a position, for an order no keyset holds (the trips); `literals(VALUES)` a stored enum; `withoutNulls(row)` drops null fields (required: Fastify serializes a null through a `string` schema as `""`); `asResource(Schema, record)` shapes a nulls-kept record by its schema at every level (its keys only; a null dropped unless the schema declares it, `Nullable`; a Date or Buffer throws: the mapper serializes it). A feature's mappers and schemas sit beside it (`wardrobe/garment-resource.ts`); an entity MCP also answers is a nulls-kept record the API sends through `asResource` and the tool projects (`project`, MCP's "A tool answers an entity", #711). A form reader's refusal becomes the 400 through `refusedBody(errors, pointerOf)` (`refused-body.ts`: the garment, repair and trip forms).
- **A grantee's `?ownerId=`** share is read in the token's statement (`authenticateToken`'s `shareOf`, remembered as the session's is, #170) and `actorOf(request)` takes the token's user, so a feature guard (`garmentGuard`) works unchanged here and a grantee's read costs what the owner's does.
- **Idempotent creates** (#717, `src/db/create-once.ts`): a create an offline client retries after a lost 201 carries `clientId`, stored on the row, and the `(owner, client_id)` unique constraint arbitrates (`on conflict ... do nothing`, never a read first): 201, a retry 200 with the first row (the retry's body is ignored, the id names the create), and the id of a row deleted since a 410 `gone` (the sync triggers' tombstone, CL410). Garments (`createGarmentOnce`), brand sizes (`addBrandSizeOnce`), capsules (`createCapsuleOnce`) and trips (`createTripOnce`) do; a new create of a synced root copies them through `createOnce`. Outfits, outfit picks and calendar entries are idempotent by their own key (a garment set, an outfit on a day) and only log the id; a saved look has no client id column and logs it. A wear's is `setWoreToday`'s. `api-idempotent-creates.spec.ts` is the table over them.

- **Tests**: `t.api(token, request)` (harness: no cookie, no Origin) and `deviceToken`/`signInDevice`/`expectProblem` (`test/integration/api.ts`). `api.spec.ts` covers the surface, the credential and every refusal; `api-statements.spec.ts` pins each route's statements (sign-in 6 like its twin `POST /auth/tokens`, `/me` 1 plus the last-use write, sign-out 3, the spec 0, the garment reads 3 as their pages, a grantee's too; each garment write against its page twin, equal but PATCH +1 and tags −1). `api-garments.spec.ts` covers the wardrobe's reads (paging, stable cursors, filters, the owner's records) and writes; `api-outfits.spec.ts` outfits and wears; `api-trips.spec.ts` trips, packing and extras; `api-wishlist.spec.ts` and `api-capsules.spec.ts` theirs; `api-calendar.spec.ts` the calendar, Wear this, selfies and the week plan; `api-inspiration.spec.ts` saved looks; `api-style.spec.ts` the style profile, its rules and the shared wardrobes; `api-sizes.spec.ts` sizes; `api-changes.spec.ts` the changes feed (insights' and the recap's API rows are `today.spec.ts`'s); `api-weather.spec.ts` Today, the weather and a trip's (its own app, weather on, Date pinned to `STUB_WEATHER_NOW`); `api-ideas.spec.ts` ideas, the pick, clashes and the feedback; `api-photos.spec.ts` the photo's, the repair log's and the link import (multipart refusals, a grantee's upload, the shared budget); the photo and repair writes pin their page twins' counts, the link import 11 (no twin saves); every trip route equals its page twin, every wishlist and capsule route too but two capsule reads that skip what only the page draws, every look route too, every Today and weather route too (a section with its own weather-on app). The shared twin device has spent most of its `API_LIMIT` minute by the later sections, so a new section signs in a user of its own (the looks'). Each area's API cases join its existing `authorization-<group>.spec.ts` as a third via.

## Parity (#191)

- **Refusal parity**: a matrix route (`authorization-<group>.routes.ts`) whose page route has a twin must carry `api: { ok, request }`, which must reach that operation. A read may carry one too (GETs are not classified): `GET /wardrobe` and `GET /wardrobe/:id` replay on `listGarments` and `getGarment`. `authorization-coverage.spec.ts` counts an `api` request as covering its API route, so an API id route needs a matrix twin or an EXEMPT line. Its group's matrix then replays every case on the twin with each actor's device token: the same outcome, `login` being the API's 401 (`docs/testing-integration.md`).

## Adding an API route

1. Add its operationId to `OPERATIONS` and turn its page twin's `pending` line into `api` (`operations.ts`). Write it in `src/web/<feature>/api-routes.ts`, a `FastifyPluginCallbackTypebox<ApiOptions>` registered in `apiPlugin`, calling the same domain function the page calls (parse, call, map). The user is `request.accessToken!.user.id`. A public route says `config: { public: true }` and `schema.security: []`.
2. Declare `operationId` (camelCase, unique), `tags`, a `summary`, the TypeBox `body`/`querystring`/`params` (a multipart route: `multipartBody`, below), and `response: apiResponses({ 200: Resource })`. Resource schemas carry `title` and `description`. Fastify serializes through them, so an unlisted column never leaves. `requireContract` refuses the route at boot without them.
3. A querystring is closed (#577): an undeclared parameter is a 400 `validation` whose `errors` name `querystring/<name>`, for every route with no per-route work (`validator.ts`: `declareQuerystring` gives a route without one an empty schema; the compiler sets `additionalProperties: false` and turns `removeAdditional` off). Declare every parameter the route accepts (`ownerId`, `v`), never loosen it; `api.spec.ts` sends a bogus one to every GET.
4. JSON is camelCase and leaves out nulls. A household day is `YYYY-MM-DD`, an instant ISO 8601 with `Z`, money a decimal string, and lists `{ data, pagination }` (plan section 2).
5. `npm run api:spec` and commit `src/web/api/openapi.json` in the same PR. Pin the route's statements in `api-statements.spec.ts`. Give each matrix route of its page twin an `api` request.

## Gotchas

- **A body is closed only where its schema says `additionalProperties: false`** (#195c: the style profile and outfit rules): bodies compile with `removeAdditional: false`, so a closed one refuses an extra key as a 400 at `body/<key>` instead of stripping it (ajv strips inside an `anyOf` while trying branches). Every other body is open: closing one is a contract change (decisions 2026-11-13).

- **`CloneType(schema, { description })` keeps the schema's own description** (TypeBox 0.34 spreads the options under it): it adds one to a bare schema (`IsoDateSchema`, `RowId`, `literals(...)`), never overrides one (`ListCursor`'s, a titled resource's). Say the rest on the route or the parent schema, and read the regenerated spec (#193c's review).
- **A route answering bytes** (a private photo) declares its 200 as `Type.Unsafe({ description, content: { 'image/webp': { schema: { type: 'string', format: 'binary' } } } })`: Fastify never serializes a stream, and the spec documents the media type. Its refusal is a problem like any other (`servePrivatePhoto`), never the page's bare 404. Its schemas are `private-photo-bytes.ts`'s (`PhotoBytes`, `PrivatePhotoParams`, `PrivatePhotoQuery`).
