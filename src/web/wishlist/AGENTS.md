# Wishlist

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds the agent's suggestions and option groups; The API.

`src/wardrobe/status.ts`, `src/web/wardrobe/status.ts`, `src/web/wishlist/` (#18, slice 18a; plan section 11). A wishlist item is a garment with `status = 'wishlist'`: same table, form, photo, link import and sharing as any garment, and out of every closet read.

- **The status is a state machine.** `garment.status` (`wishlist`, `closet`, `archived`; a check constraint) replaced `archived boolean` in `drizzle/0014_garment_status.sql` (true to archived, false to closet; `garment-status-migration.spec.ts` (retired 2026-10-13)). Transitions are events, each with one edge: `buy` wishlist to closet, `archive` closet to archived, `restore` archived to closet (`garmentStatusTransition`, pure, `status.spec.ts` covers all nine pairs). Refused on purpose: wishlist to archived (dropping a wishlist item is a delete: it has no history to keep), anything to wishlist (wanting another is a new item: clone or "Find a replacement"), and self-moves. A garment is inserted with an entry status (`insertGarment`'s `EntryStatus`: closet or wishlist; a clone of a wishlist item lands on the requester's wishlist, anything else in their closet, `statusOfClone`) and changed afterwards **only by `setGarmentsStatus`** (`setGarmentStatus` for one; rows locked in id order, the machine asked for each, a purchase's day and price written with it, and its instant, `bought_at`, #337: the agent's feedback): archive (one, or select mode's, #677), restore, "Bought it" (`buyGarment`, which archives the replaced garment in the same transaction only when asked) and the seed.
- **`inCloset` is the one predicate of every closet read** (`src/web/wardrobe/status.ts`, with `onWishlist`, `ownedGarment` = closet or archived, and `inScope` for `GridFilters.scope`): the grid (`ownedGarment` with "Show archived"), its filter choices, the builder's cycles, capsules' counts, strips and pages, tagging, laundry and the wash counts, `availableGarment`/`isAvailable`, the MCP tools' closet reads, insights (#17). Writes that may only name owned garments filter by `ownedGarment`: capsule membership (`changeMembership`), `markWashed`, `setAway`; `setWoreToday` answers `'wishlist'`; the wear routes answer a wishlist item 409. Outfit slots follow their own rule, `slotMayNameSql` (Outfits, Incomplete outfits): an outfit nothing holds may hold a wishlist item offered to style with. The outfit generator (#9) reads `availableGarment`, which includes it; "Goes with my closet" (#18b) reads `closetGarmentsSql` (`inCloset`) and locks the wishlist item beside it (see below). `wishlist.spec.ts` proves an item is absent from each read.
- **Replacing**: `garment.replaces_garment_id` (nullable, `ON DELETE SET NULL`, not itself by a check), kept after "Bought it" as the record of what the purchase replaced. The same-owner rule is the writers': `replacementOf` (`src/web/wardrobe/queries.ts`) stores the id through a subquery in the insert or update itself, only when it names a garment of the same owner that is owned now or once, else null. It is read from the form only beside its marker `wishlist=1` (Gotchas). A garment marked `replace_soon` shows "Find a replacement" (owner and MANAGE) to `/wardrobe/new?to=wishlist&replaces=<id>`, prefilled from it (`destinationValues`: category, type, properties, brand, colours, size; not its name, notes, dates, price or care), and lists the wishlist items that would replace it.
- **Shared like the rest of the wardrobe** (owner decision on #18): a VIEW grantee reads the owner's wishlist (gifting; the owner reading a sibling's), a MANAGE grantee adds, edits and buys, only the owner archives what a purchase replaces (a grantee asking is a 403: `purchaseNeed` is ownership) and deletes an item (never a suggestion: 409, see `suggestions.md`). Matrix rows in `authorization-wardrobe.spec.ts`.
- **"Goes with my closet" (#18b; `src/wardrobe/goes-with.ts` pure, `goesWithCloset` in `src/web/gallery/ideas.ts`, `gallery/goes-with.tsx`)**: a wishlist item's page judges it against the closet, **the owner's alone** (it reads their closet and clashes, like ideas; a grantee who reads the item never gets it, and `goes_with_closet` refuses another's item: matrix rows in `authorization-wardrobe.spec.ts`, `mcp-seed.spec.ts`). The generator with the item `locked` (never in a pool, so ideas, Today and picks cannot draw it: `goesWithInputsSql` is the only read that hands one to the generator) over `closetGarmentsSql`: **the whole closet**, dirty and away included (a purchase is judged against what is owned, not today's laundry), **no weather** (worn across seasons; so no layer is drawn and each closet layer is checked on its own, locked with the item), **the item's own formality as the range** (the best few are those dressed at its level; the count still takes every outfit the hard rules allow), **no rotation** (idle days nulled: uniform draws). One search asks for a page as large as `MAX_DRAWS`, so it returns every distinct outfit it met: the count is exact below `OUTFIT_COUNT_CAP` (50) and "50+" past it; the best 3 as `OutfitCollage` cards (display only: no form, `pickIdea` takes closet garments; "Bought it" changes that); per role it is worn with, "k of n" and the best 3 partners (at its formality, then in the most outfits), layers always asked ("No layer goes with it"); **near-duplicates** (`nearDuplicates`: same category, same type, same colour set, not empty; brands ignored, where #20's "add a copy" asks it with `sameBrand`) warn "do I need this?", except the garment it replaces, shown like for like. Seeded by the item's id. The agent inbox counts many items' outfits over one closet read (`unlocksOf`, `suggestions.md`). Theo's merino (replaces T21), padded jacket and Allbirds (twin of the Vejas) are the demo (`34-demo-goes-with`). ~15-35 ms over his 80 garments, so it renders inline; the page logs one debug line.
- **"Bought it" is one owner transaction** (`buyWishlistItem(deps, actor, address, purchase)`, `purchase.ts`, which authorizes and refuses itself, #188): `buyGarment`, then `decide(bought)`, which settles an agent pick's need and writes nothing for an own item. The owner lock comes first: `decide` takes it, and a pick takes it before its garments.
- **The wardrobe plans' addresses are retired** (#337 part B1, `inbox-routes.tsx`): `GET /wardrobe/plans`, `/wardrobe/plans/*` and `/wardrobe/shopping` answer 302 to the inbox, `GET /wardrobe/:id/plan-items` 302 to the garment (302, never 301: nothing caches them for good); an old form's post falls to a 4xx. `plans-removed.spec.ts`, which also sweeps every page for a plan link.
- **A grantee never reads the owner's wears through an item's page**: its closet read leaves out the pool's last-worn subquery (`closetGarmentsSql`, `idleDays: null`; the search draws uniformly, so it fed nothing). "Bought it" on an item no longer on the wishlist is a 409, its form a 302 to the garment.

## Gotchas

- **A wishlist form's `replaces` has its own marker, `wishlist=1`.** Closet forms and forms cached before #18 post neither and must leave the stored replacement alone (the product, care and props markers' rule). The replacement is stored only through `replacementOf`, which is where the same-owner rule lives: a second writer of `replaces_garment_id` must go through it.
- **Routes' rules**: "Bought it" prefills today (`APP_TIMEZONE`) and the listed price, offers archiving the replaced garment (unchecked) only when it is still in the closet and the requester owns it, re-renders a bad date or price as a 400 and 303s to the garment with `?bought=1`; the API takes both fields explicitly (null records none). A wishlist form has no care fields or acquired date; the link import carries `?to=wishlist&replaces=` to the form, while the share target always adds to the closet. `goes-with` is the owner's: a share naming the owner is a 403. The agent's own writes stay MCP's (`agentOnly`); `readInbox` reads the switcher only for a `viewerId`.
- **Moved rules** (detail in `reference.md`): every suggestion decision goes through `decide` (the pure `decideSuggestion`), the page's through `suggestion-actions.ts`. `GET /api/v1/wishlist` is one unpaged resource: the needs sort by what every option unlocks, which only the whole list knows.
