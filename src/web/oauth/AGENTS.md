# OAuth for /mcp

`src/web/oauth/` (#681; design `docs/plans/2026-11-27-mcp-oauth.md`, sections 4.1 to 4.9): hosted MCP clients (the Claude app's custom connectors, ChatGPT's) connect to `/mcp` with OAuth 2.1, per the MCP authorization spec (revision 2026-07-28). Built so far: discovery (#1289), the consent page and its one-time codes (#1290). The token endpoint is #1291.

- **On exactly when `MCP_PUBLIC_URL` is set** (`loadConfig`; `WebConfig.oauth`, built once by `oauthDiscovery`, `discovery.ts`). It is `https://<public MCP host>/mcp`: the resource (RFC 8707/9728) and, by its origin, the issuer. The boot refuses a non-https URL, a path other than `/mcp` or with a query, fragment or credentials, a host that is not `SITE_URL`'s or an `ALLOWED_HOSTS` entry, and a non-https `SITE_URL`. The boot logs `OAuth discovery on: ...` or `OAuth off: ...` (logger `OAuth`).
- **Nothing an agent calls needs the tailnet** (owner, 2026-11-27): `/mcp`, `/oauth/token` and the discovery documents are served on the public MCP host; only `authorization_endpoint` (`SITE_URL/oauth/authorize`, the consent sheet in the person's browser) is on the tailnet. RFC 8414 allows the authorization endpoint on another host than the issuer.
- **The documents** (`routes.ts`, on the `oauth` surface, `public`): Protected Resource Metadata (RFC 9728) at `/.well-known/oauth-protected-resource/mcp` and the bare `/.well-known/oauth-protected-resource` (MCP's fallback; the same document); Authorization Server Metadata (RFC 8414) at `/.well-known/oauth-authorization-server`: `code` only, `authorization_code` and `refresh_token`, S256 only, `none` (public clients), `client_id_metadata_document_supported`, `authorization_response_iss_parameter_supported` (RFC 9207), no `registration_endpoint` (no DCR) and no `offline_access`. `public, max-age=3600`; no statement; one `OAUTH_DISCOVERY_LIMIT` budget per address across them.
- **Off, every name is a JSON 404** (`NotServed`, guards.conf `@not-served`), and `/.well-known/openid-configuration` always is: the exact routes win over the shell's `/.well-known/*` `{}` catch-all, which a discovering client would read as broken metadata.
- **The `/mcp` 401 points here when on**: `WWW-Authenticate: Bearer realm="closet", resource_metadata="<issuer>/.well-known/oauth-protected-resource/mcp", scope="closet:read closet:write"` (`mcpChallenge`, carried by the bearer gate's `HttpError` as `challenge`; the root error handler writes it). A hosted client reads it only on a 401.
- **The `oauth` surface** (`src/web/surface.ts`): no cookie (the root preValidation hook skips it), errors are RFC 6749 section 5.2 JSON (`{ error, error_description }`, `sendOAuthError`, `errors.tsx`) from the error handler and the same-origin hook, a POST with no Origin passes and a foreign one is a 403. `assignSurface` refuses it off `/.well-known/oauth-*`, `/.well-known/openid-configuration` and `/oauth/token`; `/oauth/authorize` is a page.
- **The consent** (`consent-routes.tsx`, a page on `SITE_URL`; a 404 with OAuth off and on the public MCP host). `GET /oauth/authorize` (`OAUTH_AUTHORIZE_LIMIT`, no HEAD twin: each one fetches) proves the request in order (`authorize-request.ts`): `clientIdUrl` (https, a path, no raw `?#@\`, written as the parser writes it, no address literal or local name), the Client ID Metadata Document fetched fresh as `untrustedJson` (`client-metadata.ts`: its `client_id` the URL exactly, a public client, 1-5 https or loopback `redirect_uris`), then `redirect_uri` an exact listed string (a loopback entry on any port, RFC 8252), all capped at `URL_MAX`. Until then a refusal is the 400 page with no link; after, the rest (`response_type`, S256, `resource`, scope; a repeat is `invalid_request`, a repeated `resource` `invalid_target`) is a 400 page with a "Return to <host>" link carrying `error`, `state` and `iss`, **never a redirect of ours** (decisions 2026-11-28). The page puts the redirect host as the headline and the client's name only as what it "calls itself" (`displayText`: bidi, zero-width and control characters out, NFKC, 60 characters), warns on a document host other than the redirect's and on loopback, and defaults to read-only (writes offered only when asked).
- **The signed field** (`consent-token.ts`): the proven request as an HS256 JWT on `ACCESS_TOKEN_SECRET`, audience `oauth-consent`, issuer `SITE_URL`, 10 minutes; the POST trusts it alone and never refetches. `CONSENT_FIELD_MAX` is derived from the claim caps, so a request the GET took always fits the POST's schema.
- **`POST /oauth/authorize`** is `sessionless` (no cookie read or set) and on the sign-in's budgets (`signInGuards`, one checker with the login): Deny is a 303 `access_denied`; Allow runs `checkSignIn` (one bcrypt for an unknown email too) and `grantConsent` (`codes.ts`): one statement that writes the code only if the password is still the one verified and Agent Access has room, not counting this user's grant from the same client (`personal_access_token.oauth_client_id`), stamped with the fingerprint, 2 minutes, hashed; then the 303 with `code`, `state`, `iss`, built with `URLSearchParams` onto any query the URI has. `logOp` `oauth.consent.granted` names the code row, the hosts and the scope.
- **Every answer of both** is `no-store` and `Referrer-Policy: same-origin` (`no-referrer` would null the POST's Origin); both are `secretPath`. The consent page's CSP widens `form-action` to the redirect's origin (`allowFormTarget`, `csp.ts`). The worker never handles `/oauth/*` (`bypassesWorker`). Nightly, `oauth-code-prune.ts` deletes codes a day past expiry. Never logged: the code, state, challenge, password, the field or the client's name.
- **A client document's `logo_uri`, `client_uri`, `tos_uri` and `policy_uri` are never fetched or rendered**: one outbound fetch per consent, and no stranger's image or link on the page.

## Gotchas

- **With OAuth on, the metadata names `/oauth/token` before #1291 builds it**, and a consent's code has nothing to exchange it yet. Production stays off until #1293 sets `MCP_PUBLIC_URL` in the compose, after #1291 ships; never set it earlier, or a connecting client follows the metadata to a 404.
- **The gate forwards only `POST /mcp` today**: the documents reach the internet only once homelab's `closet-mcp-gate` forwards their exact paths (#1293).
