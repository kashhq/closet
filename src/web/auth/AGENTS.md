# Auth

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds the full prose: the cookie and JWT claims, the registration and email-uniqueness write, the session resolver's one statement, sign-in return targets (`return-to.ts`), the revocation statement's anatomy, account deletion, the `Clear-Site-Data` relay, and the file layout.

- **Login is always required** (the upstream `AUTH_ENABLED=false` mode is gone). A JWT (HS256, claims `userId`, `email`, `pwf`, `sep`, `sv`, 365 days) in an `access_token` cookie: httpOnly, `SameSite=Lax` (CSRF depends on it), `Secure` only when the request arrived over https (`sessionCookieOptions`, `request.protocol` through `TRUSTED_PROXIES`; never a blanket `secure: true`, #700). bcrypt passwords. No password reset by email: a locked-out user is `npm run user:set-password` (`docs/operations.md`).
- **The session is resolved once per request** by `createSessionResolver` (`session.ts`) into `req.auth` (`{ user: { id, email } }`, never the hash). Its one statement (`findSessionAccount`) cuts the password fingerprint in SQL (`right(password, 8)`), reads `session_version` and, for a `?ownerId=` request, the share's permission (#170). `sv` is the `session_version` a token was issued under (Sign out everywhere and a new password bump it); `sep` is the restore epoch (`maintenance:after-restore` ends every session, #908). The version is a counter, never a time.
- **Routes need a session unless `config: { public: true }`**; `requireSession` only reads `req.auth`. Without one: a page navigation is a 302 to `/auth/login`; an htmx fragment, fetch or outbox replay (`X-Closet-Queued`) is a 401 with `HX-Redirect`. Handlers take the user as `sessionUserId(request)`.
- **Emails are stored trimmed and lower case** (`normalizeEmail`), unique on `lower(email)` (`user_lower_email_unique`). Registration and update-email check the address inside their one write (`insertUser` / `updateEmail` are `where not exists` statements, #171), so a taken address raises nothing; only the race hits the index, caught as `USER_EMAIL_UNIQUE` by name. Registration hashes before it knows the address is taken, so both cost the same.
- **Step-up rule: every route that changes or hands out a credential asks for the current password** (change password, change email, delete account, Sign out everywhere, creating a personal access token with its scope fixed at mint (#701), creating an edit invite link (#668); a view link stays one tap). Each is `ACCOUNT_LIMIT`ed and says `config: { checksPassword: true }`; the handler takes the hash from `sessionAccount(request)` (a `WeakMap` by request, never on `req.auth`, so no view or log line can reach it); on any other route it throws. Routes that only narrow access (sign out, revoke a token or device) do not ask.
- **Minting rechecks the password under the lock**: `createToken` takes `verifiedPassword` and refuses `password-changed` if the row's differs once it holds the user's lock. A push subscribe and an invite do the same against the session's stamp (`sessionStillOpenSql`, #512, #668).
- **A new password ends every other session in two statements, never one** (`updatePasswordHash`): the new hash (which takes the user's row lock), then the token, device and invite revocations as CTEs of one statement (`revokeSignIns`, shared with `endOtherSessions`). Folding them into one statement (#171) let a token minted during the lock wait survive (#189). Sign out everywhere bumps `session_version` alone and reissues this session's cookie; its scope is device tokens and pushes only.
- **Sign-in does the same work for an unknown email as for a wrong password**: the same lookup, one bcrypt comparison against a constant unknown-account hash of the configured cost (`PASSWORD_HASH_ROUNDS`: 12 in production, 4 in tests), the same page; `verifyPassword` marks the request (`markSecretChecked`) so it answers without Server-Timing. `auth.spec.ts` compares the refusals.
- **Sign-in returns to its page** through `signInReturnTo` (`return-to.ts`), the one reading: `safeReturnTo`, then page targets only (no `/api`, `/mcp`, exports, invite accept/decline), nothing past 2 KB, no credential shape; a bad value is `/`, never a 400. It can carry an invite link, so `GET /auth/login` and `/auth/register` are `secretPath` and every sign-in render is `no-store`. The API's device sign-in takes none.
- **`Clear-Site-Data` is relayed to the landing page** (#244): WebKit applies it only to the response a load ends on, so `createCacheClearRelay` (`session.ts`) sets a 60 s `cache_clear_pending` cookie on a non-document answer carrying it and the next whole HTML document repeats it once. A new way to end a session needs only `endSession` / `startSession`.
- **Deleting an account** locks only the account, then deletes its `file` and pending rows; `file` rows are only its own wardrobe's photos (garment, selfie and inspiration point at `file` by `(photo_id, owner_id)`, #703), so no other wardrobe loses one.
- **A device token** unused for `DEVICE_IDLE_DAYS` (90) is refused as revoked (`idleExpired`, #705); agent tokens never idle out and are minted behind the password.
- **`PostForm`** (`src/web/form.tsx`) is the only native-post form, disabled offline by default (`allowOffline="<reason>"` the one opt-out: guards.conf `@post-form-offline`). Profile (`pages.tsx`) is an index of `SETTINGS_ROWS`; no form above Sign out, and a setting's editor never goes back on it (decisions 2026-11-14).
- Wardrobe permissions come from one `resolveWardrobeAccess` (`src/web/sharing/access.ts`); `/mcp` takes personal access tokens instead of the cookie; `DISABLE_REGISTRATION` sends every registration route to the login page. See Request security.
