# PWA and the service worker: reference

Moved out of `AGENTS.md` (#723) so the auto-loaded doc keeps only invariants, gotchas and ownership. Not auto-loaded: read it before changing this area. Where it disagrees with the code or a spec, they win.

**Client modules** (#713). The page's scripts are TypeScript in `views/assets/page/<name>.ts` (and `views/assets/outbox.ts`), strict under `views/assets/tsconfig.page.json` (DOM lib, in `npm run typecheck`; `page-globals.d.ts` types htmx, `page-vendor.d.ts` the untyped importmap libraries). `npm run generate:pages` (`buildPageModules`, `scripts/static-assets.ts`; `build`, `start:dev` and the integration tier's globalSetup run it) bundles each with esbuild to `public/js/gen/<name>.js`, served as `/js/gen/<name>.js`, the URL the layout and the importmap name through `pageModuleUrl(name)` (`src/web/layout/import-map.ts`); `public/js/gen/` is gitignored and wholly the build's, kept apart from the tracked plain-JS files in `public/js/`: relative imports (the shared rules in `src/`) are bundled in, every importmap name (`src/web/layout/import-map.ts`) stays a bare import, so a module several import is one instance per document. A bare name a module imports needs its `paths` entry in `tsconfig.page.json` and `knip.jsonc`. **Every `data-*` name, id and event a module shares with the markup is a constant in `src/web/page-contract.ts`**, spread by the view that writes it (`{...needsNetwork()}`), so a rename fails the typecheck on both sides; a TS module never spells one itself. **Every page/worker message `type` is a constant in `src/worker-messages.ts`** (`PAGE_MESSAGES`, `WORKER_MESSAGES`, typed message shapes), imported by `src-sw.ts` and the page modules, so a name only one side knows fails the typecheck. Each `generate:pages` leaves `public/js/gen/` holding exactly its outputs (and their precompressed variants), so a renamed or deleted module's output is gone with no record of earlier runs; never write anything else there. It also warns, touching no file, about an untracked `public/js/<name>.js` of a page module's name (obsolete output from before `gen/`: delete it by hand, `git clean -n public/js` lists them; `warnLegacyCopies`; a tracked file is never named, and without git nothing is said). `start:dev` also runs `generate:pages:watch` (esbuild watch into the same directory; a new or renamed module needs a restart). The modules still plain JS in `public/js/` are `scripts/ci/plain_js.conf`'s list, which only shrinks (`make plain-js-check`, ci-quick and pre-commit): a new module is TypeScript, and a converted one drops its line and its tracked file, moves its URLs to `pageModuleUrl` and its importmap name's `paths` to its source.

- **Service worker strategies.** public/ files are precached by content hash, one precache per static build (`closet-precache-<id>`); a `?v=X` URL is answered from X's only (`updates.md`). The tab roots opened as a document are stale-while-revalidate (below); every other navigation and every htmx request is NetworkFirst (3 s timeout; `ServerFirstPages`: an answer saying the server is unwell, `serverUnavailable` in `page-cache.ts` (429, 502, 503, 504: the database outage's busy page, #643), is taken like the timeout, the cached copy answering with its stamp, and the server's answer only without one). Both page strategies share one cache, `pages-v2` (`WARM_PAGE_CAP` + 100 entries; the offline page outside the expiration, warmed again by the first page a cache without an owner stores, since a quota error purges the cache whole: `ensureOfflinePage`, #731), and one plugin list; navigation preload is on, so a navigation's request starts while a cold worker boots and both answer or revalidate with the preload response (every GET navigation must stay routed to one of them, or the preload is wasted); fragments are keyed `url|hx` by `src/htmx/fragment-request.ts`, which the server uses for the same decision. A followed redirect is not stored under the URL that redirected. `/file/**` `<img>` loads CacheFirst (`images-v2`, `WARM_IMAGE_CAP` + 200 entries, no age limit: the URLs are immutable; a session cache, below); `/selfies/**` matches no route. Unmatched requests (other POSTs, `/health/live`) bypass the worker, and so does every request to `/mcp` and the wardrobe export, navigations included (`bypassesWorker`, `page-cache.ts`; the GET navigations deliberately left unrouted). Every whole-cache delete is the worker's `deleteCacheAndMetadata`, which also forgets Workbox's expiration rows for it (`workbox-expiration` IndexedDB: one URL each, a previous account's included); never `caches.delete` alone, and never the plugin's own `deleteCacheAndMetadata`, which knows only the caches it touched since the worker started (#731). On activate the worker deletes retired caches (`RETIRED_CACHES`: the in-browser model's, ~42 MB; `pages-v1`, unstamped; `images-v1`, outlived sessions; `assets-v1`, any build's bytes; Workbox's default precache) and every build precache but its own and the one it replaces.
- **Stale-while-revalidate tab roots** (issue #2). `/wardrobe`, `/styling`, `/outfits` and `/calendar` (`OPENS_STALE`, `page-cache.ts`: every dock tab but Today, which is network first, see Today), exactly (no query), loaded as a document (the app opening, a reload, pull to refresh) are answered from the page cache at once while the worker fetches the page again (`StaleTabRoot` in `src-sw.ts`, `servesStaleWhileRevalidate` in `src/web/page-cache.ts`); without a cached copy they are NetworkFirst; a copy stored before this worker activated (an older build's) opens NetworkFirst, never stale-first (`updates.md`). In-app taps stay NetworkFirst on purpose: they follow the user's own writes (an archive lands on `/wardrobe` through `HX-Location`), which must show at once; the cold open is where the wait was. The revalidation compares the server's body with the cached one (`revalidationOutcome`: current, updated, signed-out, account-changed, failed), so **a tab root must render byte for byte the same while nothing changes** (`delivery.spec.ts` checks it): no timestamps, nonces or random ids in those pages. There are no `updated_at` columns and none are needed: the freshness shown is the copy's age, not the data's.

- **Offline warm** (#286): `offline-warm.md` beside this file. Once a day, after a signed-in page loads, `pwa.js` asks (`WARM_PAGES`) and the worker fetches the account's whole wardrobe from `GET /offline/warm` (the session's own, never a shared one; 500 garments, 250 outfits): next week, every garment and outfit page, the grid's later pages and every thumb, never a tab root (stale-while-revalidate would open a warmed one stale after the user's own edits; cached when opened), through the session caches' own plugins, each request stamped with the run's generation, so a drop mid-warm stores nothing more; a 401 or `X-Session-Ended` on a warm's fetch drops the session. Offline, a cutout never viewed is drawn from its thumb. Every HTML answer is `Cache-Control: private, no-cache` (`send()`), and a whole page carries an `ETag` the warm sends back, so an unchanged page costs a 304 (#708): **a warmed page keeps its tag only if it never names the server's today**: the garment page's day text and Wore today's state and the outfit page's Plan day are its script's (`outbox.md`, The page's day); next week and trips still name it and download again daily. Read it before touching the warm, the list or the caches' caps.

- **Connectivity.** `connectivity.js` probes `HEAD /health/live` (checks nothing, so a down database is never shown as offline; no body: an unread GET body stays open until the 5 s abort; `no-store`, skips the session hook; a 2xx counts only with the route's `X-Closet-Live: up`, so a captive portal's own 200 on the HTTP twin is not online, `src/live-answer.ts`, #731; `src/web/health`) every 30 s while visible, on every `htmx:sendError`/`responseError`/`timeout`, and every 5 s while offline; it drives `#connectivity-banner` in `src/web/layout/app-status.tsx` and dispatches `connectivity:change` on the document (freshness.js revalidates a cached display on it). `navigator.onLine` is only a hint. Those two probes are suppressed while the page is leaving (`pagehide`/`beforeunload`, until `pageshow`) or hidden: a native form post cancels any htmx request in flight, which WebKit turns into `htmx:sendError` (#241), not evidence the server is unreachable. The heartbeat and the `visibilitychange` probe still catch a real drop.
- **Per navigation, only the body.** A boosted navigation swaps the body and nothing else should run again: `pwa.js` sits in the head; the install dialog (below) is mounted once on `<html>`, outside the swapped body (in the body every navigation re-mounted it and re-fetched `/manifest.json`); pull to refresh (iOS standalone only) is rebound when the body is swapped, not on fragment swaps. The htmx config has no view transitions (taps are dropped while one runs), no attribute settling (`attributesToSettle: []`: an element replacing one of its id is drawn in its own classes from its first frame, never the old one's for 20 ms) and keeps 3 history snapshots (`layout.tsx` has the measurements). The app bar's back arrow returns to those snapshots through history (`views/assets/page/back.ts`, which keeps its own per-entry trail in `history.state` around htmx's rewrites: `src/web/layout/AGENTS.md`). Tap feedback: the body's inherited `hx-indicator="#loading, closest a"` lights the app bar's spinner for every request and marks the tapped link `htmx-request` (`main.css` dims it and its card).
- **Install dialog** (issues #4, #48). `<pwa-install>` (`@khmyznikov/pwa-install` 0.7) costs whoever mounts it the bundle (160 KB, 45 KB compressed), `/manifest.json` once and the manifest's first icon, so `pwa.js` imports it only on a load that can offer an install: never standalone (`display-mode: standalone`, or `navigator.standalone` on iOS); in Chromium only on `beforeinstallprompt` (installable, not installed); in a browser without that event only on the platforms the element has instructions for (`manualInstallPlatform`: iPhone and iPad, Safari on macOS, Android). The element shows itself; there is no install button in the app. It shows the manifest's `icons[0]` (fetching no other), so the manifest lists the small rasters smallest first (`src/web/app-icon.ts`: `icon-192.png`, 5 KB, and `icon-512.png`, from `npm run generate:icons`); the 1000 px `ICON_NAME` (45 KB) is only for Open Graph and the watermark, and the apple-touch-icon (which Firefox also fetches on every cold load) is the 192 px one. On Chromium 155+ 0.7 installs through the Web Install API (`navigator.install()`, the manifest's `id`) and keeps the prompt event as its fallback. **No screenshots** (owner decision): the manifest has none, the element gets `disable-screenshots`, and `public/assets/screenshots/` is gone. Nothing under `public/assets/` is precached (`scripts/generate-sw.ts`): no page renders the icon (the OS reads it at install, link previews and the dialog online), and precaching it cost every fresh install 45 KB. `test/install-dialog.spec.ts (retired 2026-10-13)` proves a cold load of the installed app (Android and iPhone) fetches no icon, no dialog and the manifest at most once, desktop Firefox loads nothing, the Chrome dialog fetches the manifest exactly once (the browser's own read, which the element's `getInstalledRelatedApps()` triggers in headless Chromium, is told apart by resource type) and only the 192 px icon, and the Chrome and iPhone dialogs still work; Chromium stands in for Safari (user agent, `navigator.platform`, no `BeforeInstallPromptEvent`) and the spec dispatches the `beforeinstallprompt` headless Chromium never fires.
- **Page-only libraries** (Styling's `styling`, which imports the shared `snap-strip` through the importmap too; the garment page's `mask-editor`) load from the page that needs them, as ES modules through the importmap (`src/web/layout/import-map.ts`) so boosted navigations cannot race a global. A page-only library whose package ships no minified ESM gets an esbuild entry in `npm run generate:vendor` (which `generate:tailwind` and its watch run first, so `generate` and `start:dev` do too) that bundles and minifies it into `public/vendor/` (gitignored), which the importmap maps its name to; the package directory is not served (sortablejs went this way until Styling retired it, #91). Styling imports `styling` from an inline module (a fixed string through `dangerouslySetInnerHTML`, `src/web/styling/styling-page.tsx`) that calls `initStyling` for this visit's rows: a `<script type="module" src>` runs once per document, so it would not run again when a boosted navigation returns to the page. The module registers its delegated listeners on the document once, at evaluation; an inline module registers its own on an element of the page, never on the document, or every visit would add another. No page loads a background-removal model or WASM (`pwa.spec.ts` asserts none is ever requested, through a whole upload). The mask editor (`views/assets/page/mask-editor.ts`, bound by the garment page's inline module) listens on `#garment-photo-slot` and reads the pencil's URLs from its data attributes at the tap, because the cutout polling swaps the button; every way out of its dialog (Skip, Close, the backdrop, Escape) ends at the dialog's `close`, so the pencil is always re-enabled. The colour field's `color-picker` is a head module whose listeners are all delegated on the document (`toggle` in the capture phase), so it needs no per-swap setup. `photo-input` is no page module: the file inputs' `onchange` (`PREPARE_AND_SUBMIT_PHOTO`, `src/web/layout/parts.tsx`; the photo sheet and selfies) imports it at the pick and submits only when a file came back, so an empty pick posts nothing and no page script has to re-run after a boosted navigation.
- **Wardrobe fragment.** `GET /wardrobe` with a fragment request (`HX-Request` without `HX-Boosted`/history restore) returns `WardrobeMain` (`#wardrobe-body`) with `Vary`, the facets' content (`#wardrobe-aside`, `innerHTML`; `src/web/wardrobe/grid.md`, The facets) and the ⋯ menu out of band (`WardrobeFragment`), so its Select keeps the new filters; the scope row (capsule menu, chips, search) and the filter sheet's own GET form target `#wardrobe-body` with `hx-push-url`, so filtering never re-renders the app bar, tabs and dock. The wardrobe switcher is a plain full-page link: switching changes the title, the tabs and what may be done. The grid's later pages come from `GET /wardrobe/tiles`, always htmx requests, so the worker caches each under its own `url|hx` key; offline, the pages scrolled through or warmed (`offline-warm.md`) are what the cache has.
