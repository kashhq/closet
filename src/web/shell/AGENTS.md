# PWA and the service worker

`public/sw.js` is a build artifact. Edit `views/assets/src-sw.ts` and run `npm run generate:sw`: esbuild bundles and minifies it with `process.env.NODE_ENV` defined as `"production"`, which strips Workbox's development logging and assertions (130 KB to 30 KB), then `scripts/generate-sw.ts` injects the precache manifest and records the static id. Every `workbox-*` module the worker imports is a declared devDependency. The worker's only console output is its own `[sw]` lines. Service workers and Web Push require a secure context, which is why production is served over HTTPS (see Deployment).

Delivery model (audit fixes, see `src-sw.ts`, `public/js/pwa.js`, `public/js/connectivity.js`):

- **Static cache key.** Every first-party static URL carries `?v=<appVersion>` (the layout, the importmap, the garment page's module import). `appVersion` is `BuildInfo.assetVersion` (`src/build-info.ts`): in production the static set's content id (`staticBuildId`, the worker's precache name: `updates.md`), else the release, else the build time. `src/static-assets.ts` serves `/modules`, `/js`, `/vendor`, `/assets` and `bundle.css` as `public, max-age=31536000, immutable`, so **the key is the only thing that rolls the cache**: any changed public/ file changes it, a server-only deploy does not. `sw.js` and `manifest.json` stay `no-cache`. `NODE_ENV=development` turns the immutable policy off so `tailwind --watch` output shows on a plain reload.
- **Precompressed static files** (#116): `static-delivery.md` beside this file (one `public/` root, `.br`/`.gz` from the build, never served stale). Read it before touching `src/static-assets.ts` or the build's generate steps.
- **Service worker strategies.** public/ files are precached by content hash, one precache per static build (`closet-precache-<id>`); a `?v=X` URL is answered from X's only (`updates.md`). The tab roots opened as a document are stale-while-revalidate (below); every other navigation and every htmx request is NetworkFirst (3 s timeout; `ServerFirstPages`: an answer saying the server is unwell, `serverUnavailable` in `page-cache.ts` (429, 502, 503, 504: the database outage's busy page, #643), is taken like the timeout, the cached copy answering with its stamp, and the server's answer only without one). Both page strategies share one cache, `pages-v2` (`WARM_PAGE_CAP` + 100 entries; the offline page outside the expiration), and one plugin list; navigation preload is on, so a navigation's request starts while a cold worker boots and both answer or revalidate with the preload response (every GET navigation must stay routed to one of them, or the preload is wasted); fragments are keyed `url|hx` by `src/htmx/fragment-request.ts`, which the server uses for the same decision. A followed redirect is not stored under the URL that redirected. `/file/**` `<img>` loads CacheFirst (`images-v2`, `WARM_IMAGE_CAP` + 200 entries, no age limit: the URLs are immutable; a session cache, below); `/selfies/**` matches no route. Unmatched requests (other POSTs, `/health/live`) bypass the worker, and so does every request to `/mcp` and the wardrobe export, navigations included (`bypassesWorker`, `page-cache.ts`; the GET navigations deliberately left unrouted). On activate the worker deletes retired caches (`RETIRED_CACHES`: the in-browser model's, ~42 MB; `pages-v1`, unstamped; `images-v1`, outlived sessions; `assets-v1`, any build's bytes; Workbox's default precache) and every build precache but its own and the one it replaces.
- **Stale-while-revalidate tab roots** (issue #2). `/wardrobe`, `/styling`, `/outfits` and `/calendar` (`OPENS_STALE`, `page-cache.ts`: every dock tab but Today, which is network first, see Today), exactly (no query), loaded as a document (the app opening, a reload, pull to refresh) are answered from the page cache at once while the worker fetches the page again (`StaleTabRoot` in `src-sw.ts`, `servesStaleWhileRevalidate` in `src/web/page-cache.ts`); without a cached copy they are NetworkFirst; a copy stored before this worker activated (an older build's) opens NetworkFirst, never stale-first (`updates.md`). In-app taps stay NetworkFirst on purpose: they follow the user's own writes (an archive lands on `/wardrobe` through `HX-Location`), which must show at once; the cold open is where the wait was. The revalidation compares the server's body with the cached one (`revalidationOutcome`: current, updated, signed-out, account-changed, failed), so **a tab root must render byte for byte the same while nothing changes** (`delivery.spec.ts` checks it): no timestamps, nonces or random ids in those pages. There are no `updated_at` columns and none are needed: the freshness shown is the copy's age, not the data's.
- **Freshness stamp and indicator** (#240): `freshness.md` beside this file. Every stored copy carries a cache-arrival stamp (`X-SW-Cached-At`, a `Server-Timing` entry); `public/js/freshness.js` shows it as "Updated N minutes ago" and asks the worker to revalidate (`REVALIDATE_PAGE`), swapping in a newer page only when the page is untouched. Read it before touching the stamp, revalidation, or a worker message that expects state to survive past a fetch event (WebKit gotcha).
- **Session caches** (#121, #131, #226): `session-caches.md` beside this file. `pages-v2` and `images-v2` hold one account's pages and photos and are dropped together (`dropSession`, `SESSION_CACHES`) as an auth form posts (`SESSION_ENDING`), on a page for another account (`claimPageCache`), a tab root revalidated signed out or for another account, and a followed redirect to the login page (`sentToLogin`); a page or photo requested before a drop is never stored after it (generations). Selfies are never the worker's; only a 200 HTML answer is a page or names an account (`renderedAccount`: the 503 busy page renders signed out, #643). Read it before touching what the worker stores for an account or how it learns the account changed.
- **Queued writes** (#178): `outbox.md` beside this file. Wears, washes and packing ticks tapped offline go to the page's IndexedDB outbox (`views/assets/outbox.ts`, bundled to `public/js/outbox.js`) and replay on reconnect; the worker sends nothing, deletes the store at session boundaries, refetches the cached pages a sync changed (`OUTBOX_SYNCED`) and posts the open tabs the changed copies (`PAGES_RENEWED`, swapped in by `freshness.js`: a renewed copy leaves `REVALIDATE_PAGE` nothing new to find). Read it before touching a queueable control, `#app-status`'s account, or a page that draws a queued write's state.
- **Offline warm** (#286): `offline-warm.md` beside this file. Once a day, after a signed-in page loads, `pwa.js` asks (`WARM_PAGES`) and the worker fetches the account's whole wardrobe from `GET /offline/warm` (the session's own, never a shared one; 500 garments, 250 outfits): next week, every garment and outfit page, the grid's later pages and every thumb, never a tab root (stale-while-revalidate would open a warmed one stale after the user's own edits; cached when opened), through the session caches' own plugins, each request stamped with the run's generation, so a drop mid-warm stores nothing more; a 401 or `X-Session-Ended` on a warm's fetch drops the session. Offline, a cutout never viewed is drawn from its thumb. Every HTML answer is `Cache-Control: private, no-cache` (`send()`), and a whole page carries an `ETag` the warm sends back, so an unchanged page costs a 304 (#708): **a warmed page keeps its tag only if it never names the server's today**: the garment page's day text and Wore today's state are its script's (`outbox.md`, The page's day); outfit pages, next week, the laundry and trips still name it and download again daily. Read it before touching the warm, the list or the caches' caps.
- **Updates** (`updates.md` beside this file: read it before touching activation, the refresh or the per-build static cache). The worker does not `skipWaiting()` on install. `pwa.js` shows an "Update available: Reload" toast on `waiting` (Reload disabled, saying why, while `data-connectivity` is not online), posts `SKIP_WAITING` on tap, and reloads on `controlling`. Never force a reload or defer activation (why: `updates.md`). The older build's pages stay, served offline with their build's scripts (each install keeps its build's whole static set; an incomplete build's copies go on read), until `WARM_PAGES` refetches them (#656); a 401 still drops the session caches, on purpose. Another window keeps its page and toast (#180, `updates.md`).
- **Connectivity.** `connectivity.js` probes `HEAD /health/live` (checks nothing, so a down database is never shown as offline; no body: an unread GET body stays open until the 5 s abort; `no-store`, skips the session hook; any 2xx counts; `src/web/health`) every 30 s while visible, on every `htmx:sendError`/`responseError`/`timeout`, and every 5 s while offline; it drives `#connectivity-banner` in `src/web/layout/app-status.tsx` and dispatches `connectivity:change` on the document (freshness.js revalidates a cached display on it). `navigator.onLine` is only a hint. Those two probes are suppressed while the page is leaving (`pagehide`/`beforeunload`, until `pageshow`) or hidden: a native form post cancels any htmx request in flight, which WebKit turns into `htmx:sendError` (#241), not evidence the server is unreachable. The heartbeat and the `visibilitychange` probe still catch a real drop.
- **Per navigation, only the body.** A boosted navigation swaps the body and nothing else should run again: `pwa.js` sits in the head; the install dialog (below) is mounted once on `<html>`, outside the swapped body (in the body every navigation re-mounted it and re-fetched `/manifest.json`); pull to refresh (iOS standalone only) is rebound when the body is swapped, not on fragment swaps. The htmx config has no view transitions (taps are dropped while one runs) and keeps 3 history snapshots (`layout.tsx` has the measurements). The app bar's back arrow returns to those snapshots through history (`public/js/back.js`, which keeps its own per-entry trail in `history.state` around htmx's rewrites: `src/web/layout/AGENTS.md`). Tap feedback: the body's inherited `hx-indicator="#loading, closest a"` lights the app bar's spinner for every request and marks the tapped link `htmx-request` (`main.css` dims it and its card).
- **Install dialog** (issues #4, #48). `<pwa-install>` (`@khmyznikov/pwa-install` 0.7) costs whoever mounts it the bundle (160 KB, 45 KB compressed), `/manifest.json` once and the manifest's first icon, so `pwa.js` imports it only on a load that can offer an install: never standalone (`display-mode: standalone`, or `navigator.standalone` on iOS); in Chromium only on `beforeinstallprompt` (installable, not installed); in a browser without that event only on the platforms the element has instructions for (`manualInstallPlatform`: iPhone and iPad, Safari on macOS, Android). The element shows itself; there is no install button in the app. It shows the manifest's `icons[0]` (fetching no other), so the manifest lists the small rasters smallest first (`src/web/app-icon.ts`: `icon-192.png`, 5 KB, and `icon-512.png`, from `npm run generate:icons`); the 1000 px `ICON_NAME` (45 KB) is only for Open Graph and the watermark, and the apple-touch-icon (which Firefox also fetches on every cold load) is the 192 px one. On Chromium 155+ 0.7 installs through the Web Install API (`navigator.install()`, the manifest's `id`) and keeps the prompt event as its fallback. **No screenshots** (owner decision): the manifest has none, the element gets `disable-screenshots`, and `public/assets/screenshots/` is gone. Nothing under `public/assets/` is precached (`scripts/generate-sw.ts`): no page renders the icon (the OS reads it at install, link previews and the dialog online), and precaching it cost every fresh install 45 KB. `test/install-dialog.spec.ts (retired 2026-10-13)` proves a cold load of the installed app (Android and iPhone) fetches no icon, no dialog and the manifest at most once, desktop Firefox loads nothing, the Chrome dialog fetches the manifest exactly once (the browser's own read, which the element's `getInstalledRelatedApps()` triggers in headless Chromium, is told apart by resource type) and only the 192 px icon, and the Chrome and iPhone dialogs still work; Chromium stands in for Safari (user agent, `navigator.platform`, no `BeforeInstallPromptEvent`) and the spec dispatches the `beforeinstallprompt` headless Chromium never fires.
- **Page-only libraries** (Styling's `styling`, which imports the shared `snap-strip` through the importmap too; the garment page's `mask-editor`) load from the page that needs them, as ES modules through the importmap (`src/web/layout/layout.tsx`) so boosted navigations cannot race a global. A page-only library whose package ships no minified ESM gets an esbuild entry in `npm run generate:vendor` (which `generate:tailwind` and its watch run first, so `generate` and `start:dev` do too) that bundles and minifies it into `public/vendor/` (gitignored), which the importmap maps its name to; the package directory is not served (sortablejs went this way until Styling retired it, #91). Styling imports `styling` from an inline module (a fixed string through `dangerouslySetInnerHTML`, `src/web/styling/styling-page.tsx`) that calls `initStyling` for this visit's rows: a `<script type="module" src>` runs once per document, so it would not run again when a boosted navigation returns to the page. The module registers its delegated listeners on the document once, at evaluation; an inline module registers its own on an element of the page, never on the document, or every visit would add another. No page loads a background-removal model or WASM (`pwa.spec.ts` asserts none is ever requested, through a whole upload). The mask editor's pencil is wired by a listener delegated on `#garment-photo-slot` that reads its URLs from the button's data attributes at the tap, because the cutout polling swaps the button. `photo-input` is no page module: the file inputs' `onchange` (`PREPARE_AND_SUBMIT_PHOTO`, `src/web/layout/parts.tsx`; the photo sheet and selfies) imports it at the pick and submits only when a file came back, so an empty pick posts nothing and no page script has to re-run after a boosted navigation.
- **Wardrobe fragment.** `GET /wardrobe` with a fragment request (`HX-Request` without `HX-Boosted`/history restore) returns `WardrobeMain` (`#wardrobe-main`) with `Vary`, and the ⋯ menu out of band (`WardrobeFragment`), so its Select keeps the new filters; the scope row (capsule menu, chips, search) and the filter modal's own GET form target `#wardrobe-main` with `hx-push-url`, so filtering never re-renders the app bar, tabs and dock. The wardrobe switcher is a plain full-page link: switching changes the title, the tabs and what may be done. The grid's later pages come from `GET /wardrobe/tiles`, always htmx requests, so the worker caches each under its own `url|hx` key; offline, the pages scrolled through or warmed (`offline-warm.md`) are what the cache has.

## Gotchas

- **The worker never sends a navigation post to the server** (#542): it cannot tell ours from a cross-site one, and its fetch would carry our Origin and cookie past the CSRF check. A listener above every route stops each (`navigationPostAnswer`, unit-tested) and answers only the share target, on the device (`receiveShare`: a stash in `shares-v1`, a session cache, a 303, no fetch). What it must learn of a post, our page messages it as it leaves (`SESSION_ENDING`; `session-caches.md`).
- **WebKit never settles a fetch whose opaque redirect carries `Clear-Site-Data`** (#239): the worker must not `fetch()` a navigation's own request (redirect mode `manual`) where that can be the answer. GET navigations use the navigation preload, which is unaffected.

- **Chromium hides `Clear-Site-Data` from the response it applies**, the worker's own `fetch` included, so the worker cannot read it: `endSession` also sends `X-Session-Ended` (`SESSION_ENDED_HEADER`, `page-cache.ts`), which it reads (#131).

- **Playwright's `context.setOffline` does not cut the worker's own fetches** (Chromium): the page's requests and the navigation preload fail, but NetworkFirst for an htmx request, a `REVALIDATE_PAGE` or an image the worker fetches still reaches the server. `networkSwitch` (`test/support/service-worker.ts`) also fails them through `context.route`, which does see a worker's requests (and turns the HTTP cache off).

- **`@fastify/static` 10 applies `setHeaders` after `send`'s own Cache-Control**, passing the `FastifyReply` (`reply.header()`), which is what makes the per-file policy in `registerStaticAssets` (`src/static-assets.ts`) work; before 10 it was the raw response and `send` overwrote it. Its `path` is `sw.js.br` for a precompressed worker: `staticCacheControl` judges the source, or the worker would be cached for a year. `test/integration/delivery.spec.ts` asserts the headers.
