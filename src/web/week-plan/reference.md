# Weekly auto-plan: reference

Moved out of `AGENTS.md` (#723) so the auto-loaded doc keeps only invariants, gotchas and ownership. Not auto-loaded: read it before changing this area. Where it disagrees with the code or a spec, they win.

- **The planner** (`planWeek`, pure, `week-planner.spec.ts`): the template's slots of the days asked (today and the six after it), in day and occasion order; a slot is **empty** when no entry has its occasion that day, and a day occasion's slot when no day occasion is planned (one outfit dresses the day); today's slots whose window (`OCCASION_HINTS`) has ended are left. Each slot's idea is `generateIdeas` over the planner's pool with that slot's `weatherNeeds` (the occasion's window of that day's forecast, the personal offset) and the occasion's demands (`occasionDemands`), seeded by (day, occasion) (`slotSeed`, `PLANNER_VERSION`); the best idea is taken, a near miss included (its problems are reported); a slot with none stays empty (`unfilled`), as a workout does without clean activewear (#647: never a near miss; the banner says why, `data-needs-activewear`: `no-activewear` when the closet has none of the kinds, else `none-available` (it reads the calendar and the closet's kinds, `closetKindsSql`, not the plan's reasons)). **Wash limits across the week**: the pool is every closet garment not away, dirty ones too (`weekPoolSql`, beside `ideaPoolSql`), with its wash state today; the unworn entries in the window and every outfit planned so far add their wear **days**, and a garment is offered only while `cleanCopies` stays above zero after all of them, so a planned wear never dirties a copy a later planned day relies on (a garment already worn that day costs nothing more). Nothing is washed in between. **No outfit twice**: each planned outfit joins the saved outfits the generator never repeats. Rotation: a garment the week already wears counts as just worn for later slots.

- **Writes** (`plan.ts`, `planMyWeek`): the forecast is read first (`weekForecast`, outside any lock), then one transaction under `lockOwner`: the template, the window's entries (`windowEntriesSql`) and its trips (one statement, #684), the pool, saved outfits and avoided pairs are read **after** the lock, so a double tap or a retried `plan_week` waits and finds its slots filled (`/calendar?planned=none`); with no empty slot (`emptySlots`, the slots `planWeek` fills) it stops before the pool and the memory (#165, #684: 5 statements with the session). Each outfit goes through **`pickIdea`** (the gallery's pick: reused or created and named `ideaName`) with `plannedBy: 'auto'`, its entry recorded in the batch. Tables: `week_plan` (the batch: one tap, for the banner and Undo) and `week_plan_entry` (entry, batch, whether the planner created the outfit, and the targets it was planned for: `torso`, `limbs`, `layer`, `rain`, all null without a forecast, and `limbs_ceiling`, null also for entries from before 0054).

- **Undo** (`undoWeekPlan`, under `lockOwner`): the batch's entries still `auto` are deleted with each outfit the planner created for them that nothing holds any more (`removeBatchAutoEntries`, one `DELETE ... USING` scoped to the owner's batch, then `removeUnheldOutfits`: no calendar entry and no trip, `outfitIsHeld`); entries taken over since stay; the batch goes once empty. Whose batch it is is asked only when the delete found nothing (another's, whatever share, is `NotFound('weekPlan')` from `undoWeekPlan(db, actor, id)` itself, #188d; an own one fully taken over `undone=0`). **`removeUnheldOutfits` is two statements whatever the count** (#165; Undo, the swap, Change and the calendar's x, `deleteEntry`, #659, #748, share it; it deletes only origin `idea`/`planner` outfits, so a `person` or `agent` one is safe whatever the caller passes): the outfits locked, then one delete of the unheld ones, not `deleteOutfit` per outfit (4 each): an unheld outfit has no entry, wear, selfie or trip for its rules to keep. Never fold the two into one: a delete waiting on the row lock judges `outfitIsHeld` by its own older snapshot. Undo is 8 statements (`week-plan.spec.ts`).
- **The daily re-plan** (`replan.ts`): `replanToday(deps, userId, now)` is one user's re-plan for the day, **once, whoever asks**: the minutely run (`replanWeeks(deps, now)`, every user `replanCandidates` lists: an auto entry recorded in a batch from today on and no claim today) and **the morning reminder, which re-plans its person first** (#76, see Web Push). Scheduled by `server.ts` only (every minute through `scheduleMinutely`, with or without `WEATHER_ENABLED`: without a forecast it still judges availability; claims pruned nightly), never by `createApp()`, so the harness and the CLIs never re-plan (a spec calls it with the instant it wants). The run does nothing before **`REPLAN_HOUR`, derived from `REMINDER_WINDOWS.morning.from`** (05:00 on the household's wall clock, `hourIn`): everyone is re-planned by the earliest time a reminder can be set to, and a swap notice comes before a reminder; the reminder does not depend on it. **The claim commits with the work**: per user one transaction under `lockOwner` that reads the auto entries and claims the day in one statement (`claimAutoEntries`: a data-modifying CTE inserting into `week_replan (user_id, day)`, `ON CONFLICT DO NOTHING`, only when an auto entry exists, so a week planned later today is judged by a later run), judges and writes. A second caller (the next minute, the reminder, a second server in an overlapping deploy) waits on the owner lock and finds the day claimed and the re-plan committed, never half done, which is what lets a reminder read the day after it. A re-plan that throws is logged and its day left unclaimed (the claim rolled back with the work); **`ReplanRetries`** (in process, held by `server.ts`'s one `ReplanDeps`, so the minutely run and the morning reminder share it; no table, a restart only retries sooner) retries that person after 5, 15 and 60 minutes, and the fourth failure claims the day (`claimAfterFailure`), so a persistent failure is four attempts a day, not one a minute. Each job counts only its own first failure of the person-day into its `run.failed` (`job`: `replan` or `reminders`; the reminder's must not use up the minutely run's, #858), so each scheduled run ends with one `PartialFailure` per person-day after re-planning the others (`replanWeeksWhole`, #687: one `failure` metric and one capture). Without `retries` (specs) a failure claims the day at once. **A forecast fetch that fails with nothing cached is no forecast, not a failure** (`userWeatherOrNone`: the re-plan judges availability, the reminder drops its weather line); one that timed out waiting on the owner lock (`OwnerLockTimeout`, see Calendar) judged nothing and is logged `deferred`, the day left unclaimed for the next minute and not a failure; the swap notice goes after the commit (a crash between loses the notice, never doubles it). The judgement (`replanWeek`, pure): **an outfit that can no longer be worn** (`unwearableOn`, `isAvailable` on the planned day's terms: a garment archived or a wishlist item, lent or at repair, deleted since (an empty slot, only telling in an outfit the planner created: every slot had a garment; a reused saved outfit may have one empty on purpose), or, **on today only**, without a clean copy and not worn today) is swapped for the slot's best idea under the planner's rules, whatever the forecast, and kept (logged) when nothing else dresses the slot. Dirty counts only on the day itself because today's wash state is a fact and a later day's a projection the next load of laundry changes; the run is daily, so a garment still dirty on its day is caught that morning, before the person dresses (the planner's own "nothing is washed in between" is right for filling a week and too eager for undoing one). Otherwise the weather: an entry whose targets (torso, limbs, layer, rain) did not change, **and whose legs and feet did not turn too warm** (the stored `limbs` is capped on the cold side and cannot show `limbsCeiling`, the uncapped too-warm bound, so `week_plan_entry.limbs_ceiling` keeps it: warmth-5 boots planned for the cold; judged only when `assessOutfit` finds legs or feet too warm now and the ceiling is lower than the one it was planned with, so a near miss the planner chose knowingly is not re-judged in unchanged weather, and an entry with a null ceiling, planned before 0054, never is; a fallen ceiling is the one cause, so such a swap says "warmer"; a kept entry records the new ceiling), or whose day has no forecast is kept; with changed targets an outfit that still fits them is kept (recording the new targets), else the slot is planned again and **swapped only for an idea that answers the weather better** (the old entry and its planner-made outfit removed, the new one in the same batch). What swapped is **pushed** to the person's devices **with the morning reminder on**, one line per swap saying why ("Thursday turned cold: swapped in Wool coat", "Bean Boots is at repair: swapped in Chelsea boots on Thursday", "A garment of Friday's outfit was deleted: swapped in ..."; title "Your week changed", opens `/calendar`, tag `week-replan`, TTL 6 h): the notice is about what to wear, the reminder's subject, so no new setting; without `PWA_ENABLED` swaps happen and nobody is told. **One push per swap, never two**: when the morning reminder runs the re-plan (`replanToday(..., { announcesToday: true })`), today's swaps are said in the reminder itself and left out of the notice, which then goes only for other days' swaps (if any); the minutely run announces everything, today included. `replanToday` returns every swap it made either way. `outfitGarmentStatesSql` (`queries.ts`) reads the auto entries' outfits' slots with each garment's status, away, wash state (`wearsSinceWashSql`) and whether it was worn today. **The minutely run's statements** (#165, #173: 2 + 5 per due user, 7 for one; `week-plan.spec.ts`, `job-statements.spec.ts`): the candidates, every candidate's weather in one statement (`refreshForecastsFor` answers it, so `replanUser` does not read it again), then per user the transaction: begin, the owner lock, `claimAutoEntries` (each entry marked `away` by `awayOnSql`), then the window, the pool, the memory and the kept entries' outfits' garments in one `selectScalars` (`weekSql` + `outfitGarmentStatesSql`, each a scalar subquery: `windowEntriesSql`, `weekPoolSql`, `generatorMemorySql`), read after the removal from days away so a removed entry's wears count toward no wash limit (#862), commit (that removal adds its own statements); swap notices go last, in one `sendEach` for the run. A listed user is not asked `replanCandidates` again; the morning reminders ask it once for all their people and pass their batch's weather (`replanToday`'s `listed`, `weather`). "Plan my week" reads its pool and memory in one statement too.
