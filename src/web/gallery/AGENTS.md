# Outfit gallery

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds The generator; generator_avoid; The page; Entry points.

`src/wardrobe/generator.ts` (pure) and `src/web/gallery/`. The model: **the gallery chooses whole outfits** (the Outfits page's Ideas and Saved tabs); composing row by row is Styling; **the generator is the one source of suggestions**, reached only through `ideasFor` (`ideas.ts`): the Ideas tab, `suggest_outfits`, Today (today's all-day ideas, 3 a page, through `todayIdeas`) and Styling's Shuffle (its locked rows as `IdeasInput.locked`, read by `styledGarmentsSql` in the same statement through `ideasColumns` and `ideasFrom`); and its siblings `goesWithCloset` (see Wishlist: the whole closet with a wishlist item locked) and `browseIdea` (Shuffle over a shared wardrobe, see Styling). A pick goes where its destination says through `pickTo` (`pick.ts`; Styling's Save calls `pickToPath`, the same without the reply) and a `?for=` is aimed through `aimIdeas` (`aim.ts`, shared with Shuffle). Private like outfits: the signed-in user's garments, capsules and outfits; `?ownerId=` is not read. Tab labels: `gallery.TAB_*`; Ideas lives inside the Outfits page (`outfit-tabs.tsx`: static without a destination, so `/outfits` stays byte-stable for the service worker; a day's `?for=` travels between the tabs).

- **Seeded and paged, never materialized**: the draws are `seededRandom('generator', GENERATOR_VERSION, seed)`; a page asks for `offset + limit + 1` fitting ideas and stops drawing once it has them, else spends all `MAX_DRAWS` (2000) and appends the sorted near misses. **It stops sooner only where the page cannot change**: once `want` ideas score the floor (`scoreFloor`: the locks' formality misses plus each open role's smallest, since misses only add up and the weather's part is never negative; 0 when a fit is possible); no later draw scores lower, and a tie ranks after. It also stops when the locks break a colour, pattern or clash rule (no idea: those rules only worsen as garments are added, `HardRules.compatible`) and once every distinct base has been drawn (`baseCount`). A gallery page past what fits still spends 2000, since the weather part has no floor. Within a draw, a base breaking a hard rule on its own is never scored, each kind of layer is scored once (`layerKinds`; `assessOutfit` is most of a draw's cost) and the rotation order is drawn only until a passing layer of the lowest score turns up (#996), and rotation weights are computed once a request. `generator-output.spec.ts` pins the exact output (ideas, order, scores, `more`) of seeded closets: a speed-up that changes it is not one. The fitting list is prefix-stable: page 1 never changes when page 3 is read; the same (pool, seed, page) is the same page. A base is judged deterministically (layer included): one idea however often drawn. The day's seed (`dailySeed(today)`) opens the gallery; Shuffle is `shuffledSeed(seed)` (no `Math.random` or `Date.now` anywhere in the data path).
- **A pick is one transaction, and happens once**: `pickIdea` (`src/web/outfits/pick.ts`, a Queryable; the outfit write is Outfits', so `ideas.ts` stays read-only and imports neither `ownerTransaction` nor the calendar) runs in `ownerTransaction` (Calendar's owner lock), checks every garment is the owner's and in the closet (else refused whole, nothing written, the garments named by the route: `garmentsGoneError`, a 409 for an archived or wishlist one, a 404 for one not theirs; see Outfits) and **keeps them locked `FOR SHARE`, in id order, until the outfit is saved** (`pickedGarments`): an archive or delete waits for the pick, or the pick waits and leaves the garment out, so no pick saves an archived garment or an emptied slot; in the same statement it looks for an outfit of the owner's with exactly these garments (`sameGarmentsOutfit` from `src/web/outfits/queries.ts`, empty slots aside). **One exists** (a double tap, a retried `pick_outfit`): it is the answer, `alreadySaved`, planned on the destination's day through `insertEntry`, and nothing is created; a person's pick (not the planner's `plannedBy: 'auto'`) of an outfit "Plan my week" created **takes it over** (`reuseOutfit`'s `adoptOutfit`, `src/web/week-plan/adopt.ts`: its `week_plan_entry.outfit_created` rows cleared in the pick's transaction), so "Already saved" stays true through Undo and the re-plan (`PickResult.adopted`, logged "taken over from the week planner"); the redirect carries `?alreadySaved=1`, which the outfit page and the week show as "Already saved" (`AlreadySavedToast`, stripped from the address). **None**: the slots top to toe (`OUTFIT_ORDER` by role), the name (`ideaName`: the garments' names or categories, top to toe, within `OUTFIT_NAME_MAX`) and `createOutfit`, which joins the pick's owner transaction and writes the outfit (checking once more, in its insert, for one of these garments, see Outfits), its slots and the calendar entry. `gallery.spec.ts` fails the entry's insert (no outfit or slot left), picks twice, and holds one pick open while a second waits (one outfit, one entry).
- **URL state or data, said at the route**: `?for=` / `?occasion=` are navigation state (`parseDestination`: none is today, all day) and `?seed=` / `?page=` fall back (past `MAX_IDEAS_PAGE` too; `ideasPage` answers `more: false` on that page, so no sentinel asks past it); `?capsule=` / `?with=` name data (not an id: 400; not the user's own: 404), and so does a write's `for` (malformed is a 400: it must read back as posted, `destinationTarget`). The route validates them before `ideasFor`, never inside it: its input is Today's and MCP's too.

## Gotchas

- **Suggestions come from the generator, through `ideasFor`, and its randomness is seeded.** A new surface that suggests outfits calls `ideasFor` (or `generateIdeas` with a pool from `ideaPoolSql`; "Goes with my closet" is one other pool, `closetGarmentsSql`, with its item only ever `locked`, and the week planner the other, `weekPoolSql`: dirty garments included, judged per day by `cleanCopies` with the week's own wears), never a query of its own, or the availability, colour, clash and duplicate rules fork. Nothing in its data path may use `Math.random` or the clock: a gallery page is a function of (pool as a set, seed, page), and the sentinel's page 2 must continue page 1. Postgres never promises row order without ORDER BY, so `generateIdeas` orders each role by id before it draws by position; a new seeded path that draws by position does the same. Bump `GENERATOR_VERSION` to reshuffle every seed on purpose.
- **A sentinel inside a scroll container triggers on `intersect`, and a delete swap needs a 200.** htmx's `revealed` listens to the window's scroll, so a sentinel at the end of a horizontal strip never fires with it; `intersect` uses an IntersectionObserver, which sees the container's clipping. htmx swaps nothing on a 204, so a write whose answer removes its element (`hx-swap="delete"`, "Clashes") answers 200 with an empty body.
