# Calendar

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds Changing an entry's outfit; The page; The desktop week grid; The plan page; OutfitDestination; Tabs; Selfies.

`src/web/calendar/`. A calendar day is a plain date: `outfit_calendar.day` is a Postgres `date`, a `'YYYY-MM-DD'` string everywhere in TypeScript, and all arithmetic is on day numbers in `src/calendar-date.ts` (pure, shared by the pure layers, so it lives beside `random.ts`). No JS `Date` represents a calendar day (DST mislabels days). The one conversion from an instant is `todayIn(APP_TIMEZONE, now)`: "today" is the household's date in `APP_TIMEZONE` (IANA name, default `America/New_York`, checked at boot), never UTC or the container's zone. Weeks run Sunday to Saturday.

- **Scheduling is idempotent**: `UNIQUE (owner_id, day, outfit_id)`, and the one writer, `insertEntry` (`src/web/calendar/queries.ts`, taking a `Queryable`), inserts with `ON CONFLICT DO UPDATE ... WHERE`: **a person's write (`planned_by` `user`, the default) that meets the week planner's `auto` entry of that outfit on that day takes it over** (`planned_by` becomes `user`, nothing else; the answer is `already-scheduled` with `adopted`, told from an insert by `xmax = 0` in `RETURNING`), and the planner's `auto` write never downgrades a person's entry. The unique index leads with `(owner_id, day)`, so it also serves the week query and the owner foreign key.
- **Owner lock**: **every write to `outfit_calendar`, the week planner's tables (`week_plan`, `week_plan_entry`, `week_replan`) and Muse's needs and suggestions (`option_group`, a suggestion's columns) runs in `ownerTransaction`** (`src/web/auth/queries.ts`: a transaction (a savepoint in a caller's) whose first statement is `lockOwner`, the owner's `user` row `FOR NO KEY UPDATE` plus the lock timeout; **nested in an `ownerTransaction` of the same owner it joins it**: no savepoint, no second lock, so a nested writer's failure is its caller's). The writers take it themselves: `insertEntry`, `scheduleOutfit`, `wearOutfitOn`, `setEntryWorn`, `setEntrySelfie`, `deleteEntry`, `replaceEntryOutfit`, `createOutfit` (always), `updateOutfit`, `deleteOutfit`, `pickIdea`, `planMyWeek`, `undoWeekPlan`, the re-plan (and its claim after a failure), `decide`, `markSuggestion`, `createOptionGroup`, `buyWishlistItem`, and the repair log's `addRepair` and `deleteRepair` (`src/web/wardrobe/repairs.ts`, for the bounded waits); the helpers below them (`setEntryOutfit`, `removeAutoEntries`, `recordAutoEntry`, ...) are called only inside one. **Why a lock, not conflict-safe statements**: the re-plan, Undo and a replace read several rows, judge, then write; `ON CONFLICT` makes one statement safe but cannot keep a judgement true. **Order**: the owner lock before any row lock of the transaction (an entry, an outfit, a garment, a trip), because the re-plan and Undo lock outfits under it: `updateOutfit` and `deleteOutfit` take it before the outfit, `buyWishlistItem` before the garment. **Every write to a synced table takes it first (#196a)**, in `ownerTransaction` or folded into its first statement; how, and the test-only guard that holds it: `src/db/AGENTS.md`, The owner lock's statement. A new writer uses `ownerTransaction(db, ownerId, '<its name>', work)`; `test/integration/owner-lock.spec.ts` holds one writer open while the other waits. **Exempt, because they judge nothing**: `pruneReplanClaims` (nightly; no writer reads old `week_replan` rows). **Bounded waits**: every form of the owner lock (`lockOwner` and the folded ones) sets `lock_timeout` to `OWNER_LOCK_TIMEOUT_MS` (5 s, `SET LOCAL`, so nested it lasts to the caller's commit); past it the writer throws `OwnerLockTimeout` (`src/web/errors.tsx`), a 503 "still saving, try again" page; the re-plan defers to the next minute instead. The pool's `statement_timeout` and `idle_in_transaction_session_timeout` (`src/db/AGENTS.md`) end a stalled holder. A missing owner row is a 404, not an unlocked write. **A savepoint that took the lock first and rolled back releases it**: a caller that catches a nested `ownerTransaction`'s failure and carries on is unlocked from there (none does; take `lockOwner` first if one must).
- **Occasions**: `outfit_calendar.occasion` (text, default and check constraint from `src/wardrobe/occasions.ts`) is the part of the day an entry is for: `all-day`, `workout`, `work`, `daytime`, `evening`, `night-out`, in that display order. `OCCASION_HINTS` gives each a weather window (hours in `APP_TIMEZONE`, e.g. work 8 to 18) and a formality range on the garment scale (work 3 to 4, workout 1): the one source for the weather and the generator. **Several outfits a day are separate entries; the same outfit is on a day once**, whatever the occasion: planning it again for another occasion inserts nothing and keeps the first occasion (so a form re-saved at the default never moves an evening entry to all day). No "change an entry's occasion" write yet: delete and plan again.
- **Worn** is `setEntryWorn` (`src/web/wears/queries.ts`): `worn_at` and the wear rows change together. Days after today have no pill and are refused. `/worn` is queueable: a replay is a 204 (Wears' Queued writes), and the pill queues offline (`src/web/shell/outbox.md`). **"Wearing this"** for a whole outfit off the calendar is `wearOutfitOn` (`queries.ts`): planned and locked in one statement (`planToWear`), then `changeEntryWorn`; idempotent.
- **Every surface reaches an entry only through `entry-actions.ts`** (#188d: `planOutfit`, `markEntryWorn`, `requireEntry`, `removeEntry`, and `replaceEntryOutfit`), the pages, MCP and `/api/v1/calendar-entries` alike: each takes the `Actor` and throws `NotFound('calendarEntry')` / `NotFound('outfit')`, never a 403, because a share never reaches an entry (`entry-actions.spec.ts`). `?week=` is navigation state (missing or malformed is the current week, never a 400); a post's `returnTo` goes through `safeReturnTo`.

## Gotchas

- **The week opens at the top; nothing scrolls it to today** (#1087): no `:target` on `/calendar?week=`, no `scrollIntoView`, no htmx `show:`. A day is reached by its `#day-D` link only. Its late layout is the weather line (a 20 px slot the summary replaces, about 52 px), which Chromium's scroll anchoring absorbs once scrolled. A spec that shoots a sheet over the week settles first and scrolls the opener itself (`openTuesdayPlanSheet`, `screenshots.spec.ts`, which also takes the shot twice and requires a match).
- **The calendar's unit specs (`src/web/calendar/*.spec.ts`) run in America/New_York through their own project**, `unit-new-york` in `vitest.config.mts` (`env: { TZ }`, `pool: 'forks'`), to prove the date logic ignores the process's zone. Node reloads the zone on Vitest's `process.env` assignment only in a child process, so the project must stay on forks. Each spec first asserts the offset. Another zoned spec gets its own project likewise (named `unit*` to stay under `npm test`).
- **`src/calendar-date.ts` keeps one `Intl.DateTimeFormat` per zone and shape** (`perZone`: `todayIn`, `hourIn`, `instantAt`'s offset). Building one is the cost (2.2% of server CPU per call); formatters are stateless. A new zone-aware helper takes a `perZone` formatter.
- **Moved rules** (detail in `reference.md`): `replaceEntryOutfit` is the one replace write: a worn entry is refused (409), as is an outfit already on that day; the planner's outfit it replaced goes only once unheld and only while the entry was `auto`. `OccasionRow` is the one way the week draws an entry; never put `data-occasion` on a wrapper (the worn swap retargets `closest [data-occasion]`). Undo of a delete posts only its random token. `OutfitDestination` is the one parser of `?for=`: a feature spelling `day:`/`trip:` itself is a regression.
