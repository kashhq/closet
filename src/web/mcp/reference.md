# MCP server: reference

Moved out of `AGENTS.md` (#723) so the auto-loaded doc keeps only invariants, gotchas and ownership. Not auto-loaded: read it before changing this area. Where it disagrees with the code or a spec, they win.

- **Auth: personal access tokens of kind `mcp`** (`src/web/auth/personal-tokens.ts`, table `personal_access_token`, `drizzle/0012_personal_access_token.sql`; `kind`, `drizzle/0048_token-kind.sql`, #189): the table also holds native clients' `device` tokens (Profile › Devices, Auth), and `authenticateToken(db, token, kind)` takes only the surface's kind, so a device token on `/mcp` is the same 401 as an unknown one and records no use. Otherwise: `closet_` plus 32 random bytes in base64url, stored as its SHA-256 (hex, `personal_access_token_token_hash_unique`) with an 11-character display prefix; `created_at`, `last_used_at` (written at most once a minute), `revoked_at` (revoked rows stay, hidden from the list). At most `MAX_ACTIVE_TOKENS` (20) in force per user and kind, checked on the list `createToken` reads under the user's row lock and hands back for the page; at the cap an agent token is refused, a device sign-in evicts that kind's least recently used (`coalesce(last_used_at, created_at)`, then the lowest id), logged with the user and the evicted row id. Managed at `/auth/tokens` ("Agent Access"). **Creating needs the current password** (`currentPassword`, checked with `verifyPassword` like change-password; the step-up rule, Stack Auth): a wrong one re-renders the form 400 (name kept, password never echoed or logged); a missing one is a schema 400; every attempt counts against `ACCOUNT_LIMIT`. A created token is answered once in the page, `Cache-Control: no-store`, beside the `claude mcp add` command. Revoking needs no password; `POST /auth/tokens/:id/revoke` of anyone else's, a device's, an unknown or an already revoked id lands back on the page with "already revoked" (`?revoked=0`), never a 404 page. A new password revokes them all, of both kinds. The bearer gate `/api` shares (`createBearerGate`, `src/web/auth/bearer-gate.ts`; Request security) reads `Authorization: Bearer` (never the cookie) into `request.accessToken` at onRequest, before the body is read; a missing, malformed, unknown, revoked or device token is the same JSON 401 with `WWW-Authenticate: Bearer realm="closet"`, charged to the address's `BEARER_REFUSAL_LIMIT` (past it, a missing, malformed or unknown one is a JSON 429).

- **A tool answers an entity by projecting its API resource's mapper, never by mapping it by hand** (#711): the feature's `<entity>-resource.ts` exports a record with its nulls kept (`garmentRecord`, `garmentListRecord`, `tripRecord`, `tripListRecord`, `outfitListRecord`, `outfitGarmentRecord`, `calendarEntryRecord`, `capsuleRecord`, `capsuleListRecord`), which the API sends through `asResource(Schema, record)` and the tool through `project(record, Schema, X_FOR_MCP, own)` (`src/web/api/resource.ts`): both shape the record by the resource's TypeBox schema at every level (only its keys, so a stored row's other columns never reach an agent; the API drops a null the schema does not declare, MCP keeps it). `X_FOR_MCP` is a `Projection<Record>` listing every field `keep`, `omit` (a photo URL an agent cannot fetch) or `own` (a nested level's own projection, `agent`'s bare name), so a field the resource gains is a type error at each projection, and `projections.spec.ts` holds each projection to its schema's fields, nested kept ones included. An `own` agent is `record.agent?.name ?? null`: a bare `?.` drops the key. A new entity's tool exports its projections and adds a row there; what the tool says beside the resource (`hasPhoto`, `today`, `weather`) goes in `own`.

- **`INSTRUCTIONS`** (`routes.ts`, the server's `instructions`): what Closet is, then the agent's workflow in rounds (#337; the design `docs/plans/2026-10-05-muse-suggestions.md` section 5): `get_suggestion_feedback` then `list_suggestions` first in every conversation, acting on every reason; read the style profile, the closet, `wardrobe_stats`, `get_sizes` and photos; `get_closet_coverage` for real gaps (`replace_soon` pieces are gaps); `create_option_group` per need, its note naming the closet pieces it pairs with; 2 to `MAX_OPTIONS_PER_GROUP` products each through `suggest_garment`, with note, rank, price and size; `goes_with_closet`; `suggest_outfit` a few per occasion of the week, every option in one; `finish_round` once at the end with the feedback read's `until`. The rules: never buy, mark owned, archive or delete, never propose again what was set aside. The README's "Styling with an agent" is the owner's side: change them together.

- **What a tool writes carries its token** (#682, `src/web/write-origin.ts`): every stamping writer takes a required `madeBy`, which a tool builds with `originOf(ctx)` (never by hand); calendar entries become `planned_by = 'agent'`, trip outfits, outfits and garments record the token. Each writing tool's `attribution` in `MCP_WRITES` (`src/web/api/operations.ts`) says what it stamps or why it stamps nothing; `test/integration/mcp-attribution.spec.ts` runs every `stamps` tool. Readers read the agent through `agentLabelSql` with the viewer (the token's author sees its name, the owner "<first name>'s agent", anyone else "Agent"; resolved in SQL, so no row holds the author) and word it with `agentName`; API resources and the feed answer `agent: { name }`, the tools `agent`. A token on a row never means the agent: suggestions and proposals are `suggested_at` / `proposed_at`. **The app shows it with one `AgentBadge`** (`src/web/agent-badge.tsx`, #822: `data-agent`, "Made by <name>" for assistive tech) beside where Auto shows (a calendar row and Today's card, a trip's outfit, the Saved tab's tile and the outfit page, a plain agent-added wishlist card and the garment page; the suggestion agent's rows keep "From {agent}"). A page adds the label to its own statement through `agentLabelSql` with its viewer, never a read of a token name of its own; the month's cells draw collages only and carry none.
- **The agent's tools are the app's writers, never their own** (#337): a need is `createOptionGroup`'s, a pick the link import's garment marked by `markSuggestedProduct` in the garment's own transaction (`withGarment`), an outfit `proposeOutfit`'s (the outfit writer's proposal), the gaps `matchPlan`'s (`src/wardrobe/coverage.ts`, over `garmentSummaries`, as `get_wardrobe` reads the closet); a read is the page's (`readInbox`, `agentOutfitsSql`). The wardrobe plans' tools are gone (#337 part B1, after one release as 410 stubs). `test/integration/mcp-agent.spec.ts`, `mcp-agent-races.spec.ts`, `mcp-style.spec.ts`.
- **Connect**: `claude mcp add --transport http closet https://<SITE_URL host>/mcp --header "Authorization: Bearer <token>"` (README, Connect your Claude). Off the tailnet: production's public MCP host, through homelab's `closet-mcp-gate` (homelab `stacks/closet/README.md`). Hosted connectors need OAuth, not built.

## Moved out of AGENTS.md's Gotchas (#723)

- **`/.well-known/*` answers `{}` to anything** (`src/web/shell/routes.tsx`, to keep browser and tool probes out of the error log). An MCP client refused with a 401 may look for OAuth metadata there (`/.well-known/oauth-protected-resource`) and gets an empty object: harmless, since `/mcp` offers no OAuth, but its error can read oddly. Real OAuth for `/mcp` would need real documents there.
