`src/web/mcp/` (#33; plan section 14): the owner's own Claude (Code, Desktop) works on the wardrobe through MCP. `POST /mcp` is a Streamable HTTP endpoint on the official `@modelcontextprotocol/sdk` in **stateless** mode: a `McpServer` and a `WebStandardStreamableHTTPServerTransport` per request (`sessionIdGenerator: undefined`, `enableJsonResponse: true`: JSON answers, no SSE, no `Mcp-Session-Id`), fed a Web `Request` built from the Fastify request and the body Fastify already parsed, its `Response` copied onto the reply, so the root hooks (security headers, the request log line, compression) apply as to any route. `GET` and `DELETE /mcp` are 405. Tool inputs are zod 4 (the SDK's schema language; the only zod in the app); a call's arguments hold at most `MAX_TOOL_INPUT_ELEMENTS` array elements and object keys (`routes.ts`), and every array input has a `.max()`. **One request is one JSON-RPC message** (#667): a batch (an array body; the current MCP spec dropped them) is a 400 `-32600` before any server is built, so `MCP_LIMIT` counts tool calls.

- **An API route, not a page: `config: { surface: 'mcp' }`** (`src/web/surface.ts`, read through `surfaceOf`, shared with `/api`'s `api`). The root preValidation hook skips the session and the page context (so its errors are JSON, as on a static path), `requireSession` lets it through, and the same-origin hook accepts it without Origin (Request security, CSRF). The header is read by `presentedBearer` (`src/web/auth/bearer.ts`): two headers, a malformed one and none are each the 401, logged by reason. `secretPath` is set too, so the request log shows `/mcp` even if a client put a token in the query string.
- **Scope** (#701, `drizzle/0067_token-scope.sql`): an agent token is `read_only` and/or `own_wardrobe_only`, chosen at mint (Agent Access: read-only unless "Can make changes" is ticked) and never changed after; rows before 0067 are full power. `authenticateToken` reads it with the token (no statement) into `ToolContext.scope`, which **no tool reads**: read-only is `scopedTools` (`tool.ts`), which registers only `writes === false` tools, so `tools/list` omits the rest and a call is the SDK's `MCP error -32602: Tool <name> not found` tool error, logged `refused (read-only token)` by the route, and the server's instructions open with the read-only line; own-only is `actorOf(ctx)`'s `ownWardrobeOnly`, which `resolveWardrobeAccess` answers for any other wardrobe as unseen with no share read (the unknown id's "Wardrobe not found") and `sharedWardrobesOf` as none. **`writes` is therefore a security flag**: `mcp-statements.spec.ts` runs every `writes: false` tool through a read-only token on a cold forecast against every table's digest (only `weather_forecast`, `weather_normals` and the last-use mark may change, no cutout wake), and `mcp.spec.ts` holds `writes: false` to the tools `MCP_WRITES` omits.
- **A token acts as its user, within its scope.** Every tool resolves the wardrobe it addresses (`ownerId`, from `list_shared_wardrobes`) through the same `authorizeWardrobe` as a page's `?ownerId=` (`wardrobeFor`, `tool.ts`), and calls the pages' own query and write functions: no SQL of its own for a write, and its reads are the page's own fragments (`garmentContext`, `todayFor`, `styleProfileSql`), never a query path of its own (`mcp-statements.spec.ts` pins each tool's). Refusals are the domain functions' `NotFound` / `Forbidden` (`src/web/refusals.ts`; a tool never builds one, `guards.conf [refusals]`) and answer a tool error with the page's message (`Wardrobe not found`, `Forbidden`, `Garment not found`); the garment reads go through `wardrobe/garment-access.ts` (`garmentIn`, `searchGarments`, `garmentPhotoIn`) and the writes through `wardrobe/garment-actions.ts` (`editGarment`, `addGarmentCopies`, each addressed with `unseen: 'wardrobe'`), capsules through `capsules/capsule-actions.ts` (same), the agent's writes through `wishlist/suggestion-actions.ts` and goes_with_closet through `goesWithCloset(db, actor, id)`, the outfit tools through `outfits/outfit-actions.ts` (`requireOutfit`, suggest_outfit's `proposeOutfitTo`) and the calendar's through `calendar/entry-actions.ts` (`planOutfit`, `markEntryWorn`) and `replaceEntryOutfit`, each `actorOf(ctx)`; anything else is logged with its stack and answered without detail.
- **Tools** (`tools/`): each tool's contract: `tools.md`. Read tools are annotated read-only; write tools start their description with `WRITES`, and nothing deletes or archives. A tool acts on the caller's own data unless it takes an `ownerId`; suggestions, outfits, the calendar, wears and trips are always the caller's own.
- **Photos: the one exception to "no photos leave the homelab"** (#90). `get_garment_photo` (read, `tools/garments.ts`) answers a garment's **400px thumb** (`Photos.getVariant(..., 'thumb')`, the cutout's if any, never the original) as an MCP `image` content block (`image/webp`, base64) after a text block naming the garment, so the owner's own authenticated Claude can tag garments (`search_garments` with `needsTagging`, then `update_garment`, MANAGE or owner as ever). A tool answers a picture by returning an `ImageAnswer` (`tool.ts`), which `registerTools` turns into those blocks; everything else is JSON text. Scope is `get_garment`'s: the caller's own garments and a wardrobe shared with them at VIEW or more (`wardrobeFor`), another user's garment without a share is "Garment not found"/"Wardrobe not found", a garment without a photo "Garment has no photo". **Never a selfie**: a garment's photo is its own `file` row, but the tool still asks `publicPhoto` (which also names the thumb its row points at) and answers a selfie's file as "Garment not found" with a warn line (logger `Web`; `garmentPhotoIn`), as the public `/file/**` routes do. Logged by the one `Mcp` line, never the bytes. `test/integration/mcp-photos.spec.ts`.
- **`ToolContext.tokenId`** is the calling token's row id: the call's log line, the provenance of what the agent suggests (a need's, a pick's, an outfit's) and the key of its feedback cursor. Never the token.
- **Never logged**: a call's arguments or the token, nor its prefix (`mcp.spec.ts` asserts it of every line); a refused credential logs its reason and the address. A converted writer's op line says `surface: 'mcp'`, so a tool logs no success of its own.

## Gotchas

- **`/mcp` is publicly reachable, and the token is the whole gate.** The public hostname reaches only `POST /mcp`, through a gate that 404s everything else, so nothing in closet may assume `/mcp` callers are on the tailnet. A token must never appear in a log line or error (asserted by `mcp.spec.ts`).
- **`@fastify/rate-limit`'s `createRateLimit()` answers `isAllowed: true` only for the allow list.** A counted request is `isAllowed: false` whatever its count; over the limit is `isExceeded`. `/mcp`'s link import budget reads both (`src/web/mcp/routes.ts`).
- **Moved rules** (detail in `reference.md`): `authenticateToken` takes only the surface's kind, so a device token on `/mcp` is the 401; the token is read from `Authorization: Bearer` at onRequest, never the cookie. Creating a token needs the current password, never echoed or logged; revoking another's or an unknown id answers "already revoked", never a 404. A tool answers an entity by projecting its API resource's mapper, never by hand. A tool's write stamps `madeBy` from `originOf(ctx)`, never by hand; a token on a row never means the agent. The agent's tools call the app's writers, never their own; `INSTRUCTIONS`: never buy, mark owned, archive or delete, never propose what was set aside.
