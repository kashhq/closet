# Today

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds The page.

`src/web/today/` (#15; plan section 9, redesign "Today"): `GET /`, the home screen, the dock's first tab and the manifest's `start_url` (its `id` stays `/wardrobe`: the installed app's identity). The signed-in user's own day, like the calendar; signed out it is the login redirect like any page. **Today stores nothing of its own**: it reads the calendar and the generator and writes through their writers.

- **The model is `todayFor`** (`today.ts`), shared by the page, the MCP tool `get_today` and the morning push reminder (which hands it the batch's weather, `ownWeather`, #173), so the three never disagree: a row per occasion planned today (`entriesSql`, shared with the calendar: occasion order, each entry with its outfit's collage garments), and, **while nothing that dresses the day is planned** (`DAY_OCCASIONS` in `src/wardrobe/occasions.ts`: all day, work, daytime), an all-day row of suggestions first: `todayIdeas`, `ideasFor` for today's forecast with the day's seed (`dailySeed`, as the gallery opens), a page of `TODAY_IDEAS` (3), and the person's weather (`weatherWithForecastSql` then `userWeatherFrom`, null with the weather off), which the line and the ideas share. A day with only a run and a dinner planned still gets ideas for what to wear between; a work day does not. Worn today (`somethingWornSql`: a worn entry or a garment's "Wore today") is read only when asked (`todayFor`'s `worn`, in the same statement), since the page never shows it: `get_today` asks, and the evening reminder reads it with the day's bare entries (`entriesOfDaySql`) for every evening person in one statement (`eveningDays`, #173): the evening names the plan and needs neither weather nor ideas, so it never builds the model.
- **The first-run path** (#666): `todayFor`'s `firstRun` (asked by the page only) reads `closetKindsSql` in `readDay`'s statement and judges it with `closetCanDress` (`src/web/gallery/queries.ts`, over `canProduceOutfit` in `src/wardrobe/properties.ts`: a top and a bottom, or a dress), the one gate Calendar's "Plan my week" and Styling's Include picks (`StripsReads.canDress`) use too, each in its own statement. Until it holds the page is `FirstRunCard` (`data-first-run="empty"`: the welcome and "Add your first garment"; `"incomplete"`: what is missing and "Add a garment"), its one primary button opening Wardrobe's own `AddSheet` in place (`sheetOpener(ADD_SHEET_ID)`, camera first); the weather line (the city) only once a garment is in; no "Plan another outfit", no "Plan my week" and no ideas row (none could be drawn). `first-run.spec.ts`.
- **"Wear this" is one transaction, and happens once** (`wearIdea`, `queries.ts`; `POST /today/wear`: `garmentId` × n and the `occasion`, a native `PostForm`, 303 back to `/`): `pickIdea` (under `lockOwner`: the outfit of exactly these garments, reused or created), then `wearOutfitOn` (planned today for the occasion through `insertEntry`, the entry marked worn through `setEntryWorn`), in the same transaction. A double tap's second transaction waits on the owner lock, finds the outfit and the entry, and `setEntryWorn` finds it worn (`changed: false`, logged "already worn"); `today-home.spec.ts` holds one transaction open while a second waits. Garments not in the owner's closet are a 404 with nothing written; a malformed post a 400. The API's twin is `POST /api/v1/outfit-wears` (`api-routes.ts`, #193b): the same `wearIdea`, but with the `day` sent (`wearIdea`'s `day` apart from `today`), judged by the queued taps' window. **The API's read** is `GET /api/v1/today` (`api-routes.ts`, `today-resource.ts`, #195a): `todayFor` with the page's `needs`, so the same statements; an ideas row's `nextCursor` is Refresh as `GET /api/v1/ideas?limit=3&cursor=` (the same seeded read: page 1 here, then the cursor's offset).
- **Network first, not a stale-while-revalidate tab root** (decided in #15; `OPENS_STALE`, `src/web/page-cache.ts`): all of Today is the day's own data (the plan, the ideas, what was worn), so a byte-stable page would be a shell with a date and every row a fragment, and a copy opened first would show yesterday's plan with live "Wear this" buttons. NetworkFirst with the navigation preload answers a cold open in one round trip; offline the worker's last copy shows with its age (freshness.js) and its writes disabled (`data-needs-network`, a `data-offline-note`). `SECTION_HOME.today` is `/` (the dock's link) and is deliberately absent from the stale tab roots.
- **"Ask your agent"** (#1286; `src/web/requests/AGENTS.md`): the sheet's opener under the agent's card, never on the first-run path (it queues offline: the one write Today keeps while offline), and the requests card above it, read in `readDay`'s statement (`todayFor`'s `requests`, the page's alone).
- **The dock** (`DOCK_TABS`, `src/web/layout/sections.ts`): Today · Wardrobe · Style · Outfits · Calendar, the owner's decision on #43 (2026-09-27; no centre "+"). `/` stays Today.
- **The page's rules** (detail in `reference.md`): one suggestion card ("Your agent has 4 needs..."), counted live (it shrinks as the owner decides and goes at zero), nothing to dismiss. A planned card's "Wore it" is a native post to the calendar's `POST /calendar/:id/worn` with `returnTo=/` (one worn write wherever it is tapped; native because the card's Change goes once worn); "Change" opens the gallery with `replace=<entry>` (`replaceEntryOutfit`), never once worn, and nothing is swapped on its own. Refresh (`GET /today/ideas`) is lenient (malformed: all day, page 1) and wraps to the first page after the last. From lg rows stack, never side by side.
