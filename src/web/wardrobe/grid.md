# The wardrobe grid

Part of the Wardrobe (`AGENTS.md` in this directory): `GET /wardrobe` (the Closet tab, or `#wardrobe-body` to a fragment request) and `GET /wardrobe/tiles` (the next page).

## What each statement reads, and why

Production reaches Postgres over a link that costs a round trip per statement (about 114 ms, homelab #40), so the grid's cost is its statement count (#156, #159). `wardrobe-grid.spec.ts` asserts every count below; a new read joins a statement that already runs, never a new one.

- **The session** (`select ... from "user"`): the root hook's, every page's (#174).
- **The page** (`gridPage`): one row per tile and one more that says there are more; only what a tile shows (id, name, category, status, photo name and version, quantity, condition). The owner's grid adds `care`: `away`, and the dirty copies, a correlated count of the garment's wears since its wash per tile with a wash limit (`dirtyCopiesSql`, over `garment_wear_garment_id_day_index`). The plan puts it at about 0.03 ms a tile, so it stays correlated: a set-based join would cost more than it saves. The capsule picker (`?pick=`) adds `member`, `inCapsule` per tile, which pre-checks the tile. It replaced a separate `memberIds` read, the ids of every member, in #159.
- **The context** (`gridContext`, `grid-context.ts`): one row of scalar subqueries (`selectScalars`, `src/db/select-scalars.ts`), since they share no rows. Lists arrive as JSON, so the harness's Rows column counts it as one. Each part exists for one piece of the page, and `gridContextParts` (`grid-routes.tsx`) asks only for what the answer renders:
  - `count`: the scope row's "N results", `count(*)` over `gridWhere`, the page's own filters;
  - `options`: the filter sheet's choices (`filterOptionsSql`), only values the wardrobe holds, archived included, so no choice finds nothing;
  - The sheet that shows them (`FilterSheet`, #674; a `filters` sheet since #1067, see The facets below): every choice is `Chips` (`form-field.tsx`: a real radio `input.btn` named by `aria-label`, plus a "× Clear" chip while one is chosen), never a hidden input (`closet/no-hidden-control`, scripts/lint/hidden-control.mjs, which reads computed classes too); the dialog is `aria-labelledby` its heading and each group `role="group"` over its heading. Every built-in category's type group is rendered, each shown by `group-has-[input[name=category][value=…]:checked]/filter:block` (`TYPE_GROUP_REVEAL`, a literal table so Tailwind sees the classes), so Type appears as soon as a category chip is checked; `gridSearch` keeps a type only while an applied category owns it (`findType`: no category, or another one, drops it), so clearing the category clears the type (the applied type is checked only inside the applied category's group, never in another group sharing its name such as `other`) and a stale hidden type radio never filters (the sheet still posts it). The API and MCP (`checkedType`, `garment-search.ts`) share the predicate but refuse a type without its category as a 400, since the caller named it;
  - `capsules`: the scope row's capsule menu, and the lookup that makes another wardrobe's `?capsule=` or `?pick=` a 404 and names the picker's bar;
  - `toTag`: "N garments need details" (`toTagCountSql`), for an editor only;
  - `toWash`: the laundry prompt (`needingWash`, `src/web/wears/queries.ts`), for the owner only (it reads wears);
  - `drafts`: "N photos waiting · Continue" (#200, `draftsWaitingSql`), for an editor only;
  - `sharedWardrobes`: the app bar's switcher, on a full page only (a fragment swaps `#wardrobe-body` and the ⋯ menu, never the bar).

  The picker reads only `capsules` (to refuse a foreign `?pick=` and name it); select mode reads `count` ("Select all N") and `capsules` (Add to capsule, and a foreign `?capsule=`), #677.

- **So**: a page or fragment is 3 statements, select mode 3, the picker 3, a next page 2. Before #159 a page was 9 (8 reads in parallel, each its own round trip and pool connection) and the picker 10.

Tagging mode is 2 statements. `nextToTag` reads the card with its count left as a window (`count(*) over ()`), the garments below the cursor sorted first. A tap's answer is 3 (`taggedGarment`, the chips and the count), or 4 when it writes (`select-and-tag.md`).

## Paging, filters and search

- **The grid is keyset-paged**: `GRID_PAGE_SIZE` (48, `grid-page-size.ts`, which the service worker bundles) tiles newest first, `id < before` for the next page. The last tile is followed by a sentinel (`PageSentinel`, `src/web/page-sentinel.tsx`, every paged list's since #660: `hx-trigger="revealed"`, `hx-swap="outerHTML"`) that fetches `/wardrobe/tiles` with the same filters and replaces itself with the next page and its own sentinel. Filtering and searching swap `#wardrobe-body` and so start at page one. Indexes: `(owner_id, status, id desc)` and `(owner_id, category, id desc)`, also the owner foreign key's; at household size the planner often prefers a backward primary-key scan with a filter, which is as fast (under 0.3 ms at 1,500). A new sort order needs its own cursor and index.
- **Care filters and badges** (#7): `?needsWash=true` (a copy needs a wash; the owner's own wardrobe only, `gridSearch` drops it on a share, and the sheet does not offer it there) and `?attention=true` (condition not good), checkboxes in the modal's Care group. Tiles carry `quantity` ("×3") and `condition` for everyone, and `care` (dirty copies, away) only when `gridPage(..., { ownerView })` is the owner's: the correlated wear count is not even computed for a share. The owner's grid shows a "N to wash" chip linking to Laundry (`toWash`; one chip row with "N to tag" and "N photos to add", #732); Laundry is also a Wardrobe tab, not on a shared wardrobe.
- **Capsule filter** (`?capsule=<id>`, #8): members only (`inCapsule`, `src/web/capsules/queries.ts`); chosen from the scope row's capsule menu (`CapsuleScope`, which also links the Capsules tab), carried by every link through `GridSearch`; a `?capsule=` URL is honoured wherever it comes from. Not an id is a 400, not one of the addressed wardrobe's capsules a 404.
- **Property filters**: `type` (only with its category: `gridSearch` drops a type the chosen category lacks, so dropping the category pill drops it too), `warmth`, `formality` and `material` (`materials @> array[...]`, as the colour's `colors @> array[...]`); the scales and the material are 400 outside their sets, like a colour. No GIN index on either array: the owner's grid index narrows to one wardrobe (hundreds of rows) and the containment is a filter over those, as the other property filters are. The filter modal's values: `options` above (materials through an `unnest` subquery). `GridSearch`'s keys are the query parameters' names, so `searchParams(search)` is the whole list: links, the sentinel, the search form's hidden inputs and the bulk form's action all spread it, and a new filter needs no second list.
- **The facets** (#1067, the desktop plan's §4): browsing is a `facets` page whose aside is the filter sheet (`wardrobeFacets`), one `<dialog data-sheet="filters">` that is the bottom sheet below lg and, closed, the docked left column from lg (main.css; layout/sheet.tsx), its form never rendered twice; its opener is `dockedFiltersOpener`, gone where it docks, so the page holds no `lg:` class. Every fragment answers the facets out of band, their content swapped into the aside (`PageFragment`'s `aside`, `innerHTML`), so the form's markup is always what the URL asks for: htmx's history snapshot keeps attributes, never a checked property, and a form kept across Apply came back from Back unchecked beside a filtered grid. The aside is the docked column's scroller, so its scroll survives; Apply and Clear keep ids, so htmx refocuses them. **Every other answer that brings the facets is asked from them** (#1144): a chip's × and the capsule menu send the filter form's fields (`#filter-form`, `fromFilters`: a bare `hx-get="/wardrobe"` with `hx-include`, the chip's filter left out by `hx-params="not <name>"`, the capsule set over the form's by `hx-vals`, or dropped by `hx-params="not capsule"` for All garments, never sent empty; on a page without the filter form `nativeWithout` (`actions.ts`, a capture listener ahead of htmx's) stops htmx's listener so the link's own href, every filter in it, is followed; not `hx-on`, which needs the `unsafe-eval` the CSP refuses), and search's Enter submits the filter form itself (`submitsVia`, `actions.ts`, with htmx loaded; the search form unboosted, its native GET without script), so a facet ticked and not yet applied lands in the pushed URL and comes back checked, never silently dropped. Never `hx-include` the filter form into the search form: its own hidden filters (the no-script GET's) would go too, a filter sent twice (a 400); `<noscript>` around them does not help, since htmx parses every swap with scripting off, which makes them real inputs. The phone's sheet closed without Apply (Close, the backdrop, Escape) resets its form to the applied filters (`Sheet`'s `resetsOnClose` for a `filters` kind, `actions.ts`), so only applied filters ride along there; docked from lg it never closes, so the live ticks do. Not the other choice, an answer that leaves the facets alone: a chip's × and the capsule change what the facets show, and the aside must be the URL's state. **One keyword field**: the scope row's `#search-form` at every width (from lg too, not at the facets' head), which the sheet's Apply and Clear `hx-include`, so a keyword typed and not yet searched rides along; a filter-form field (`form=`) would not submit on Enter on the phone, where Apply, the default button, is in the closed sheet and not rendered. `/` focuses it (`views/assets/page/search-shortcut.ts`). Select mode and the picker stay `single`, without facets (they read no `options`).
- **Search** (#673, `keyword-search.ts`) is one predicate for the grid, `GET /api/v1/garments` and `search_garments` (all through `gridWhere` and `gridOrder`): the keyword split on whitespace, every word must start a word of the name, brand, notes or category, or of a colour's or type's label, `FOLDED_PUNCTUATION` dropped on both sides, one fixed set ("jcrew" is "J.Crew"; "shirt" is not "T-shirt" or "sweatshirt"), letters of any script kept ("café"). Colours, types and built-in categories are keys: a word is resolved to the keys whose labels match in TypeScript before the query, never labels in SQL. The fold in SQL is `translate(lower(... collate "pg_unicode_fast"), FOLDED_PUNCTUATION, '')` per row, independent of the database's locale (a `[:alnum:]` class is ASCII under C, and "café" never matched), no index or column at household size; a punctuation-only word (`%`) is matched as itself, LIKE's wildcards escaped. **The order**: `keywordRank` first (0, or 1 when a word matched only the notes), newest first within it; the next page is "a later rank, or the same and an older id", **the rank carried in the cursor** (`GridCursor`, `grid-cursor.ts`: `before=<id>` at rank 0, as every unranked cursor always was, `before=<rank>.<id>` past it; the API's `rankedIdCursor`). Never read the cursor's rank from its row: a lookup by the client's id read any wardrobe's garment, so the page told a stranger whether its private text held the keyword (#784), and an edit to that garment between pages skipped rows. With the rank carried, the next page may repeat a garment edited meanwhile, never skip one; the statement counts are unchanged. The colour filter (`colors @> array[<colour>]`) must be a built-in colour (else 400).
