# Outfits

`src/web/outfits/` (ported to plain Fastify and Drizzle 2026-09-26). Outfits are private: every query is scoped to the signed-in owner, shares never reach them, `?ownerId=` is ignored, and another user's outfit id is a 404. **Every surface's read of one outfit and change to one is `outfit-actions.ts`'s** (#188d: `requireOutfitPage`, `requireOutfit` (get_outfit), `editOutfit` (the outfit form, Styling's Save in place, the API's PATCH, whose absent `slots` keep the rows: `OutfitEdit`), `removeOutfit` (a proposal not loved: 409), `reactToProposal`, suggest_outfit's `proposeOutfitTo`; `outfitNotFound` for Styling's `?outfit=` read), each `(db, actor, id, input)` over the owner-scoped queries with `actor.userId` and throwing `NotFound('outfit')` or a 409 with a `logDetail`, so routes and tools parse, call and render; a VIEW or MANAGE grantee is a stranger here (`outfit-actions.spec.ts`).

- **Composition is `outfit_slot`** and nothing else: `(outfit_id, position)` primary key, `category` text, `garment_id` nullable (`ON DELETE SET NULL`: deleting a garment empties its slot). Styling saves them top to toe (the rows' order); the outfit form old cached pages post keeps the order posted, and an empty slot is a row kept without a garment. `drizzle/0002_outfit_slot.sql` built it from the old `outfit.slots` JSON and `outfit_garments` pivot and aborts the boot if the two disagree for any outfit (compared as garment sets, owner-checked). A slot only ever names a garment of the outfit's owner: owned (closet or archived), or on the wishlist while nothing holds the outfit (see Incomplete outfits). Archived garments stay in outfits.
- **One outfit per garment set, at save time** (#219): `createOutfit` is the one writer of new outfits (every pick through `pickIdea`, `pick.ts` (R4: it moved here from `gallery/ideas.ts`, lock order unchanged; the engine reads, the owner writes): the gallery, Styling's Save, Today, trips, a replace, `pick_outfit`, the week planner, a saved look's "Save as outfit" (Inspiration); the outfit form's POST /outfits, `create_outfit`, `suggest_outfit`'s proposal, the seed) and always runs in `ownerTransaction`. Its outfit insert is one statement (`insertOutfitOnce`, a CTE over `sameGarmentsOutfit`: the owner's outfit whose non-empty slots are exactly these garments, the oldest) that inserts only when there is none, else answers that one: `alreadySaved`, nothing created, its own name and notes kept, planned on the save's day when asked (`insertEntry`, once a day), and any save but the planner's takes it over as far as its origin reaches (`reuseOutfit`: `adoptOutfit`, `src/web/week-plan/adopt.ts`, #77, #659). A pick asks first, in its garments' locked read (`pickedGarments` joins `sameGarmentsOutfit`, #168), and goes straight to `reuseOutfit` when it finds one, so a repeated pick costs no insert. Under the lock two saves of the same garments take turns, so a concurrent Save and pick make one outfit. **Why not a unique key on the set**: the set is not stable data. A garment delete empties its slots (`ON DELETE SET NULL`) and can leave two outfits alike; an edit (`updateOutfit`) may make one match another (allowed: the rule is about what a save creates). A key would have to refuse the delete or merge outfits that carry entries, wears, selfies and trips. Occasions live on calendar entries, so one outfit serves every occasion; the one thing lost is the same garments twice on one day (an outfit is on a day once), which the pick already refused. An outfit with no garments (the form's empty outfit) is never "the same". The API's POST /outfits therefore refuses one (400: `minItems: 1` and at least one row with a garment), since a retried empty create would otherwise make a new outfit each time. The seed throws if a bible repeats an outfit's garments. The outfit form redirects with `?alreadySaved=1` on a reuse; `create_outfit` answers `alreadySaved`. `outfit-saves.spec.ts` interleaves each save with a pick (held transaction, `test/integration/interleave.ts`).
- **A save never drops a garment** (#219): a garment it cannot hold refuses the whole save, nothing written, the answer naming it (`OutfitGarmentsGone`, `gone-garments.ts`): "Not saved: Linen shirt is archived." A 409 when every gone garment is the owner's (archived for a pick, on the wishlist: named), a 404 when any is not a garment of theirs (deleted, another's, unknown: those are indistinguishable, counted, never named, as Request security wants). A pick takes closet garments (`pickedGarments`). **A slot write takes what `slotMayNameSql` allows, the one rule of what an outfit may name** (Styling's rows read it too, `rowGarmentsSql`): closet garments, those the outfit already holds (an archived one stays), and a garment not bought yet that is offered to style with (`offeredToStyle`) while nothing holds the outfit. It is judged by `insertSlots` itself, never a read before it: it locks them `FOR SHARE` in id order in its insert, under the owner lock (a pick set aside meanwhile is refused, `GONE_SET_ASIDE`), so a delete either waits for the save or makes it refuse; never a slot emptied behind the save's back, never a foreign-key 500). Before #219 `insertSlots` stored such a slot empty and logged it. Where a pick answers `'not-found'` (it locked and judged), the route names the garments afterwards with `garmentsGoneError` (pickTo, Wear this, `pick_outfit`); a replace names them in its own transaction and throws them (`garmentsGoneRefusal`), so every caller answers the same. **Styling answers it with its page** (see Styling), the rows and sheet as posted and the gone rows back to None; the outfit form and the MCP tools answer the error page and the tool error with the same words. The week planner's own pick of a garment gone meanwhile skips that slot (it saves nothing partial either).
- **Pages read slots by position**, empty slots showing nothing, and **each Outfits page is one statement after the session's** (#164, `page-context.ts` over `selectScalars`; production pays a round trip per statement, #156): the Saved tab (`savedContext`: a page of `savedOutfitsSql`, the tiles newest first, only id, name and garments, as a trip's add page reads them; `outfitActivitySql`; with `?for=day:` the calendar's `entriesOfDaySql`, judged by `readDayChoice`) and the outfit page (`outfitContext`: `outfitDetailSql`, null when not the owner's, so a 404 costs the same; `outfitEntriesSql`, split by `readOutfitEntries`). The collage's garments are one fragment, `outfitGarmentsSql`, shared with the garment page's strip (`outfitsWithGarmentSql`) and a trip's outfits. `findOutfit` (with notes and the share link) is the MCP tools'; `listOutfitsPage` is `list_outfits`' and `GET /api/v1/outfits`' (`api-routes.ts`, `outfit-resource.ts`). `outfit-statements.spec.ts` pins every count below.
- **Every list of outfits is read a page at a time, through one reader** (#660, `outfitPageSql` in `queries.ts`): newest first, keyset on the id (unique, so no tiebreaker is needed and outfits alike in every other way neither repeat nor skip), `OUTFIT_PAGE_SIZE` (30, `page-size.ts`) a page, one row more read to say there is a next, the answer `{ outfits, next }` in the page's own statement. `savedOutfitsSql(owner, list, page)` (the Saved tab, the plan page, a trip's add page, the warm list's kept outfits) and `listOutfitsPage` (`list_outfits`, `GET /api/v1/outfits`) are its two row shapes; never an unpaged list read. Each page's last tile or button is followed by `PageSentinel` (`src/web/page-sentinel.tsx`, the wardrobe grid's, `revealed`), which fetches the next page into the same list (and form): `GET /outfits/tiles` (`SavedTiles`), `GET /calendar/plan/more`, `GET /trips/:id/outfits/new/more` (`SavedOutfitButtons`), each `before` (`OutfitCursor`: a bound, not a resource id; malformed is a 400) and the page's own navigation state, one statement after the session like its page. Bare `/outfits` is byte-stable because page 1 is a fixed size. Offline, a next page never fetched fails as `htmx:sendError` (the offline banner) and the list ends there; nothing warms them. `outfit-paging.spec.ts` (60 outfits alike but for the id) holds the three surfaces, the tool and its API twin, and their statements.
- **Composing is Styling** (#42, see Styling). The builder's pages are redirects: `GET /outfits/new` to `/styling` (carrying `?for=`, a pre-#13 `?scheduleDate=` as all day, `?capsule=`, `?returnTo=`) and `GET /outfits/:id/edit` to `/styling?outfit=ID` (its `returnTo=/calendar&returnToWeek=W` as `returnTo=/calendar?week=W`), so cached links and the manifest's old shortcut still land. `/outfits/row-fragment` is gone (htmx-only, nothing links it).
- **The outfit form's writes** (POST /outfits, POST /outfits/:id; kept for pages the installed app cached before Styling, and the specs' fixtures, test/support/e2e-data.ts): `category` and `garmentId` arrive one pair per row, in document order (a single row as scalars, which ajv's `coerceTypes: 'array'` turns into arrays); unequal counts are a 400. `scheduleDate` and `returnToWeek` are `''` or a real date (else 400). The outfit, its slots (replaced whole) and the calendar entry commit in one owner transaction (a create reuses an outfit of the same garments, above). **An update is 7 statements** (#164; 10 before): the session, begin, the owner lock, `lockForEdit` (the outfit `FOR UPDATE`, then its name and notes and the planner's entries claimed, each write reading the locked row, so none runs ahead of the lock), `insertSlots` with `replace` (positions past the new last deleted and the rest upserted on the `(outfit_id, position)` key, one statement: the two touch disjoint rows), the outfit's trips (read after the lock, so a trip that added it meanwhile is seen), commit; a prune only when it is on a trip, the entry only when planned. The row lock keeps two saves of one outfit from colliding on the slot key. An update without `name`/`notes` leaves them; blank ones are stored as null ("Untitled Outfit"). Both are `text` columns since `0005`; the caps are the form's (`OUTFIT_NAME_MAX` 255, `OUTFIT_NOTES_MAX` 4000 in `form-page.tsx`, shared by the inputs' `maxlength` and the route schema, a longer post is a 400). The redirect goes back to `/calendar?week=` when `returnTo` is `/calendar`, else to the outfit. "Add to calendar" is the date plus an occasion select (`scheduleOccasion`, all day when absent: forms cached before #13).
- **The Saved tab** (R5, `list-page.tsx`; plan "Outfits"): a two-column grid of `OutfitCollage` `tile`s (a 4:5 frame so rows line up), each with its name and `outfitActivitySql`'s line ("Planned Oct 3 · Worn 4×": one grouped statement over the owner's entries; worn is `entryWorn`, marked worn or with a selfie, the outfit page's Worn strip's own predicate, so the two agree; it depends on the day, never the hour, so bare `/outfits` stays a byte-stable tab root). No per-card calendar dropdown: planning is the outfit page's. **With `?for=day:D&occasion=O[&replace=E]`** (navigation state through `parseDestination`; a trip or anything malformed is the plain grid) it picks for that day, the calendar's "Pick a saved outfit": one native `PostForm` to `POST /calendar` (date, occasion, week, and `replace` only while that entry can still change, `pickDestination`), each tile a submit button stretched over it; an outfit already on the day is disabled, saying for which occasion. The plan page and it judge the day by one `readDayChoice` over `entriesOfDaySql` (`src/web/calendar/day-choice.ts`: what is on the day, the entry `replace` names, `plannedNote`), so they never disagree; the Saved tab reads the entries in its grid's statement. `DayDestinationLine` (`destination-views.tsx`, "For Tuesday, Sep 29 · Evening" with the way back to the plan page) heads both tabs; `OutfitTabs` carries a day destination between Saved and Ideas (`savedUrl`, `ideasUrl`) and is static without one; its third tab, Inspiration (#22, `src/web/inspiration`), is always the bare `/inspiration`.
- **The destination (`destination.tsx`) owns every encoding of `?for=`** (2026-10-17): `parseDestination`/`destinationQuery` for URLs, `DestinationQuery` (a page's lenient querystring) and `DestinationBody` (a write's strict body) to spread into a route's schema, `DestinationFields` (the hidden fields a form posts back); `destination-views.tsx` holds what the pages say of one, `DayDestinationLine` and `destinationPickLabel` ("Plan for Tuesday", "Add to the trip", the change's word), the one piece needing `t` (the ratchet's fan-in bound is i18n's importer count, so the parser module stays off it). A feature spelling the format or the schema itself, or switching on the kind for a label, is a regression; the calendar's plan sheet is the one form writing the field names by hand (its occasion is the user's choice: Calendar); `destination.spec.tsx` holds the fields → body → parse round trip.
- **Origin and the one list rule** (#659, `src/wardrobe/outfit-origin.ts`, decisions 2026-11-13): `outfit.origin` is `person`, `agent`, `idea` (picked for a day, a trip or an entry: Wear this, a day's pick, Change) or `planner`; every `createOutfit`/`pickIdea` caller says it (the gallery's `pickOrigin`). A reuse only raises it (`adoptOutfit`), an edit makes it `person`. **Saved, the plan page and a trip's add page list only through `savedOutfitsSql(owner, list)`**, whose `keptOutfit()` (`person`, `agent`) is the one predicate; the rest are "Worn and planned" (`?show=one-offs`, `outfit-list.tsx`, lenient; `GET /api/v1/outfits?show=`). Never a per-surface filter. A calendar row draws a one-off's collage and occasion, no name. `week-plan.spec.ts` (the one-offs) holds the three surfaces.
- **Muse's outfits** (#335, `proposals.ts`, `reactions.ts`, `muse-cards.tsx`): ordinary outfits the agent proposed, with the owner's reaction; which list each is on, the one writer, what may be held and the tab's cards: `muse-outfits.md`.
- **Incomplete outfits** (#335, the Muse epic; the rule and its two halves: `references.ts`): **an outfit may hold a garment not owned yet only while nothing holds it** (`outfitIsHeld`: no calendar entry, no trip), so a planned, packed or worn outfit is always complete. A slot write takes wishlist items offered to style with only into an unheld outfit (`slotMayNameSql`; into a held one it names them `GONE_WISHLIST_HELD`). Every write that makes an outfit held writes only where `outfitIsComplete` and reads `piecesToBuySql` in the same statement, throwing `OutfitIncomplete` (409, "Buy Wool blazer first: an outfit with pieces not bought yet can’t be planned or packed.") when it wrote nothing for that reason: the calendar's `upsertEntry`, `planToWear`, `setEntryOutfit`, and `addTripOutfit` (its check after the outfit's lock: Trips). Wearing needs an entry; Ideas, Today and the week planner pick closet garments only, and the generator's memory (`savedSlotsSql`) leaves incomplete outfits out (its duplicate rule compares drawn roles, so one whose piece to buy is an accessory would hide a closet idea). Derived on every read, never stored: Bought it completes an outfit, a dismissed pick keeps its slot. The views judge the garments they read (`OutfitGarment.status`, `piecesToBuy`; `to-buy.tsx`): the collage badges a piece To buy, the Saved grid's line says "1 piece to buy", the pickers (`SavedOutfitButton`, the Saved tab's `?for=day:`) disable it with "Buy 1 piece first", and its page shows the pieces above Edit in Styling (opened with Include picks on, `picks=1`), with no Plan. Styling's rows read the same rule (`rowGarmentsSql`), so a piece to buy stays as its row; `insertSlots` names its refusals itself (`slotRefusals`). MCP `list_outfits`/`get_outfit` answer `toBuy`. `incomplete-outfits.spec.ts` holds a row per surface.
- **The outfit page** (R5, `show-page.tsx`): the collage (`card`; it warns, #358: archived and away pieces marked, read by `outfitGarmentsSql({ away: true })`, the only collage read that asks), **Plan** (a `modal-bottom` sheet: a date from today and the occasions as chip radios, a `PostForm` to `POST /calendar`, 302 to that week) and **Edit in Styling** (`stylingUrl({ outfitId, returnTo })`), then its entries (`outfitEntriesSql`, in the outfit's statement: `planned`, the unworn ones from today on, soonest first, each linking its week; `worn`, the Worn strip), then its garments in saved order, each opening its page. Share and Delete are in the app bar's ⋯ menu (`#outfit-menu`); a shared outfit shows "Shared publicly" under the collage with its link and Stop (`POST /outfits/:id/share`, `/share/stop`, `setOutfitPublicShare`, #669; see Sharing). The name and notes caps (`OUTFIT_NAME_MAX`, `OUTFIT_NOTES_MAX`) live in `queries.ts`.
- **An outfit beside its name is `OutfitCollage size="row"`** (#360): every piece in one line, top to toe (`inOutfitOrderByCategory`), at one fixed size, marks as dots; a long outfit scrolls inside the strip, never the page. `SavedOutfitButton` (the plan page, a trip's add page, both through `SavedOutfitPicker`, the pickers' one Saved section) and a trip's outfit rows draw it, so picking shows what the trip shows; never a first-N slice (it cut the shoes off). Its pieces carry `data-collage-piece` (the category), as every collage's do. **A collage's pieces shrink in width, never overflow** (#663): heights are fixed per size, but every piece is `min-w-0` (and `object-contain`), so a layer and a top in a 48 px month cell share the row instead of spilling out; the root carries `data-collage` (the size) and `test/support/collage-fit.ts` (run by `test/calendar.spec.ts`) asserts no piece's box leaves its plinth.

## Gotchas

- **Never delete an outfit with a plain `DELETE`.** `outfit_calendar.outfit_id` and `garment_wear.outfit_calendar_id` both cascade, so it erases every wear of the days the outfit was worn. Go through `deleteOutfit`, which detaches them first (`detachOutfitWears`, one statement; Wears and washes). It is 7 statements whatever the outfit held (#164): the session, begin, the owner lock, the outfit `FOR UPDATE`, the detach, the trips read and the outfit deleted in one (the read sees the `trip_outfit` rows the cascade then removes), commit; a prune only when it was on a trip. Deleting one calendar entry does cascade its wears, deliberately; account deletion takes everything. A new path that deletes outfits or calendar entries in bulk must choose between the two on purpose; `wears.spec.ts` covers both.
- **"Delete the outfit once nothing holds it" asks one predicate, `outfitIsHeld`** (`src/web/outfits/references.ts`: a calendar entry on any day, worn or not, and a trip's `trip_outfit`), like `photoIsReferenced` for photos. `deleteOutfit` cascades every holder, so a holder missing from the list is a row silently deleted with the outfit: until #69's review, `removeUnheldOutfits` (Undo, the daily re-plan's swap, Change) asked only `outfit_calendar` and took planner-made outfits off the trips that held them, packing lists included. A new table with an `outfit_id` joins the predicate in the same change, unless its link is `ON DELETE SET NULL` and losing it loses nothing (`plan_look.outfit_id`, #292, was one until `drizzle/0045_drop-plans.sql` dropped the plans, #337). `removeUnheldOutfits` locks the outfits (`FOR UPDATE`) before asking, so a holder being inserted meanwhile either committed first and is seen, or waits and fails on the deleted outfit's foreign key; never a silent cascade. `replace-entry.spec.ts` and `week-plan.spec.ts` hold a planner-made outfit on a trip through each of the three paths.
