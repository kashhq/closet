# Images

Every photo is a set of WebP files sharing one base name: `<uuid>.webp` (original, 1080px, q90), `<uuid>-nobg.webp` (the cutout, made by the server, padded to a transparent square; older photos keep the browser's), `<uuid>-thumb.webp` (400px, q80, from the cutout when present, then trimmed to the garment: Gotchas). Only the original has a `File` row, which also carries the cutout's state (see Background removal). **A cutout written onto an existing row** is a new nobg and thumb under a **variant key**, `<uuid>-nobg-<key>.webp` and `-thumb-<key>.webp` (`image-variant.ts`), and `file.variant_key` says which set is the photo's (null: the unkeyed ones); the original never changes. Serving and deleting need a `StoredPhoto` (`{ fileName, variantKey }`, `STORED_PHOTO_COLUMNS`); `unkeyedPhoto(name)` only for bytes without a row yet and selfies (never keyed: `file_variant_key_check`). `File.version` is bumped with every new key. A variant URL, `?v=<version>&k=<key>&s=<signature>` (`k` absent while unkeyed), names its exact files, so the `/file` routes (`src/web/files/routes.ts`) serve all three `private, immutable` for a year (Request security) and, when the signature holds, straight from storage (Gotchas, Signed URLs). Views never build `/file/...` by hand: `imageUrl(photo, 'thumb')` (a branded `SignablePhotoRef`, made only by `queries.ts`' photo-ref helpers: `photoRefJson`, `photoWithCutoutJson`, `plinthPhoto` (over `plinthPhotoJson`), `readPhotoRef` over `PHOTO_REF_RELATION`, `pendingPhotoRef`; each answers no photo once nothing of it is stored, `file.original_missing_since` (#653, Maintenance), so a page draws its placeholder; a positional tuple names the photo through `shownPhotoName`; writes find the photo by `photo_id`, never through them) (`src/web/files/image-url.ts`; grids, `loading="lazy"`) or `'nobg'` (detail, share, Open Graph). Missing thumbs are made on first request, single-flighted. Deletion always goes through `deleteVariants`. An outfit selfie is the same set without the cutout (`unwanted`), served under `/selfies/` by `selfieUrl`, never `/file/` (Outfit selfies); so is a saved look's photo, under `/inspiration/photo/` by `inspirationPhotoUrl` (Inspiration). Both go through `sendPrivatePhoto` (`private-photo.ts`); a look's photo to a device token through `servePrivatePhoto` (`GET /api/v1/look-photos/*`, a problem 404).

All of it is `Photos` (`src/web/files/photos.ts`) over `PhotoStorage` (`storage.ts`: a flat directory, `DATA_PATH`, the only storage; atomic writes through `.incoming/`). One instance per process, built by `createPhotos()`, so everything in the server shares its thumb single-flight map (`createApp()` builds it with `photosConfig()` for `webPlugin` (`photos`) and `server.ts`; the reconcile CLI builds its own). Uploads (`storeUpload`, and `storeUploadParts` for the garment form's multipart: its `photo` part, every other part drained unread; both adapt `storeImage`, over any `ImageSource` stream) and copies (`copy`) write bytes only and return the `file` row to insert (`NewPhotoRow`) (Gotchas: the commit contract). `pendingPhotoRow` builds that row for a pending photo stored earlier, and `preview` makes a small WebP in memory, never stored (link import's choices); `inputPixels` budgets its decodes from the header (sharp's only: link import's sources are `fetched`, never decoded as HEIC). A photo stored before its garment form is saved is a **pending photo**: bytes plus a `pending_photo` row (`src/web/files/pending-photos.ts`), kept only through `keepPendingPhoto` (`src/web/wardrobe/writes.ts`: the row; bytes deleted if it fails), at most `MAX_PENDING_PER_USER` (10) unbatched ones a user (another evicts their oldest); a library pick of several is a batch of drafts (`batch_id`, `batch_position`, `batch_owner_id`), never evicted and capped at `MAX_DRAFTS_PER_USER` (30) by refusing the upload (`recordDraftBatch`; Wardrobe, `drafts-and-export.md`); only that user may claim it (the save deletes the row in the transaction inserting the `file` row) or discard it; reconciliation removes day-old ones (a draft: week-old, `DRAFT_LIFETIME_MS`; `pendingCutoffs`/`isAgedPending`, the one rule) outside its guard, and account deletion removes a user's with their photos. A cutout of an existing photo (`saveEditedCutout`, the mask editor; `saveModelCutout`, the server job) is stored by `writeCutout` under a new variant key before any transaction; the row points at it only if the cutout state machine accepts it. **Rotating** a garment photo (`rotateStored`) never modifies the original: it streams it through `storeImage` with `rotate` (a quarter turn after `autoOrient`) into a new unkeyed photo, and with `withCutout` (an `edited` cutout, a mask) turns the row's cutout into the new set's unkeyed nobg, the thumb from it; any other cutout is re-made (the new row is `pending`). The caller swaps it in like an upload (`rotateGarmentPhoto`, `src/web/wardrobe/writes.ts`; a 409 if the photo changed since read). `cutoutInput` and `composeCutout` hold the server cutout's image rules. Failures are `HttpError`s (400, 413, 404).

**Every decode is bounded by `MAX_INPUT_PIXELS`** (64 MP, `photos.ts`): sharp pipelines are only built through `decoder()` (`limitInputPixels`, refusing from the header, before any pixel), and a HEIC's dimensions are checked before heic-decode allocates. sharp's default (~268 MP) lets a few KB of PNG or HEIC claim a gigabyte. A new sharp call goes through `decoder()` or passes the limit; `writes.spec.ts` uploads such a bomb.

## Layout

`photos.ts` (Photos), `storage.ts` (PhotoStorage, the disk), `storage-identity.ts` (claimStorage: the `.closet-storage` marker, Gotchas), `queries.ts`, `pending-photos.ts`, `routes.ts` (`/file/**`), `image-variant.ts` (names), `image-url.ts` (the one URL builder), `references.ts` (what references a file row; which are private), `private-photo.ts` (`sendPrivatePhoto`: the owner-only image routes' one answer), `heic.ts` (the HEIC upload: buffering, the answers), `heic-decoder.ts` + `heic-worker.ts` (the decoding thread, Gotchas).

## Gotchas

- **Photo bytes are written before any row, and rows commit together.** `Photos.storeUpload` / `copy` write the files and return a `NewPhotoRow` without inserting it; the caller inserts it with `insertPhotoRow(tx, row)` inside the transaction that points a garment at it and calls `deleteVariants` if that fails (`commitWithPhoto`, `src/web/wardrobe/writes.ts`); removals delete the row in the transaction and unlink after commit. Nothing in `src/web/files` inserts or deletes a `file` row; it only changes `version` and the cutout columns, through `applyCutoutEvent`.
- **The DB cascade deletes rows, never bytes.** `deleteRule: 'cascade'` on `File.createdBy` and `Garment.owner` drops the rows when a user goes, but only `Photos.deleteVariants` removes the files. Every path removing a `file` row (`removeGarment`, photo replacement, `POST /auth/delete-account`) must unlink through `Photos` after commit; account deletion also deletes the user's `pending_photo` rows in its transaction and unlinks those bytes; **a photo's `file` row is its showing row's owner's** (`created_by_id` = the garment's, selfie's or look's `owner_id`, whoever uploaded: a MANAGE grantee's upload is the owner's), held by the foreign keys `(photo_id, owner_id)` to `file (id, created_by_id)` (#703; garment's `ON DELETE SET NULL ("photo_id")` is hand-written in drizzle/0065), so a writer passes the wardrobe's owner to `Photos`; `reconcileStorage` (`src/maintenance/reconcile.ts`, `npm run maintenance:reconcile`) is the backstop for day-old unreferenced sets and rows. Outfits own no files; **a calendar entry owns its outfit selfie**: deleting the entry deletes the selfie's `file` row in its transaction and unlinks after commit (`removeEntry`); deleting the outfit keeps the selfie as a look (`selfie.outfit_calendar_id` set null). **What "references" a photo is one list, `photoIsReferenced`** (`src/web/files/references.ts`: `garment.photo_id`, `selfie.photo_id` and `inspiration.photo_id`): a new table with a photo column must join it, or reconciliation deletes its photos the next night (`reconcile.spec.ts` proves selfies survive).
- **A cutout's thumb is trimmed to the garment; the stored cutout never is** (#373). `cutoutThumb` crops to `contentBox` (alpha above 24, a 5% margin; under 0.5% of the frame keeps the whole frame), pads it to a centred transparent square and resizes to exactly 400 px, so every tile shows its garment at one size. Every thumb made from a cutout goes through it (`writeThumb`, `cutoutFiles` for `writeCutout`); an original's thumb stays whole. The nobg keeps the original's frame: it is the mask editor's master (`mask-editor.js` pads the original the same way to restore from it), so trimming it would misalign the restore brush. Changing the trim needs `npm run maintenance:retrim-thumbs` (Maintenance): a thumb is served immutable, so it moves to a new key, never rewritten in place.
- **Every stored image honours EXIF orientation**: `storeImage` builds one `decoder(raw).autoOrient()` for both the photo and the `alphaIsCutout` art path (`photos.spec.ts`). The browser side is `photo-input.js`'s `imageOrientation: 'from-image'`.
- **HEIC uploads are buffered.** sharp's libvips has no HEIC decoder, so `image/heic`, `image/heif` and an `application/octet-stream` named `.heic`/`.heif` are read whole (capped by `MAX_HEIC_BYTES`, 413 past it), checked against `MAX_INPUT_PIXELS`, and decoded by heic-decode to RGBA sharp reads as `raw`. libheif applies the container's rotation and raw pixels carry no EXIF, so HEIC photos are stored as decoded. Chrome/Android cannot decode HEIC in a canvas: `photo-input.js` sends it untouched. Only an upload is HEIC: an `ImageSource` marked `fetched` (link import) never is, whatever its type or name, and the outbound fetcher refuses `image/heic` and `image/heif` (#699).
- **HEIC is decoded on one worker thread, never the event loop** (#699): a 50 MP decode is seconds of WASM and ~256 MB of RGBA, which inline stalled every user. `HeicDecoder` (`heic-decoder.ts`, one per `Photos`, built by `createPhotos`) runs `heic-worker.ts` on one thread, one decode at a time in arrival order: the pixel check and `decode()` happen there, the RGBA comes back transferred. Its bounds: at most `HEIC_MAX_WAITING` (4) queued behind the one running, checked before the bytes are buffered (a fifth is a 503 `SERVER_BUSY` with `Retry-After`, holding nothing) and again once they are; an upload still sending holds no place, so slow bodies cannot shut others out; one deadline per decode from when it joins the queue, `HEIC_DEADLINE_MS` (30 s, wait and decode together): past it a waiting decode is dropped and a running one's thread terminated (`terminate()` interrupts WASM), answered as the same 503 `SERVER_BUSY` as a full queue (`heicBusy`, `heic.ts`: a deadline is load, the 64 MP pixel cap already bounds a hostile file), never the permanent bad-photo 400 that a crashed thread or undecodable bytes get; the next decode starts a fresh thread. `resourceLimits` caps the thread's JS heap (256 MB), not libheif's WASM memory (external, capped at 2 GB by libheif-js): the pixel check is that bound. The thread starts on first use, exits after a minute idle (the WASM heap never shrinks) and is `unref`'d then, so a CLI exits without closing it; `Photos.close()` terminates it at onClose (`HEIC_DECODER_STOP_MS`, `src/shutdown-budget.ts`). The worker imports nothing from `src/` at runtime: from `src/` it runs under type stripping (as the cutout's `child.ts`), `--disable-warning=MODULE_TYPELESS_PACKAGE_JSON` in its `execArgv`. Specs steer a stub thread by the uploaded bytes (`test/support/heic-stub-worker.ts`: `block:<ms>`, `hang`, `crash`, `oom`; `createTestApp`'s `heicDecoder`): `heic-decoder.spec.ts` (the thread's rules, the real worker on `example.heic`), `test/integration/heic-thread.spec.ts` (`/health/live` under 100 ms mid-decode, the bad-photo answers, no HEIC from a link).
- **Abandoned pending photos must never reach reconciliation's guard.** An unsaved link import or add-sheet upload leaves bytes without a `file` row. The guard refuses a whole run past 25 unexplained photo sets (or a fifth of them), which one person browsing without saving passes in a day, and then nothing is cleaned. So every stored pending photo has a `pending_photo` row: reconciliation deletes day-old ones (row and bytes) in its own pass, reports them as `pendingPhotosDeleted` apart from the guard's count, leaves younger ones out of the plan, and deletes pending rows whose bytes are gone (`pendingRowsWithoutFiles`). A new feature that stores bytes ahead of their `file` row keeps them through `keepPendingPhoto`, or it jams the nightly clean-up. The form field stays `linkPhoto` whatever the source: installed apps' cached forms post it. Its cutout is queued when the save inserts its `file` row.
- **`/file/**` serves from `DATA_PATH`, which holds only photos (the log is stdout; a `LOG_FILE` may never sit there).** The route accepts only a photo base name as `parseStoredName` defines it (the rule reconciliation uses); a looser regex once served `/file/app.log` (the request log, then written there), session cookies included. Never add a second definition of a stored name. `test/integration/file-route.spec.ts` covers it. Its refusals (a name that is no stored photo, a private photo's name, an unknown share id, bytes missing from storage) are `NotServed` (`src/web/refusals.ts`: the bare status text, no resource named, the body these public routes always answered), never `NotFound`: no actor asked; guards.conf `@not-served` lists the sites. **Public by name is only for photos a share may show**: an outfit selfie's or a saved look's name is a 404 there (`publicPhoto`, `references.ts`, which also answers the row's variant key in the same statement) and its share id makes no preview; a new kind of private photo gets its own session-checked route (`/selfies/\*`), joins `publicPhoto`'s refusal and gets a photo type `imageUrl` does not take (as `PrivatePhoto`), or a signed URL serves it to anyone.
- **Signed URLs: a photo request costs no statement** (per-image row reads made a cold grid 48 statements). `imageUrl` signs (HMAC-SHA256, 96 bits, keyed from `ACCESS_TOKEN_SECRET` by `configurePhotoUrls` in `createApp`) the name, variant key and version, not the variant, so a photo's three URLs differ only in path. The route (`signedPhoto`) opens exactly that set's file (`openStoredVariant`: no fallback, no thumb made under a possibly retired key); a missing file or an unsigned, altered or other-secret URL goes to the row (`publicPhoto`), which serves the current set and makes a missing thumb; `photo_requests_total{lookup}` counts both. Safe because **only garment and pending photos reach `imageUrl`**: it takes a branded `SignablePhotoRef`; `photo-ref-guard.spec.ts` fails if `src/web/selfies` touches a maker or anything outside `queries.ts` asserts the brand; the fast path does no selfie check, so a new maker must never read a selfie's row, a name never changes kind (a selfie always gets a fresh row), and a keyed file is never rewritten, so a signed URL only serves what its page showed; after a swap, rotate or delete the row answers. A client never builds or edits a `/file` URL. Rotating `ACCESS_TOKEN_SECRET` only routes old URLs via the row. Never log a `/file` URL's query: `s=` spares a lookup. **Revocation is unchanged**: a garment photo's URL is a capability; unsharing ends the pages showing it, only deleting the photo ends its URLs.
- **DATA_PATH's identity is its `.closet-storage` marker, never its contents** (#650). A bare mountpoint (NFS not mounted) is writable and empty, so it read as "every photo gone": reconciliation deleted the pending rows and uploads landed where the remount hid them. `createPhotos` (every process: the server and each CLI) runs `claimStorage`: a marker present is claimed; absent, it is written only when the `file` table is empty (first boot) or the directory holds the sets of at least `ADOPT_MIN_COVERAGE` (90%) of the rows (adopting a pre-marker share: a mountpoint's stray uploads never reach it); anything else, or a marker that cannot be read, throws `StorageIdentityError` (main.ts and `runCli` log its line alone). It is created exclusively (temp file, then `link`, EEXIST adopts the marker another booting process linked first), never renamed over one. **The marker must be the database's** (#833): the one-row `install` table holds its install id, written by the claim that writes or adopts it (or, with no row yet, from the marker found); a marker with another id is `unpaired`, refused only with `APP_ENV=production` (`InstallPairing`, `photosConfig`; elsewhere one warn line: worktrees share pgvault-dev), and a marker written over an unmarked share takes the row's id, settled before the write: an unpaired database is paired first, so a claim that loses that race writes the winner's id, never a marker its database refuses (#851). Only `--repair-storage-identity --confirm` (Maintenance) changes the row. `PhotoStorage.identityProblem()` re-reads the marker against the claimed id, in memory, and never rejects for the disk's sake: `/health/ready`'s `storage` check asks only it (never a statement, so database health stays its own check); reconciliation asks `storageIdentityProblem`, which adds the row in production. `list()` skips the marker (and directories: `.incoming`, reconciliation's `.trash`) and `parseStoredName` refuses it, so `/file/**` never serves it. Never write the marker anywhere else. `test/integration/storage-marker.spec.ts`; operator side: `docs/operations.md#photo-storage-marker`.
- **`PhotoStorage.store` must be atomic.** A variant is read while another write may replace it; storage writes to `DATA_PATH/.incoming/` and renames, so no reader sees a half-written file. Boot removes `.incoming` entries older than an hour, never fresh ones (the reconcile CLI may boot beside a live server). A cutout of an existing photo never overwrites a served name: it stores a new keyed set and the row swaps to it (writeCutout).
- **No storage I/O inside a server-pool transaction.** The pool ends idle-in-transaction sessions, photos are on NFS, and a rename cannot roll back. Store first, commit the row, unlink after (the commit contract above); check a file's existence before the transaction (`createGarmentWithPendingPhoto` asks `pendingPhotoRow` first: only whoever took the pending row deletes its bytes). **Deleting a row-backed photo needs its variant key**: every query that deletes a `file` row takes `STORED_PHOTO_COLUMNS` from the DELETE itself (`.returning`: an earlier read may miss a cutout swap) for `deleteVariants` (original, unkeyed pair, keyed pair); reconciliation quarantines orphaned sets by the names it scanned (`.trash/<day>/`, Maintenance) and a live photo's day-old variants under another key older than the row's own set (`supersededVariantsDeleted`, counted by its guard; a newer set is kept: Maintenance).
- **Pipelines started inside a multipart `for await` loop must be armed with a no-op catch at creation.** `Photos.storeUploadParts` starts the photo's pipeline without awaiting it (an unconsumed part hangs busboy; later parts, like `nobgPhoto`, are drained) and the caller awaits it after the loop; a rejection while later parts are read would be an unhandled rejection that exits the process. `startPipeline()` attaches the catch and returns the same promise, so the real error still surfaces from the await. `test/integration/heic.spec.ts` records `unhandledRejection` and checks the app still answers. Node's default (crash loudly) is kept on purpose; do not add an `unhandledRejection` handler (main.ts's `uncaughtException` one reports and exits 1; see Metrics). A body refused after that start (the file cut at `fileSize`, reported once its stream ends, after a JPEG decoded) throws from the loop: the catch deletes what the pipeline stored, or it outlives the 413.
- **The shared photo viewer** (#313; `photo-viewer.tsx`, `public/js/photo-viewer.js`, `.photo-viewer-*` in `main.css`): tap a photo, see it at its best stored resolution (`nobg`, or `original` where no cutout shows), swipe or step through its set, zoom. The server renders the set as a `<template data-photo-set="id">` (`PhotoSet`: the large `src` and the thumb as `data-fallback`; inert, so nothing is fetched until it opens) and each opener carries `viewerTrigger(setId, photo)` (`data-photo-open`, `data-photo-large`): a `<button>`, or an `<img role="button" tabindex="0">` inside a container that is not a control (a collage piece, `OutfitCollage`'s `viewerSet`). **Never nest a trigger in a link or button**: the plan card's is a sibling button over the photo. One `<dialog id="photo-viewer">` is in `Layout` and one document-level listener opens it, so htmx swaps need no re-binding. **Why a module**: `showModal` gives focus in and Esc, a scroll-snap row gives the swipe and `touch-action: pan-x pan-y pinch-zoom` the browser's own pinch; the module is only what neither does (prev/next buttons and arrows, zoom toggle: click, double tap, a button; swipe down to close; focus restored to the opener). A slide stays empty until its large image loads; the thumb the page already holds shows only when that fails (offline: an uncached cutout shows its thumb). Never the thumb as a placeholder: a cutout's is trimmed (#373), so the swap would shrink the garment. Set ids are unique per page. Wired into a Muse need's options (`need-options`), Muse's outfit cards and the garment page (`garment-photos`: cutout then original). The outfit view and shopping adopt it in their own slices. No history entry: Back leaves the page, as every dialog does here.
