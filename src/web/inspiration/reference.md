# Inspiration: reference

Moved out of `AGENTS.md` (#723) so the auto-loaded doc keeps only invariants, gotchas and ownership. Not auto-loaded: read it before changing this area. Where it disagrees with the code or a spec, they win.

- **Tables** (`drizzle/0049_inspiration.sql`): `inspiration` (`owner_id`, `title`, `note`, `source_url` http(s) only, `photo_id` unique and nullable, `ON DELETE CASCADE` from `file`; `inspiration_photo_or_link_check`: at least one of the two), `inspiration_piece` (`(inspiration_id, position)` key, `role` from `INSPIRATION_PIECE_ROLES`, `type`, `colors[]` (at most `INSPIRATION_PIECE_MAX_COLORS`), `pattern`, all checked against `src/wardrobe/properties.ts`; `matched_garment_id` `ON DELETE SET NULL`: the garment chosen for the piece, a closet garment its outfit was saved with or the wishlist item "Find this" made, written only by the match view's two writes (22c); a piece's edit clears it). Positions are never renumbered: a removal leaves a gap, and a position is never reused: `inspiration.next_piece_position` (`drizzle/0050`) only grows, an add takes from it under the look's row lock (`takePiecePositions`), so a stale match view's post is a 409, never another piece's choice; at most `INSPIRATION_MAX_PIECES` (12, a 400 past it).

- **The share target** (22d; `share-target.ts`, `share-confirm-page.tsx`, `public/js/share-confirm.js`, `src/web/shell/manifest.ts`; decisions 2026-11-13): a manifest has **one** `share_target`, so with `PWA_ENABLED` it is `POST /inspiration/share`, multipart (`photo`, `title`, `text`, `url`), for photos and links alike; without the worker it stays the link import's GET, links only. **A share never writes without a same-origin confirmation**: the service worker answers the POST navigation itself and **never sends it to the server** (`receiveShare`, the one navigation post the worker answers: `navigationPostAnswer`, Shell), because a cross-site page can auto-submit the same multipart form and the worker cannot tell it from Android's (no client id, no readable Origin): relaying it posted with our Origin and the cookie, a CSRF bypass. The first file declaring an `image/*` type is kept in Cache Storage (`shares-v1`, a session cache: one share at a time, a new one replacing it; at most `SHARE_PHOTO_MAX_BYTES`, 20 MB; gone after `SHARE_STASH_MAX_AGE_MS`, an hour) and the answer is a 303 to `GET /inspiration/share/confirm#<id>`, the id a fragment, so it never reaches the server or a log. That page (`FormPage`, no server state, its stash names in data attributes) has its module put the photo in a file input (`preparePhoto`), show it and enable **Save look**, a native multipart post to `POST /inspiration` like the add page's upload (same-origin, so the hook needs no exception; `fileSize` capped at `SHARE_PHOTO_MAX_BYTES`, a 413); the share's link (`linkIn`'s) and title are stashed beside the photo (`X-Shared-Url`, `X-Shared-Title`) and posted with it as `url` and `title` (`addUploadedInspiration`: a link not `^https?://` and parseable, a title past 255 or a field busboy cut is a 400, the stored bytes deleted). **Save look opens 800 ms after the preview decoded on a visible page** and refuses any click whose gesture began earlier (`public/js/click-gate.js`, `click-gate.spec.ts`), so a page cannot time a tap to its appearance; a share that cannot be read or decoded shows the missing state. Cancel deletes the share; Save only marks it in sessionStorage (`views/assets/page/share-saved.ts`) and **the look's page deletes it** (`forgetSavedShare`, inline in `show-page.tsx`), so a failed save keeps the photo for going back. **Without a controlling worker** (storage cleared, not yet installed) Android's post reaches `POST /inspiration/share` (`share-fallback.ts`), which **writes nothing**: a photo is a 303 to `confirm#not-opened` (open the app, share again; its bytes are never read), a link or text the same link page as the worker's (`linkPageFor`), nothing `#not-opened`; a body declared past `SHARE_BODY_MAX_BYTES` is a 413 unread. It is the same-origin hook's one `stateless` exemption (the OS's post has no Origin; see Request security); anything written there would be a CSRF hole. No photo is a 303 to `/wardrobe/new/from-link?url=<the link>` (`linkIn`, `link-text.ts`; or `?text=` cut to `LINK_INPUT_MAX`), which fetches nothing. A share while signed out lands on the login page and is lost (the sign-in drops the session caches, the stash with them); one while offline waits, the confirmation page (or the offline page at its address) reloading into it within the hour, Save disabled until the heartbeat answers. The same relay pattern on the auth posts is #542. Only a phone proves the share sheet.

- **Save as outfit and Find this** (22c; `recreate-writes.ts`, `addPieceToWishlist` in `queries.ts`, `piece-wishlist.ts`): the match view is **one native `PostForm`** to `POST /inspiration/:id/recreate/outfit`; each strip posts a `position` hidden input, then its own `garment` (the strip's input, '' for None), pairs in document order (unequal counts, a piece twice: 400). "Find this" on a missing piece is a submit button of the same form with `formaction` (`POST /inspiration/:id/pieces/:position/find`; forms cannot nest), so the form has no text field: Enter never picks it as the default button. **`saveRecreation`** is one owner transaction: `lockLookForSave` (the look `FOR UPDATE`, then **its own statement** for the pieces' roles: one joined statement would read them as they were before a waited-for edit; every piece write, `updateInspirationPiece` included, takes the same `lockOwnLook` lock), `pickIdea` (closet garments only, top to toe, **once per garment set**, so a double tap answers `?alreadySaved=1`; named after the look's title, else as an idea), then `recordPieceChoices` (one `UPDATE ... FROM (VALUES ...)` storing a garment only if it is the owner's and of the piece's `pieceCategory`). A choice for a piece the look no longer has, or of another kind, is a 409 (`LOOK_CHANGED`) rolling back the outfit too; a garment gone from the closet is pickIdea's `garmentsGoneError`; all None is a 400. 10 statements with the session. **`addPieceToWishlist`** (in `queries.ts`: only queries open a transaction, `make guard-check`'s own-tx): the piece row `FOR UPDATE`, then (its own statement, so it sees what a waiting twin committed) whether its match is already an own wishlist item, answered without a write; else `insertGarment` with status `wishlist` (`wishlistFieldsOf`: the role's category, the type as its name and its presets, the colours, the pattern where the category takes one, a note naming the look and its link) and the piece pointed at it. 6 statements. **Not the look's link as the item's product link** (the plan said so): a lookbook page is not where the piece is sold, and two pieces of one look would be one product to Muse's never-again rule. "Save with wishlist pieces" (plan §4) is not built: the outfit holds closet garments only.
- **Pages**: the list (`list-page.tsx`, one statement after the session's, newest first; a tile is the thumb in a 4:5 frame or, for a link alone, its site), the add page (`new-page.tsx`, `FormPage`: the photo buttons above, the link field its one post), the look's page (`show-page.tsx`: the photo or the buttons to add one, Change photo, the link in a new tab, title and note in an `AutosaveForm`, Delete with a confirm). Every write is a native `PostForm`, disabled offline.

- **API** (#193d; `api-routes.ts`, `look-resource.ts`, every route its page twin's writer, `operations.ts`): `GET/POST /looks` (the list paged by an id cursor, `listInspirations`' `page`; a multipart create, `addUploadedInspiration`, with `url`, `title`, `clientId`), `POST /looks/link-imports` (`addLinkedInspiration` under the page's checker; `unread` as the page's `?unread=`), `GET/PATCH/DELETE /looks/{id}` (a PATCH field left out is kept), `PUT .../photo`, `POST .../pieces`, `PUT .../pieces` (set_inspiration_pieces' `setInspirationPieces`), `PUT/DELETE .../pieces/{position}` (a removed position is a 404, never reused), `GET .../recreation` (`recreateOwnLook`), `POST .../outfits` (`saveRecreation`: 201, or 200 `alreadySaved`; a stale position 409) and `PUT .../pieces/{position}/wishlist-item` ("Find this": 201, or 200 `created: false`). A piece is `{ role, type, colors, pattern }`, a type of another role a 400 naming the role's (`typesOfRole`, MCP's too). **The photo's bytes have an API twin**, `GET /api/v1/look-photos/{fileName}?variant=` (`apiInspirationPhotoUrl`, `servePrivatePhoto`: a problem 404 for anyone else): the page's route reads the cookie, which no token request carries. No empty look: `inspiration_photo_or_link_check` wants a photo or a link. The share target stays web-only (the worker answers it).
