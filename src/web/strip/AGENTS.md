# Snap strip

`src/web/strip/snap-strip.tsx` and `public/js/snap-strip.js` (#270, epic #268): the scroll-snap carousel whose centred item, with its neighbours peeking, is the choice. Extracted from Styling's rows; Ideas, Today, Goes-with's best outfits and a Muse need's options use it too.

- **The component**: `<SnapStrip name? value? size label listbox? focusable? class? attributes? >items</SnapStrip>` (`tapThrough`: on a `listbox={false}` strip a click on a tile's button or link is left alone instead of centring a neighbour, Ideas and Today; each size also names its `gap`, Ideas' is 4; `attributes`: an `id` or `data-*` on the strip; `<SnapStripsInit />` is the inline init a page without its own hooks module renders) renders a `relative` frame (`snap-strip-frame`) holding the strip (`role="listbox"`, `data-snap-strip`, the snap classes) and, when given a `name`, right after it the hidden `<input name value>` the choice is written into. **The contract:** that input is always the strip's `nextElementSibling` (the observer writes to it when the next sibling is a hidden input, else nothing: a strip without `name` still marks `data-selected`, as Goes-with's does), so any number of strips can share one container and each writes its own input. **`listbox={false}`** (with `snapItem({ listbox: false })`) is for a strip that is not a choice and whose tiles hold links: `role="group"`, no `option` role or `aria-selected`, which would make the links presentational to screen readers (#272; Ideas, Today, Goes-with). `snapItem({ value, selected, size, class? })` returns an item's attributes to spread on its element (`data-snap-item`, `data-snap-value`, `role="option"`, `data-selected` / `aria-selected`, snap-centred, `snap-always`, the size's width, `group/item` so children style off `data-selected`). The page owns the element, its look and any other state.
- **`size`** (`regular` w-28, `small` w-20 and `roomy` w-28, both w-40 from `lg` so a Styling page has one tile size and origin there (#732); `page`, `peek` and `pair` (Goes-with's, w-11/12), an idea card: `w-full` / `w-[85%]` on a phone, w-72 from `lg`, Ideas and Today, #321, and no spacers on a phone, so the first card sits flush left; `options`, a Muse need's option cards, #333: `w-[85%]` on a phone like `peek`, and from `lg` no strip at all, every item a `flex-1` column side by side, nothing scrolling and the step buttons hidden, through a size's own `strip` and `frame` classes) fixes the item width and the strip's end spacers together; see the comment on `SIZES` and Styling's #179 gotcha (spacers, not padding, for WebKit). Widths are whole class strings so Tailwind sees them.
- **The observer**: an IntersectionObserver per strip, rooted on it with `rootMargin: 0px -50% 0px -50%` (a zero-width line down the middle), writes the crossing item's `data-snap-value` into the strip's input and moves `data-selected` / `aria-selected`. It centres the `data-selected` item once when it first watches a strip. **With a mouse (#311)**: the frame also holds two `data-snap-step` buttons (previous/next, `aria-label`s `strip.PREVIOUS`/`NEXT`) after the input, shown only by the `fine` variant (`@media (hover: hover) and (pointer: fine)`, `main.css`): one markup, no UA sniffing. They and the ArrowLeft/ArrowRight keys (a document `keydown` when focus is in a strip, not in a field) centre the item beside the chosen one, so the choice moves through the observer and `snap-strip:choose` like a swipe. Steps count from `heading` (the item a step's smooth scroll is going to, until `scrollend`), else the chosen item: `position()` is the one place both the steps and the buttons read. A keyboard step from a focused item moves focus to its target **at keydown**, never later (#469): Enter or a held key's repeat acts on where the strip is going, and nothing pulls focus back from where the user went meanwhile; Enter on a target still in flight only centres it. The buttons render disabled and `syncSteps` enables each that has a non-inert item to go to (an end or a locked Styling row's neighbour stays disabled; styling.js re-syncs on a lock). Disabled is `aria-disabled` + `aria-disabled:btn-disabled`, never the attribute: a disabled button drops its focus to `<body>` (a key held on Next did at the end). Copy never names the gesture ("swipe"). Proven in `test/styling.spec.ts` (keys dispatched in one task, so the scroll is in flight) and `test/integration/styling.spec.ts` (rendered disabled). **No touch or wheel handlers** (`test/styling.spec.ts` checks the app has none). A capture-phase document click centres a tapped neighbour (an item may be a boosted link whose htmx handler would otherwise navigate first); the chosen item's tap reaches the item.
- **Wiring**: `initSnapStrips(root)` from `'snap-strip'` (importmap, `layout.tsx`), called by the page's inline module on every visit (a boosted navigation brings new strips; a `<script src>` module runs once). `htmx:load` covers strips swapped in later, a strip's next page and history restores. Calling it twice is harmless.
- **Hooks for a page's own rules** (document listeners, nothing else): `snap-strip:choose` is cancelable, fires on the strip before an item is chosen (`detail.item`); cancelling leaves the choice as it is. `snap-strip:chosen` (#468) is not, fires on the strip once `data-selected` has moved (`detail.item`), also when the item was already chosen (a strip's first watch), so a listener must be idempotent. `snap-strip:watch` fires on the strip after each (re)scan. Styling's locks use `choose` and `watch`, its preview `chosen` (`public/js/styling.js`).
- **A page landing before the chosen item keeps it in place** (#996): `htmx:beforeSwap` inside a strip records where its `data-selected` item sits in the viewport and the same task's `htmx:afterSwap` scrolls it back, before the browser lays it out, so a strip loading backwards (Styling's newer garments) never chooses whatever slid into the middle. Never at `htmx:load`: htmx fires it after its settle delay, and the observer chose in that gap. `htmx:afterRequest` drops the anchor whatever the answer (an empty page fires no afterSwap), and the observer chooses nothing while one is pending. A page arriving while the strip scrolls (`scroll` until `scrollend`, or 150 ms quiet without it, or a step in flight) is held and swapped in by `htmx.swap` when it stops: the instant scroll back would cut a fling short. A page after the chosen item moves nothing and is never held. Proven in `test/styling.spec.ts` (the response held by `page.route`).
- **Not here**: locks, `inert`, paging, "No garment", what an item looks like. A new user supplies its item element and (if it has rules) a hooks module like styling.js.
