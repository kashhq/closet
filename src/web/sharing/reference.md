# Sharing: reference

Moved out of `AGENTS.md` (#680) so the auto-loaded doc keeps only invariants, gotchas and ownership. Not auto-loaded: read it before changing this area. Where it disagrees with the code or a spec, they win.

- **Invites expire and are credentials** (#668): an unanswered invite lives `INVITE_LIFETIME_MS` (7 days) from `created_at`, derived, no column; `created_at` is stamped from the app's clock and every check compares it with `inviteCutoff(now)`, never Postgres `now()`, so the clock shift moves both. `acceptInvite` refuses `expired` on its read and carries the same cutoff in the write's `unanswered` guard (expired in between: `not-found`); `findInvite` returns `expired` (the landing says so, no Accept); `sharesOf` marks it (listed, no link, Revoke kept). An edit link asks for the password (Auth, step-up rule); `createInvite` is one insert-select under the grantor's row lock against the session's stamp (`sessionStillOpenSql`: fingerprint and session version; `upsertDevice`'s shape; `wardrobe_share` is not synced, so no owner lock), and a new password deletes the user's unanswered invites (`revokeOpenInvitesStatement`, in `updatePasswordHash`'s revocation statement). Accepted shares never expire. Fixtures that only need a share mint through `createInvite(db, id, role)` (no session): an edit link through the route needs the password and draws on `INVITE_LIMIT`.

- **Price and notes, the `private` capability** (#680, owner decision 2026-11-25; `docs/decisions.md` 2026-11-27): OWN and MANAGE read them, VIEW never. `src/web/wardrobe/private-fields.ts` is the one file that names `garment.price` and `garment.notes` (`guards.conf @garment-private`; a row's fields are read under another name, `summary.price` or destructured): `privateColumns(role)` for a select (both, or neither; `'OWN'` for an owner-only reader: insights, the wear line, Muse's feedback and outfits), `priceJsonPair(role)` for a `json_build_object` (the Muse inbox's picks and own items, `wishlist/inbox.ts`), `privateColumnsWhere(managesWardrobeSql(...))` for the feed's batched `garmentsByIds` (null on a VIEW row, which `asResource` leaves out). The share-aware readers take a `WardrobeRead` (`{ ownerId, role }`, a `GrantedAccess` is one): `findGarment` (the garment page, API `GET /garments/{id}`, MCP `get_garment`, the clone's source, so a VIEW clone starts without them), `garmentSummaries` (API `GET /garments`, `search_garments`, `get_wardrobe`, `get_capsule`, `compare_with_shared_wardrobe`), `wishlistItems` (`list_wishlist`), `readInbox` / `readNeed` / `suggestionContextSql` (the wishlist page and API, a need, a suggestion's garment page) and `gridWhere` / `gridOrder` (the keyword: `keywordMatch` takes the notes column or none, and a search without them is unranked). Cost per wear, insights and the repair cost were already the owner's (`own` records). The feed resends a wardrobe whose grant changed (`g`, #959), so a share lowered to VIEW resends its garments without them. Specs: `share.spec.ts` (price and notes: every surface for OWN, MANAGE and VIEW, the keyword, the clone), `api-changes.spec.ts` (the downgrade), `repair-cost.spec.ts` (a VIEW `get_garment` has no price).
