# Sharing (`/wardrobe-share/*`, the access resolver)

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds the invites' lifetime and writes, and the private fields' readers.

- **One resolver:** `resolveWardrobeAccess` / `authorizeWardrobe` (`access.ts`) decide whose wardrobe a request addresses (`?ownerId=`, `''` or absent for your own) and what the caller may do there: its `role` (`OWN`, `MANAGE`, `VIEW`) and what `CAPABILITIES` grants it (`can(role, …)`: `view`, `manage`, `launder`, `private`, `own`; #680), a call's need being one; `managesWardrobeSql` is its SQL form for a batched read (`share.spec.ts` holds them equal). Share-aware pages and MCP tools go through it (MCP via `wardrobeFor`, `mcp/tool.ts`); a route plugin binds `wardrobeGuard(db, <the resource an unseen wardrobe reads as>)` once (`garmentGuard` for the garment routes) and calls `authorize(request, need)`, which reads `?ownerId=` itself, so no route relays `request.query.ownerId` or re-declares the wrapper (2026-10-27); never re-derive access from `sessionUserId` plus a share lookup.
- **`Actor`** (#188): `{ userId, surface, shareReadAhead?, ownWardrobeOnly? }`, what a domain function takes instead of a request; `actorOf(request)` (here: the session user and the share read ahead, so the statement counts hold; `surface` from `surfaceOf`, `page` or `api`) and `actorOf(ctx)` (`mcp/tool.ts`: the token's user, `surface: 'mcp'`, `ownWardrobeOnly` for an own-wardrobe-only agent token, #701). `surface` is only what an action's log line names (`logOp`, #712), never an access input. The resolver is that scope's one check: another wardrobe is unseen without a share read, `sharedWardrobesOf(db, actor)` lists none; a share reader that skips the actor (`sharedWardrobesSql`, the switchers' subquery) is for sessions only. Refusals are `NotFound` / `Forbidden` (`src/web/refusals.ts`). `authorizeWardrobe(db, actor, ownerId, need, unseen)` takes an `Actor` (#188b) and throws them itself: `NotFound(unseen)` without a view, `Forbidden()` without the need; nothing in it sees a `FastifyRequest`.
- **The access check costs no round trip of its own** (#170): a request whose `?ownerId=` is a plain row id naming another user's wardrobe reads that share inside the session's statement (`shareToReadAhead` and `sharePermissionSql`, called by `findSessionAccount`; stored per request by `rememberShareReadAhead`, only for a cookie that opened a session). A page's actor (`actorOf(request)`, what `wardrobeGuard` builds) carries the share read ahead, which `authorizeWardrobe` uses when its owner id matches and otherwise reads the share itself (a body's `ownerId`, `?ownerId=05`, the MCP tools, whose actor has none). Nothing is cached past the request, so a revoked share stops access on the next one. An `/api/v1` request reads it the same way in the device token's statement (`authenticateToken`'s `shareOf`, `src/web/api/token-auth.ts`), and `actorOf(request)` takes the token's user there. Build the actor with `actorOf(request)`, never `{ userId: sessionUserId(request) }`: that still works but pays the lookup again. A repeated `?ownerId=` parses as an array: never read ahead, and a 400. **Layering**: `auth/queries.ts` imports `sharePermissionSql` from `sharing/access.ts`, and `sharing/access.ts` imports only `auth/require-session.ts` (`sessionUserId`), `refusals.ts`, `schemas.ts`, `surface.ts` and `share-aware.ts` of the web layer; `access.ts` must never import `auth/queries.ts` or `auth/session.ts`, or the modules form a cycle. `sharing-statements.spec.ts` pins each grantee page's count (the grid, garment page, wishlist and Styling 3, capsules 2) and the invite and Profile counts below.
- **Invites expire and are credentials** (#668, 7 days, the app's clock, never Postgres `now()`; an edit link asks for the password): `reference.md`.
- **Price and notes are `private`** (#680): never a VIEW grantee's, on any surface, absent (never null); a VIEW keyword search never matches the notes. Their columns are named only in `wardrobe/private-fields.ts` (`privateColumns(role)`; `guards.conf @garment-private`): a new garment reader asks by role. Readers and specs: `reference.md`.
- **Which surfaces are share-aware** (take `?ownerId=` and serve a grantee): the wardrobe grid and garment pages (link import included), the wishlist, capsules, Styling, wears and the laundry (`launder` for MANAGE, #680; `reference.md`), the MCP tools that address a wardrobe, and the changes feed's garments and capsules (every accepted share, through the cursor, never `?ownerId=`; `src/web/sync/AGENTS.md`).
- **Share-aware is exactly a querystring declaring `ownerId`** (`OwnerQuery`; `share-aware.ts`, #680): the root onRoute hook `markShareAware` stamps `config.shareAware` (by hand: the boot stops); only those read a share ahead; the root session hook answers any other signed-in page a foreign `?ownerId=` `NotFound('wardrobe')`, reading nothing more, never one's own data under another's address. `authorization-coverage.spec.ts` probes each.
- **Owner-only by design** (the session's user; a foreign `?ownerId=` 404s): saved outfits (`/outfits`: every query scoped to the signed-in user), the style profile, the calendar (week and month), Ideas/gallery, insights and the year in review (`/wardrobe/recap`, #26: wear data never reaches a grantee; the menu offers it only on one's own wardrobe), trips, Today, the weekly auto-plan, selfies, saved looks (`/inspiration`, #22), sizes, and Profile. The wardrobe export (#200, `/wardrobe/export.*`) is owner-only too, but through the resolver: `?ownerId=` of a shared wardrobe is a 403 even for MANAGE, since it hands over the whole wardrobe with the owner's own records.
- **A new feature decides which list it joins, and says so here.** Don't copy a sibling's route shape without checking: a share-aware sibling routes through the resolver, and an owner-only one reads `sessionUserId` alone.
- **API** (#195c, `api-routes.ts`): only `GET /api/v1/shared-wardrobes` (`sharedWardrobesOf`, accepted shares, `ownerId`, `ownerFirstName` from `grantorFirstName`, never `grantorName`: no API answer carries an email). Invites, accept, decline and remove are web-only (`SHARING_ADMIN`, `operations.ts`; decisions 2026-11-13).
- **A public link is a state of the garment or outfit** (#669, decisions 2026-11-14): `shareable_id` is null until Share is tapped and null again after Stop sharing (0073 stopped every id minted before, #964); `setPublicShare` (`share/queries.ts`) is the one writer for both, one UPDATE under the owner lock (`coalesce`, so racing taps answer one id; a Share after a Stop a new one). A garment's Share and Stop are owner and MANAGE (a grantee's link shows on the owner's page with Stop after the grant ends), an outfit's the owner's. `/share` and `/file/watermark/:id` (keyed by the item's id, never a photo's; `findPhotoByShareableId` repeats `findSharedOutfit`'s first-photo rule) are a 404 for anything not shared. The API's twins (#959) are `PUT`/`DELETE .../share` on garments and outfits, the same writers; `publicShareUrl` (`share/urls.ts`, absolute on SITE_URL) is shown only to whoever may stop it, never a VIEW grantee (the feed's `managesWardrobeSql`), and never to MCP.
- Sharing is managed on its own page, Profile › Sharing (`GET /auth/profile/sharing`, `SHARING_PATH`, `SharingPage`; a Profile section until #728, whose row keeps the `sharing` anchor), where every write lands and a refused accept shows its `?shareError=`; `GET /wardrobe-share/manage` 301s there (R2 #82). Profile reads `sharesOf` too, for its row's summary and the new password's notice. The public share-link page is `share/`, not this directory.
