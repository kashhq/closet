**Pending migrations run in one transaction, all files together** (drizzle-orm's migrator). A failed batch leaves nothing behind, and `CREATE INDEX CONCURRENTLY` cannot run inside it. The tables are household-sized, so a plain `CREATE INDEX` holds its write lock for milliseconds; if a table ever grows to where that matters, build the index in a non-transactional step added to `runMigrations` after `migrate()` (under the same lock), not in a migration file.

## The owner lock's statement (#196a)

- **Every write to a synced table takes its owner's lock before any other row lock** (Calendar's Owner lock, extended): the roots and children of `docs/plans/2026-11-12-json-api.md` §7, listed in `src/db/sync-tables.ts` (garments, outfits and slots, entries, wears, selfies, capsules and members, trips and their rows, the week plan and template, sizes, the style profile and its outfit rules, measurements, a garment's photo row). The sync triggers bump the owner's revision with an UPDATE of the user row from inside the write, after the row is locked; a writer that held a garment, trip or photo row first would deadlock with one that holds the owner and waits for that row (`pickIdea`, `deleteOutfit`'s cascade into a trip, `swapPhoto`). Rows outside the synced tables count too when the owner's holder deletes them: every taker of a pending row (a garment's or a look's save, a discard) takes the owner before the photo name and the row (`lockOwnersAndPhotoName`, the only way to lock a name), as account deletion does.
- **One global order: every account a transaction writes rows of, locked in one statement, ascending, before any other lock** (#544). A MANAGE grantee's save of their pending photo writes the uploader's pending row and the owner's garment and `file` row, so it locks both (`lockOwnersAndPhotoName(tx, [ownerId, userId], name)`); account deletion locks only itself: no other wardrobe shows its photo rows (the photo foreign keys pair `photo_id` with `owner_id`, #703). A transaction taking several never takes one first and the others after: holding 5 while waiting on 3 deadlocks a save holding 3 and waiting on 5. A multi-account lock is true only when **every** account was locked (one gone is a refusal, not an unlocked write). Why no pair deadlocks: every owner-lock wait is in a first statement, and after it each writer only waits on rows of accounts it holds.
- **The mark is set only once the row is held.** The statement sets `closet.locked_owners` (SET LOCAL) in a select above its LockRows, over the row returned, never in the scan below it where `lock_timeout` must sit. The sync triggers raise `owner lock not held: a write to <table> for owner <id>` on a synced write in a transaction without the owner's mark (an owner that no longer exists passes: its cascade), so every tier proves every writer; spec fixtures write through `asFixture` (`test/integration/harness.ts`). It catches a writer that forgot the lock, not one that sets the mark by hand: forgetfulness, not malice.

## The sync triggers (#196a-2)

- **One revision per transaction per owner.** `closet_sync_revision(owner, table)` checks the mark, then returns the owner's cached revision or bumps `user.revision` once and caches it in `closet.revision_<id>` (SET LOCAL). A GUC name part may not start with a digit, so the plan's `closet.revision.<id>` is invalid. A savepoint rolled back reverts the bump and the cache together. An account's BEFORE DELETE sets its cache to `gone`: its cascades stamp nothing and write no tombstone (a tombstone for a deleted user would fail its foreign key).
- **Roots** stamp `revision` (and `updated_at` on update) in a BEFORE row trigger; an AFTER DELETE row trigger writes the `sync_tombstone`, cascades included. **Children** (and a garment's photo: only its version, cutout status or missing mark, 0062) touch each parent row once per statement (`updated_at = now()`, AFTER statement triggers over transition tables, one per event), and the parent's own trigger stamps it. A child marked `createsParent` (outfit rules, the style profile's; 0069's `closet_sync_touch_or_create`) inserts a missing parent row instead of skipping it (a one-row-per-user parent the child may precede), never for an owner gone. The week template stamps `user.week_template_revision` (a `SYNC_STAMPS` entry, which the feed reads from the user row). A no-op upsert still bumps: a spurious change is harmless, a missed one is not.
- **A replayed create never resurrects.** An insert whose `client_id` has a tombstone for its owner and table raises SQLSTATE `CL410` (`isDeletedClientId`, `errors.ts`; the route's 410 `gone`). The check is in the trigger, not the writer's statement: a trigger's query takes a fresh snapshot, so it sees a tombstone the owner lock's holder committed while the writer waited, which the writer's own READ COMMITTED snapshot (taken before the wait) does not (`queued-writes.spec.ts` interleaves it). A writer whose create carries a client id names the day's own arbiter in `on conflict (...)`, so a client id taken by another row is a unique violation (409), never a silent no-op (`setWoreToday`).

## Gotchas

- **A unique violation is answered only for the constraint the caller names.** `isUniqueViolation(error, constraint)` (`src/db/errors.ts`) takes the constraint (`UniqueConstraint`: the names are constants beside their indexes in `schema.ts`) and is false for any other, so the caller rethrows. Matching any `23505` once turned the plans' one-active race into "a plan with this name already exists". A new writer that answers a violation with a message adds its constraint to `UniqueConstraint`.
- **Indexes and constraints are declared in `src/db/schema.ts`, never only in a migration file.** `drizzle-kit generate` diffs snapshots, not the database, so DDL hand-added to a migration is invisible to every later diff and the drift test reports it. Postgres does not index foreign keys on its own. `test/integration/migrations.spec.ts` lists the expected index names.
- **A writer outside `ownerTransaction` folds the owner lock into its first statement** (`owner-lock.ts`: `ownerLockCte` + `ownerLocked`, `ownerLockSql` + `OWNER_LOCKED`); `ownerLocked` is an uncorrelated count, never `exists` or a `limit` (they stop at the first of several owners).
- **A delete that must see what the lock's waiters committed runs in the statement after the lock**, never folded into it: under READ COMMITTED the folded statement reads the snapshot taken before it waited (account deletion lost a saved row's bytes that way, #544). A folded lock stays right for a write gated on its own lock.
