# Web Push

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds Client; Revoked with the session; Reminders, per device; The scheduler; Muse's rounds.

`src/web/push/` (rebuilt 2026-09-26; the old module never delivered anything, audit A1). Registered only when `PWA_ENABLED` (`WebConfig.vapid`); without it `/push/*` and Profile › Notifications (`/auth/profile/notifications`, `PushSettingsPage`, its own page since #728) are a 404, Profile shows no Notifications row and nothing is scheduled. What it is for (#5, decided 2026-09-26, built in #15): a morning "Today's outfit" and an evening "What did you wear?" reminder, **opt-in per device**, besides the Notifications page's test send (it opens that page); the week's re-plan (#16) tells the devices with the morning reminder on what it swapped (see Weekly auto-plan), and runs before a person's morning reminder is composed (#76). A shared wardrobe notifies nobody else: reminders are about the person's own day.

- **`user_device` is keyed by endpoint** (`UNIQUE`, text) and written only by `upsertDevice` (`INSERT ... SELECT ... ON CONFLICT (push_endpoint) DO UPDATE`): renewed keys update the row, and the same browser signed in as someone else moves it to that user. **It takes the user's row lock and rechecks the session's stamp under it** (#512, #700): the insert selects from the user's row `for no key update`, only while `right(password, 8)` and `session_version` are still the session's `pwf` and `sv` (`sessionStamp(request)`, `sessionStillOpenSql`), so it and `updatePasswordHash` or `endOtherSessions` take turns: a subscribe that holds the lock is revoked by the password's second statement, and one that waited inserts nothing and answers as the gate does an ended session (`endSession` + the 401, `loginRequired`). One statement, no extra round trip; a writer of another credential a password must end does the same (`push-revocation.spec.ts`, the two `interleave` specs). Keys are columns (`key_p256dh`, `key_auth`), not JSON.
- **web-push stays 3.x** (`^3.6.7`, `@types/web-push` 3.x): 4.0.0 is ESM-only (no CJS build, no types) and the build is CommonJS, so the range is the pin. Revisit with an ESM migration, never a `require(esm)` workaround (`docs/decisions.md` 2026-11-14).
- **One sender** (`createPushSender`, `sender.ts`, built once by `createApp()` when `PWA_ENABLED`, logger `Push`, handed to the routes as `WebOptions.push` and to `server.ts`): `sendToUser(userId, payload, { ttlSeconds })` (the test send), or `sendEach(messages)` for a job's batch (#173: each message a user's claimed device ids or their devices with the morning reminder on; every user's devices read in one statement, `devicesOfUsers`, at send time and never earlier, so a device revoked or signed in as someone else meanwhile gets nothing), sends to every chosen device in parallel with web-push (aes128gcm, VAPID passed per request, 10 s socket timeout), deletes a device on 404/410, logs any other failure with the device id and never throws for a device. Endpoints are capability URLs: never log them (a `WebPushError` carries one). `loadConfig` refuses `PWA_ENABLED` without both VAPID keys or with a non-https `SITE_URL` (the VAPID subject; web-push's rule), naming the key; the sender then checks the keypair's shape when it is created, so a malformed pair fails the boot.
- **The payload is `PushPayload` (`payload.ts`: `title`, `body`, `url`, optional `tag`)**, imported by both the sender and the service worker; `parsePushPayload` is the worker's check. `notificationclick` calls `openNotification` (`notification-click.ts`), which opens `notificationTarget(url)` (same origin only, else `/`): focuses a window already on it, else navigates the first open window, else opens one. No automation can tap a notification, so its spec drives every branch with stand-in windows; `test/push-notification.spec.ts (retired 2026-10-13)` delivers pushes through CDP and asserts what shows (`docs/testing-service-worker.md`).
- **Signing out drops the subscription** in the service worker (with the page cache); the row goes on the next send's 410 or with the account (the foreign key cascades, and `push_reminder`'s claims with the row).
- **The abort cancels, never abandons** (#920): the signal reaches the re-plan (rolled back before its commit) and the forecast reads; the run awaits all but the send, then gives back; a short give-back is `lost`, a failure (`docs/decisions.md`).
- **Manual check** (CI has no push service): on an installed phone, Profile, enable notifications, turn the morning reminder on at the next quarter hour; it arrives at that minute and opens Today; mark something worn and set the evening one: nothing arrives.
- **A device's rows are its user's**: `POST /push/unsubscribe` deletes only the caller's row (204 either way); the test send past `PUSH_TEST_LIMIT` sends nothing (#705).
- **Never logged**: an endpoint (the settings route logs the user and the device id).

## Gotchas

- **A notification about the day follows the day's re-plan, by construction, not by the clock.** Two minutely timers have no order (#76: a 05:30 reminder named the outfit the 06:00 re-plan then swapped, and at the same minute it was a race), so the morning reminder calls `replanToday` for its person before reading Today, and the re-plan's claim commits in the same transaction as its writes: a claim that commits before the work (the first re-plan's `claimReplan`) lets another reader find the day "done" while it is still being done. `REPLAN_HOUR` is derived from `REMINDER_WINDOWS.morning.from`, never a second constant. A new scheduled send that describes the plan runs the re-plan first the same way.
- **A push reminder is claimed before it is sent, and claimed once.** `push_reminder`'s primary key (device, kind, day) is the only thing standing between two overlapping servers and a double notification; a new kind of scheduled send claims the same way (an insert that lands, `ON CONFLICT DO NOTHING RETURNING`), never "check, then send". A reminder's time is a wall-clock minute in `APP_TIMEZONE`, turned into an instant per day with `instantAt`; never add 24 h to yesterday's instant (DST).
- **Playwright's default Chromium (the headless shell) reports `Notification.permission` as `'denied'`** even after `grantPermissions(['notifications'])` (the Permissions API says `'granted'`), so the profile's push controls read "blocked". `test/push-settings.spec.ts (retired 2026-10-13)` runs on the full Chromium build (`test.use({ channel: 'chromium' })`, installed by `playwright install chromium`). Headless Chromium has no push service either: that spec stubs `PushManager` in the page and lets everything server-side run for real.
- **Moved rules** (detail in `reference.md`): permission is requested only by `pushManager.subscribe()` as the first await of the enable tap (iOS drops the gesture across awaits). The device's endpoint is a capability URL: reminder settings post it, never put it in a logged URL. Only what `claimReminders` inserted (`ON CONFLICT DO NOTHING RETURNING`) is a run's to send. The evening reminder is skipped when anything is marked worn today. Every message goes out in one `sendEach` at the end; one person's failure is counted in `run.failed`, the others still sent; once aborted a run never starts `sendEach`. A reminder's TTL never reaches the next day. A failed Muse round notice never undoes the round.
