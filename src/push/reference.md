# Web Push: reference

Moved out of `AGENTS.md` (#723) so the auto-loaded doc keeps only invariants, gotchas and ownership. Not auto-loaded: read it before changing this area. Where it disagrees with the code or a spec, they win.

- **Client** (`views/assets/page/push.ts`, imported by `pwa.js` only on pages the layout marks `data-signed-in` on `<html>`: the cookie is httpOnly, so no script can tell): `syncSubscription()` re-sends an existing subscription once per document (keeps keys current, moves the device to whoever is signed in); `<push-settings>` on the profile (`settings.tsx` renders every state's text hidden, the element shows one: checking, on, off, blocked, unsupported, install, error). Permission is only ever requested by `pushManager.subscribe()` as the first await of the enable tap (iOS drops the gesture across other awaits; the registration and key are fetched beforehand). iOS/iPadOS has push only in the Home Screen app (16.4+): a Safari tab has no `PushManager` and `navigator.standalone === false`, which is the "install" state.

- **Revoked with the session** (#73): a signed-out device receives nobody's notifications, including one signed out away from itself (the reminders name planned outfits on its lock screen). **One remover, `revokeDevicesStatement(db, userId, keep?)`** (`queries.ts`), used by every path: a new password (`updatePasswordHash`, the change-password route and `user:set-password`) and Sign out everywhere (`endOtherSessions`, #700, its form posting `pushEndpoint` too) delete the account's rows in their own transaction (`revokeSignIns`), beside the token revocation; the route keeps the device that made the change, named by the endpoint its form posts (`pushEndpoint`, `PushEndpointField` in `settings.tsx`, filled by `<push-endpoint>` in push.js from `syncSubscription`; empty or absent, from a browser without push or a page cached before it, every row goes and that device's next signed-in page subscribes it again without its reminders; another account's endpoint keeps nothing), so its reminders survive; the CLI has no device and removes all. A secret rotation is an ops step, `npm run push:revoke-all` (`src/maintenance/revoke-push.ts`, per user through the same statement (`revokeDevices`), one transaction), not automatic: detecting a rotation needs a stored secret fingerprint, and rotations are rare and manual. Account deletion cascades. The browser half: the login page shown signed out (never to a signed-in visitor) carries `<push-signed-out>` (`PushSignedOut`), which drops the browser's subscription (`dropSubscription`, push.js; pwa.js imports push.js for it on a signed-out page; a boosted tap that lands there upgrades it in the page it left), so every device whose cookie the session resolver rejected drops its subscription on the page the gate sends it to; the push service then 410s any send to it. Logs: `Password changed for user <id>: other sessions, N MCP tokens, D device tokens, M other push devices and I unanswered invites revoked` (logger `Web`), `Password set for user <id> via CLI: ...` (`SetPassword`), `Push devices revoked for user <id>: N` and the total (`RevokePush`); never an endpoint. `test/integration/push-revocation.spec.ts` (rows, the scheduler, the CLIs, the pages) and `test/push-revocation.spec.ts (retired 2026-10-13)` (the form and the drop in Chromium, document and boosted).
- **Reminders, per device** (`user_device.morning_reminder`, `evening_reminder`: minutes after midnight in `APP_TIMEZONE`, null when off; `reminders_set_at`; `drizzle/0019_push_reminders.sql`). The times are quarter hours in `REMINDER_WINDOWS` (morning 05:00-11:00, evening 17:00-23:00; `src/push/reminders.ts`, which the check constraints are built from): away from midnight and from the 01:00-03:00 hours US and EU DST changes skip or repeat. Only the browser knows which device it is (its subscription's endpoint), so `<push-settings>`, once on, posts it (`POST /push/reminders/form`, a POST though it reads: the endpoint is a capability URL and never goes in a logged URL) and htmx swaps the form into `#push-reminders`; every change posts `POST /push/reminders` (`endpoint`, `morningOn` + `morning`, `eveningOn` + `evening`; a time off the choices is a 400; another user's endpoint changes nothing and says to turn notifications on), which answers **only the status line** (`ReminderStatus`), never the form: the form is an `AutosaveForm` (Gotchas), in order and whole each time, in the slot `#push-reminders` push.js loads it into. One writer, `saveReminderSettings`, stamps `reminders_set_at`. `upsertDevice` clears a device's reminders when the browser signs in as someone else.
- **The scheduler** (`src/web/push/reminders.ts`, `sendDueReminders(deps, now)`): `server.ts` runs it every minute (`scheduleMinutely`, a second past the minute) and prunes claims of past days nightly; **`createApp()` never schedules it, so the integration harness and the CLIs send nothing** (a spec calls it with the instant it wants). A run: `dueReminders` (pure) lists each device's reminder whose wall-clock time today (`instantAt`, so 07:30 stays 07:30 on both DST days) has come, came after `reminders_set_at` (a device that turns one on after its time today gets it tomorrow) and is at most `LATE_LIMIT_MINUTES` (30) ago (a restart across its minute catches up; a server down for hours never sends a morning reminder at noon); `claimReminders` inserts them into `push_reminder` (`(device_id, kind, day)` primary key) with `ON CONFLICT DO NOTHING RETURNING` in one statement, and only what it inserted is this run's to send. **Two servers overlapping in a deploy** both find a reminder due and both insert; Postgres makes the second wait on the first's key and skip it, so each goes out once (`push-reminders.spec.ts` runs two servers' runs at once for 20 minutes' worth). The claim comes before the send: a crash between them loses a reminder rather than sending it twice. It raises no unique violation, so it names no `UniqueConstraint`. Then, with what serves everyone read once for the minute (#173: the mornings' forecasts, who of them is due a re-plan, the evenings' days; see src/maintenance/AGENTS.md, a job reads per batch and composes per person), per person and kind: **morning**, from `todayFor` (the page's model, with the batch's weather), "Today's outfit", composed **after that person's re-plan for today** (`replanToday`, run first if nothing has run it: once a day whoever asks, its claim committed with the work, so a 05:00 reminder never names an outfit the day's re-plan is about to swap, whatever the two minute timers' order or which of two servers claims what; a failed re-plan is logged and the reminder names the plan as it stands; `ReminderDeps.replan` is the same deps the minutely re-plan uses), **what that re-plan swapped today first, one line each** (`reminderSwapLine`: "Swapped in Wool coat: it turned cold", "Swapped in Chelsea boots: Bean Boots is at repair"; `weekPlan.why.*`), so the person gets one push rather than a swap notice beside it (other days' swaps still get the `week-replan` notice), the weather line as text (`weatherLineText`) and the planned outfits (`Work: Navy suit · Evening: Summer date`), with the top idea first while nothing dresses the day; **evening** "What did you wear?", naming what is planned, and **skipped when anything is marked worn today** (claimed all the same: it is decided at its minute); it reads only the day's bare entries and the worn check, every evening person's in one statement (`eveningDays`), never Today's weather or ideas. Every composed message goes out in one `sendEach` at the end; a person whose composing fails, or whose device the push service refused (not a gone one: pruned), is logged and counted in `run.failed`, the others still sent, and the scheduled run (`sendDueRemindersWhole`) then ends with one `PartialFailure` (#687). That batch reads its devices after the claim, on purpose (a device moved or revoked meanwhile gets nothing; `push-reminders.spec.ts` moves and revokes one in that window), so if that one read fails nothing was sent and the run gives its claims back (`releaseReminderClaims`, logged `Released N reminder claim(s)`, `ReminderRun.released`): the next minute sends them while they are within `LATE_LIMIT_MINUTES`. **Shutdown does the same**: past the timer's stop wait the run's `AbortSignal` aborts, whatever step the run is in (composing, before the send, mid-send); it never starts `sendEach` once aborted and `sendDueReminders` gives back every claim `sendEach` had not reported (`onReport`), so a stop loses nothing, and the run ends `interrupted` (`JobInterrupted`, no failure, no capture; `push-reminders.spec.ts`, #696, #914). A morning one sent then no longer says today's swaps (its re-plan is done), which the calendar still shows. Both open Today (`url: '/'`), tagged `today-morning`/`today-evening` (a later one replaces an unread one), TTL 3 h and 1 h (never the next day).

- **Muse's rounds** (#337): `finish_round` (MCP), or the quiet close of a round its agent left open (the minute timer, `src/web/wishlist/suggestions.md`), sends one notification after the round's commit (`notifyRounds`, `src/web/wishlist/round-end.ts`, shared by both), through `sendEach` to the owner's devices with `user_device.muse_rounds` on (`devices: 'muse-rounds'`; a toggle in the same per-device form as the reminders, `museRoundsOn`, off by default and turned off when the device moves to another account, `upsertDevice`): "Muse finished a round", "Muse: 3 outfits, 7 pieces to consider", opening `/outfits` (or the Wishlist inbox), tagged `muse-round` so a newer round replaces an unread one, TTL 24 h. A failed send is logged, never undoes the round. `test/integration/muse-round.spec.ts`, `muse-round-close.spec.ts`.
