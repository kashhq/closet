# Maintenance: timers, reconciliation and the CLIs

## Layout

```
  maintenance/         reconcile.ts (reconcileStorage: storage and the file table kept in step, with
                       the deletion guard; abandoned pending photos in a pass of their own), trash.ts
                       (the quarantine's purge and --restore-from-trash, #649), nightly.ts (a daily timer at an APP_TIMEZONE hour, started
                       by server.ts when MAINTENANCE_ENABLED), minutely.ts (a timer a second past every
                       minute, or every `everyMinutes`, never overlapping: the push reminders, the
                       week's re-plan, the order mail's poll, Muse's quiet round close),
                       scheduled.ts (what both timers share: ScheduledJob, whose stop() waits for a
                       run in flight at most STOP_WAIT_MS, and stopBeforeClose, the preClose hook
                       that stops them all before the pool ends), cli.ts (runCli: config, logger, schema check,
                       pool, exit status), reconcile.cli.ts (`npm run maintenance:reconcile`),
                       set-password.cli.ts (`npm run user:set-password -- <email>`): the locked-out recovery,
                       revoke-push.cli.ts (`npm run push:revoke-all`): every push subscription, after
                       a secret rotation, retrim-thumbs.ts + .cli.ts (`npm run maintenance:retrim-thumbs`):
                       the #373 backfill of cutouts' trimmed thumbs, sync-prune.ts (pruneSyncTombstones:
                       the changes feed's deletions past 90 days, raising sync_floor; src/web/sync/AGENTS.md),
                       weather-prune.ts (pruneWeatherCaches: forecast and normals rows no home, here or trip
                       location sits at, last attempted over 30 days ago; src/weather/AGENTS.md),
                       after-restore.ts + .cli.ts (`npm run maintenance:after-restore`, #653: the post-restore
                       command), repoint-cutout.ts + .cli.ts (`npm run maintenance:repoint-cutout`: a row
                       pointed at a cutout set in storage, through the state machine)
```

## Commands

```
npm run maintenance:reconcile [-- --dry-run] [--force]
                              # one storage reconciliation pass from dist/ (build first). In production:
                              # docker exec closet npm run maintenance:reconcile. Exits 3 when the
                              # guard refused; --force deletes anyway (dry-run first). Like set-password it
                              # never migrates: a database behind the build is refused (start the server first)
npm run maintenance:reconcile -- --repair-storage-identity --confirm
                              # pairs `install` with DATA_PATH's marker (#833; docs/operations.md#photo-storage-
                              # marker); 2 without --confirm, 3 no readable marker (never writes one)
npm run maintenance:reconcile -- --restore-from-trash <uuid>.webp | <day>/<entry>
                              # moves one quarantined set back into DATA_PATH (Gotchas: the quarantine);
                              # exits 3 refused (no match, several, or a live set of that name)
npm run user:set-password -- <email>
                              # sets a locked-out user's password (read without echo, or piped
                              # stdin), signs out their sessions, revokes their access tokens and
                              # push subscriptions. In production:
                              # docker exec -it closet npm run user:set-password -- <email>
npm run push:revoke-all       # removes every account's push subscriptions: the step after rotating
                              # ACCESS_TOKEN_SECRET (Deployment). docker exec closet npm run push:revoke-all
npm run maintenance:retrim-thumbs [-- --dry-run]
                              # gives every photo with a ready or edited cutout its thumb trimmed to the
                              # garment (#373), under a new variant key (the `rederive` event) so caches
                              # miss; the set it replaced is deleted by the swap. Idempotent (a thumb already
                              # trimmed is `current`); exits 1 when any photo failed (warn lines name them;
                              # run again), 130 when Ctrl-C or SIGTERM stopped it after the photo in flight
                              # (Gotchas). One read per 100 photos, then 4 statements per photo retrimmed.
                              # Once after the deploy: docker exec closet npm run maintenance:retrim-thumbs
npm run maintenance:after-restore
                              # after restoring the database from a dump (#653; Gotchas): bumps the sync
                              # epoch (every device re-syncs, every session signs in again, #908), revokes
                              # every agent and device token and every push subscription, releases
                              # dead cutout leases (older than DEAD_LEASE_MS, 2 min), then reconciles as a dry
                              # run and lists the garments whose original is missing (id, name, owner). Deletes
                              # and marks nothing; exits 3 when reconciliation refused. Safe to run twice.
                              # docker exec closet npm run maintenance:after-restore
npm run maintenance:repoint-cutout -- <uuid>.webp <key|unkeyed>
                              # points a photo's row at the nobg and thumb stored under <key> (the files must
                              # exist): `rederive` for a ready or edited row (status kept), `edit` for none,
                              # pending or failed; refused (exit 3) for an outfit selfie. Version and garment
                              # revision move; clears the row's missing mark. The `Keeping variant key <k>`
                              # line names <k>; `unkeyed` after a rollback past #141 (docs/operations.md)
```

## Statements per run

What each job sends to Postgres (#173). Production pays a round trip per statement over the WiFi link (homelab #40), so a statement inside a loop over people or rows multiplies it: **read per batch, compose per person**. A job that loops per person keeps its per-person isolation (one person's failure is logged and counted, never the others'), and only reads that serve everyone move out of the loop. `test/integration/job-statements.spec.ts` pins each count for one person (or row) and for three; the page audit's `#173` steps measure them on the demo (`docs/perf/README.md`).

| Job | Statements | Scales with | Whole-table reads |
| --- | --- | --- | --- |
| Morning reminders | 5 + 6 per person (+1 undressed day: the ideas) | people due; re-plan and Today stay per person | `user_device` rows with a reminder (a household's handful, no index) |
| Evening reminders | 4, or 3 when all wore something | nothing | as above |
| Reminders, nothing due | 1 | nothing | as above |
| Week re-plan | 2 + 5 per person due (+ writes per swap or kept entry) | people due | none |
| Forecast refresh | 1 (+1 upsert per location fetched) | locations, not people | none |
| Cutout job | 8 per photo (claim 4, result 4), +3 for the look that finds the queue empty | photos | none (indexed claim) |
| Cutout retry | 1, or 5 when anything failed | nothing | none |
| Reconciliation | 3, 4 in production (+1 per orphaned row, +1 per aged pending photo, +1 when a missing mark changes) | findings, which are rare | `install` (production's pairing, #833), `pending_photo` and `file` (with `garment` and `selfie` for the references): the job is comparing storage with every row |
| Order mail poll | 2, or 1 + per new email: 1 (no products) or 4 | new emails | none |
| Prunes (reminder, re-plan claims) | 1 each | nothing | none |
| Sync tombstone prune | 1 per 1000 tombstones pruned, +1 for the short batch that ends it | tombstones past 90 days | none (`sync_tombstone` filtered on `deleted_at`, no index: a household's deletions) |
| Weather cache prune | 2 (a delete per cache) | nothing | none (both caches are a household's few locations; the anti-joins read `user_weather` and `trip`) |
| Muse round close | 1, + 4 per round closed (`finishRound`: begin, lock, round, commit) and 1 for the batch's devices | rounds left open, which are rare | none (`quietRounds`: Muse's rows only, partial indexes) |

The morning reminders read the mornings' forecasts (`refreshForecastsFor`), who of them is due a re-plan (`replanCandidates` with their ids) and the evenings' days (`eveningDays`) once for the minute, in parallel, then send every message in one batch (`PushSender.sendEach`: the devices of all of them read in one statement at send time, never earlier, so a device revoked or moved meanwhile gets nothing). The re-plan's transaction reads its auto entries with the day's claim in one statement (`claimAutoEntries`, a data-modifying CTE) and its week, pool, memory and outfits' garments in a second (`weekSql`, `outfitGarmentStatesSql`). The cutout job's per-photo 8 is the lease's price: the claim and the result each lock the row, ask the state machine and write (see Background removal). Reconciliation's per-row deletes stay per row on purpose (`removeOrphanedRows`: one bad row must not cancel the sweep).

## Gotchas

- **Reconciliation first proves the directory is the household's** (#650): before any read of rows it asks `storageIdentityProblem` (the `.closet-storage` marker absent, another install's than the boot claimed, or, in production, not the one the `install` row is paired with, #833), and after the scan it refuses `file` rows with not one stored photo set (the guard's mirror rule, which counts only sets no pending row explains, as the guard does: `unpendingSetCount`), both ahead of the pending pass, so nothing is deleted, pending rows included, and `--force` overrides neither (an unmounted share is never what an operator means). The scan now runs before the pending pass; `planReconciliation` drops the sets that pass deleted. `storage-marker.spec.ts` covers each refusal; Images has the marker.
- **A photo set with no `file` row is quarantined, never deleted** (#649). After a restore from an older dump, the sets of garments added since have no row and are the only copy, and a trickle of them passes the guard. So the orphan pass moves each set by rename into `DATA_PATH/.trash/<today in APP_TIMEZONE>/<base name>/` (`PhotoStorage.quarantine`: atomic, bytes untouched; a name already there that day gets a `~<8 hex>` entry, never an overwrite) and reports `orphanedSetsQuarantined`. The same run deletes `.trash` day directories older than `TRASH_RETENTION_DAYS` (30) before its `now` (`purgeTrash`, `trashSetsPurged`; a failure is a warn line and the run goes on; skipped when the guard refused: the trash may then be what is needed back). Unreferenced rows' sets, pending photos and superseded variants are still deleted: a row explains them. `--restore-from-trash` restores whole or not at all: every entry holding the set's files (a quarantine that failed mid-set splits one), each file linked back (never replacing) before any leaves the trash, a failed link rolled back; refused when a live set has the name. It stamps the files `now`, so the next run leaves them a day, and restores bytes only: without its `file` row the set is quarantined again after that. `.trash` is a dot-directory: `list()` skips it and `/file/**` never serves it. `reconcile.spec.ts` (the quarantine) covers each rule.
- **Reconciliation refuses wholesale deletions.** It removes photo sets whose `file` row is gone (quarantined, above), so a database that lost its rows (a restore, the wrong `DATABASE_*`) would have it empty storage of every photo. `guardRefusal` (`src/maintenance/reconcile.ts`) stops a run that would delete anything while the file table is empty and storage holds photos, more than 25 sets, or (above 5 sets) more than a fifth of the stored ones: it logs a warning, deletes nothing, reports `refused`, and the CLI exits 3. `--force` is the operator's override after a `--dry-run`. `test/integration/reconcile-guard.spec.ts` covers each rule. Pending photos are explained, not counted, and removed past their cutoff (the run's, or a week for a batch's drafts, #200: `pendingCutoffs`; see the link import gotcha above; `link-import.spec.ts` reconciles 27 abandoned imports and then a real mismatch). A live photo's day-old cutout and thumb files under another variant key than its row's (a cutout write that died before its swap, #141; see Images) are deleted as `supersededVariantsDeleted` and do count, one set per photo.
- **A database restored behind its storage never costs a cutout** (#141). After a restore from a backup older than some cutout edits, those rows name older variant keys than the newest files on disk. The superseded pass therefore deletes a set with a cutout only when all its files are day-old and older than every file of the set the row points at. A set newer than the row's is kept and logged at warn (`Keeping variant key <k> of <photo>: newer than the row's variant (key <k'>): database restored behind storage?`); a row whose own set is not in storage deletes nothing of that photo (`Keeping every variant of <photo>: ... not in storage`). No operator step: the photo shows its row's (older) cutout, the newer bytes stay on disk until `maintenance:repoint-cutout -- <photo> <k>` points the row back (Commands) or the mask is edited again. The guard stays as the second line. A superseded key holding only a thumb goes once day-old whatever its age against the row's set: a thumb is derived (regenerable from its nobg), never the one copy of anything, and a thumb backfilled across a swap is exactly that, newer than the set the row points at; a lone superseded nobg is a cutout and is kept like a whole set. `reconcile.spec.ts` covers each case.
- **A photo with nothing left in storage is marked, never deleted** (#653). A database restored ahead of its storage has rows whose bytes are gone. Reconciliation's plan (`missingMarks`) sets `file.original_missing_since` on a live, day-old row whose original and its row's nobg are both absent, whatever its thumb (#917: the garment and share pages load the nobg, served as the original without one; a thumb alone shows only in the grid), and clears it on a marked row once either is stored again (a second restore, a remount, `--restore-from-trash`, `repoint-cutout`); `missingOriginals` still reports every missing original. The write (`writeMissingMarks`) is one statement after the deletions and the quarantine, only when a set is non-empty, under the owners' lock (`ownersLockCte` over `garmentOwnersOf`, in id order; a photo no garment shows locks nobody), its WHERE re-asserting `IS NULL` / `IS NOT NULL`; a failure (a 55P03) is logged and reported as `marksFailed`, a failure of the nightly job, and costs no deletion. A dry run marks nothing; a guard refusal still marks (a mark deletes nothing). The garment's revision moves through `closet_sync_touch_photo` (0062). While marked, the photo-ref helpers answer no photo (Images), so pages draw their placeholder and the API leaves `photo` out for `photoMissingSince`. `after-restore.spec.ts` covers marking, clearing, the pages and the writes on a marked garment.
- **After a restore, `maintenance:after-restore` is the one step** (#653; Commands). It is a dry run for storage (`reconcileStorage({ dryRun: true })`: the pending pass and the trash purge only count), and lists missing originals from the plan, not the column. The lease release goes per row through `recordCutoutEvent(release, <the row's own worker>)`, so a lease taken over since stays. It also ends what a restore revives (#908): every session, through the epoch bump (a session cookie carries the restore epoch as `sep`, `restoreEpochSql`; Auth), and every agent and device token (`revokeEveryonesTokens`: per user through a new password's `revokeTokensStatement`, in one transaction).
- **Only the server schedules the nightly reconciliation, the push reminders and the week's re-plan.** `serve()` (`server.ts`) starts `scheduleNightly` (03:00 in `APP_TIMEZONE`, recomputed after every run, never overlapping) when `MAINTENANCE_ENABLED` (reconciliation) and always (the cutout retry), with `PWA_ENABLED` the reminders' `scheduleMinutely` and their claims' nightly prune, and always the sync tombstone prune (`pruneSyncTombstones`), the re-plan's and its prune (without `WEATHER_ENABLED` it still judges availability) and Muse's quiet round close (`closeQuietRounds`, `src/web/wishlist/round-end.ts`; notified only with `PWA_ENABLED`); `createApp()` does neither, so the integration harness and the CLIs never hold a timer or send a notification. A spec runs one minute's reminders with `sendDueReminders(deps, now)`.
- **Each timer run is a job** (`runAsJob('cron')` in `scheduleJob`, the one loop under `scheduleMinutely`/`scheduleNightly`): every line it logs, its `<name> failed` line included, and its failure's Bugsink event carry a fresh `job_id` `cron-<12 hex>`; the scheduler's own lines between runs carry none.
- **Every timer is stopped and drained before the pool ends** (#78). Both schedulers return a `ScheduledJob` (`src/maintenance/scheduled.ts`): `stop()` clears the timer, so no run starts after it, and waits for a run in flight, at most `STOP_WAIT_MS` (`JOBS_STOP_MS`, 2 s, `settlesWithin`; the whole shutdown must fit docker stop's 10 s: `src/shutdown-budget.ts`), after 1.5 s it aborts the run's `AbortSignal` (`run(signal)`; the reminders stop sending and give back their unsent claims) and gives it `JOBS_ABORT_GRACE_MS` (0.5 s) more, after which it logs `<job> still running after 2000 ms; stopped` and resolves; it never rejects. `serve()` collects every job it starts into one list and hands it to `stopBeforeClose`, a single `preClose` hook that stops them all together (one bound in all, not one per job) and logs `Stopped N scheduled jobs in T ms` (logger `Scheduler`); `createApp()`'s `onClose` (the cutout queue, then the pool) runs only after it. Until #78 the nightly jobs' `stop()` only cleared the timer and ran in `onClose`, so a reconciliation in flight at a 03:00 deploy lost every later query to the ended pool. An abandoned run is safe by each job's own design (claims before work, rows before bytes). `serve()` also hands the list to the `JobRoster` `createApp()` built (`roster.adopt`): each job exposes its `name` and `runStartedAt()`, and `/health/ready`'s optional `cron_jobs` check names a run in flight past `STUCK_AFTER_MS` (30 min; see Health). A new timer is pushed onto that list, never given a hook of its own, and its run is wrapped in `metrics.timeJob(<JobName>, run)` (job_duration_seconds; see Metrics). `scheduled.spec.ts` closes a real Fastify instance with runs in flight.
- **Browser-made cutouts keep their untrimmed thumbs** (#373). `maintenance:retrim-thumbs` takes only `ready` and `edited` rows: a photo whose cutout the browser made before 2026-09-26 is `none`, and `file_variant_key_check` allows a key only on a ready or edited row, so its thumb cannot move to a new key, and rewriting it in place would break the rule that a keyed or served name never changes (an immutable URL would keep the old bytes on every phone). Its thumb is trimmed once its mask is edited (an `edited` row takes a key) or, if the thumb file is missing, when it is made on request.
- **`maintenance:retrim-thumbs` stops between photos, never inside one.** It is `runCli`'s one `stoppable` command: the first SIGINT or SIGTERM aborts `stop`, the photo in flight finishes (its new set stored and swapped, or refused and deleted), and it exits 130 with `Thumb retrim stopped by a signal after N photos`; a second signal, either one, kills it, because the first takes both listeners away (`commandStop`, `cli.spec.ts`: Node kills only on a signal with no listener, so a SIGTERM after a Ctrl-C was caught until 2026-11-12). Killed between `storeCutoutFiles` and the swap, a photo would keep a set newer than its row's, which reconciliation's superseded pass keeps forever as a restore's signature (above). `retrim-thumbs.spec.ts` stops one mid-run, and proves a failed, cutout-less or refused photo is counted and logged alone.
- **The CLIs never migrate.** `runCli` (`src/maintenance/cli.ts`) checks `requireCurrentSchema` first and exits 1 with "The database is N migration(s) behind this build. Start the server..." when the image is newer than the database, or "The database's newest migration (...) is not in this build" when it is older (`SchemaAheadError`, #651; docs/operations.md#migrations-and-rollback). A recovery tool run beside a live server must not change the schema under it (until 2026-09-26 they booted the whole app, migrations included). `test/integration/migration-runner.spec.ts` covers the check.
- **A run that left someone out ends as a failure** (#687). A job isolates per person (or per photo set), finishes the others, then the server's wrapper throws one `PartialFailure` (`src/metrics/partial-failure.ts`, `endWhole(job, counts, run)`; the message names the job and counts, never a person) when `run.failed > 0`, the guard or the storage check refused, or `missingOriginals > 0`, so `metrics.timeJob`, the one choke point, records `outcome="failure"` and captures once. The wrappers are `sendDueRemindersWhole`, `replanWeeksWhole` and `reconcileStorageWhole`, which `server.ts` schedules; the functions under them still return their run, because specs and the CLI read the report (the CLI says the same in its JSON and exit code 3). A failed person's re-plan day is retried at 5, 15 and 60 minutes (`ReplanRetries`), then claimed, and each job (the minutely re-plan, the morning reminder) counts only its own first failure, so one capture per job and person-day. A new per-person job copies this. A forecast fetch that fails is not one: the cache serves a stale answer, and with nothing cached the job runs without a forecast (`userWeatherOrNone`), since a provider outage must not alert every morning.
