## Gotchas

- **Reconciliation first proves the directory is the household's** (#650): before any read of rows it asks `storageIdentityProblem` (the `.closet-storage` marker absent, another install's than the boot claimed, or, in production, not the one the `install` row is paired with, #833), and after the scan it refuses `file` rows with not one stored photo set (the guard's mirror rule, which counts only sets no pending row explains, as the guard does: `unpendingSetCount`), both ahead of the pending pass, so nothing is deleted, pending rows included, and `--force` overrides neither (an unmounted share is never what an operator means). `storage-marker.spec.ts` covers each refusal; Images has the marker.
- **Reconciliation refuses wholesale deletions.** It removes photo sets whose `file` row is gone (quarantined, above), so a database that lost its rows (a restore, the wrong `DATABASE_*`) would have it empty storage of every photo. `guardRefusal` (`src/maintenance/reconcile.ts`) stops a run that would delete anything while the file table is empty and storage holds photos, more than 25 sets, or (above 5 sets) more than a fifth of the stored ones: it logs a warning, deletes nothing, reports `refused`, and the CLI exits 3. `--force` is the operator's override after a `--dry-run`. `test/integration/reconcile-guard.spec.ts` covers each rule. Pending photos are explained, not counted, and removed past their cutoff (the run's, or a week for a batch's drafts, #200: `pendingCutoffs`; see the link import gotcha above; `link-import.spec.ts` reconciles 27 abandoned imports and then a real mismatch). A live photo's day-old cutout and thumb files under another variant key than its row's (a cutout write that died before its swap, #141; see Images) are deleted as `supersededVariantsDeleted` and do count, one set per photo.
- **A photo with nothing left in storage is marked, never deleted** (#653). A database restored ahead of its storage has rows whose bytes are gone. Reconciliation's plan (`missingMarks`) sets `file.original_missing_since` on a live, day-old row whose original and its row's nobg are both absent, whatever its thumb (#917: the garment and share pages load the nobg, served as the original without one; a thumb alone shows only in the grid), and clears it on a marked row once either is stored again (a second restore, a remount, `--restore-from-trash`, `repoint-cutout`); `missingOriginals` still reports every missing original. The write (`writeMissingMarks`) is one statement after the deletions and the quarantine, only when a set is non-empty, under the owners' lock (`ownersLockCte` over `garmentOwnersOf`, in id order; a photo no garment shows locks nobody), its WHERE re-asserting `IS NULL` / `IS NOT NULL`; a failure (a 55P03) is logged and reported as `marksFailed`, a failure of the nightly job, and costs no deletion. A dry run marks nothing; a guard refusal still marks (a mark deletes nothing). The garment's revision moves through `closet_sync_touch_photo` (0062). While marked, the photo-ref helpers answer no photo (Images), so pages draw their placeholder and the API leaves `photo` out for `photoMissingSince`. `after-restore.spec.ts` covers marking, clearing, the pages and the writes on a marked garment.
- **After a restore, `maintenance:after-restore` is the one step** (#653; `reference.md`, Commands). It is a dry run for storage (`reconcileStorage({ dryRun: true })`: the pending pass and the trash purge only count), and lists missing originals from the plan, not the column. The lease release goes per row through `recordCutoutEvent(release, <the row's own worker>)`, so a lease taken over since stays. It also ends what a restore revives (#908): every session, through the epoch bump (a session cookie carries the restore epoch as `sep`, `restoreEpochSql`; Auth), and every agent and device token (`revokeEveryonesTokens`: per user through a new password's `revokeTokensStatement`, in one transaction).
- **Only the server schedules the nightly reconciliation, the push reminders and the week's re-plan.** `serve()` (`server.ts`) starts `scheduleNightly` (03:00 in `APP_TIMEZONE`, recomputed after every run, never overlapping) when `MAINTENANCE_ENABLED` (reconciliation) and always (the cutout retry), with `PWA_ENABLED` the reminders' `scheduleMinutely` and their claims' nightly prune, and always the sync tombstone prune (`pruneSyncTombstones`), the OAuth code prune (`pruneOAuthCodes`), the re-plan's and its prune (without `WEATHER_ENABLED` it still judges availability) and the agent's quiet round close (`closeQuietRounds`, `src/web/wishlist/round-end.ts`; notified only with `PWA_ENABLED`); `createApp()` does neither, so the integration harness and the CLIs never hold a timer or send a notification. A spec runs one minute's reminders with `sendDueReminders(deps, now)`.
- **A run that left someone out ends as a failure** (#687). A job isolates per person (or per photo set), finishes the others, then the server's wrapper throws one `PartialFailure` (`src/metrics/partial-failure.ts`, `endWhole(job, counts, run)`; the message names the job and counts, never a person) when `run.failed > 0`, the guard or the storage check refused, or `missingOriginals > 0`, so `metrics.timeJob`, the one choke point, records `outcome="failure"` and captures once. The wrappers are `sendDueRemindersWhole`, `replanWeeksWhole` and `reconcileStorageWhole`, which `server.ts` schedules; the functions under them still return their run, because specs and the CLI read the report (the CLI says the same in its JSON and exit code 3). A failed person's re-plan day is retried at 5, 15 and 60 minutes (`ReplanRetries`), then claimed, and each job (the minutely re-plan, the morning reminder) counts only its own first failure, so one capture per job and person-day. A new per-person job copies this. A forecast fetch that fails is not one: the cache serves a stale answer, and with nothing cached the job runs without a forecast (`userWeatherOrNone`), since a provider outage must not alert every morning.
- **Every timer is stopped and drained before the pool ends** (#78): both schedulers return a `ScheduledJob` (`scheduled.ts`) whose `stop()` clears the timer and waits for a run in flight (`STOP_WAIT_MS`, then aborts its `AbortSignal`); the shutdown must fit docker stop's 10 s (`src/shutdown-budget.ts`). A new timer goes through `scheduleMinutely` / `scheduleNightly`, never its own `setInterval`.
- **A job reads per batch and composes per person**: production pays a round trip per statement, so a read that serves everyone moves out of the loop, but a job that loops per person keeps per-person isolation (one person's failure is logged and counted, never the others'; reconciliation's per-row deletes stay per row on purpose). The morning reminders read forecasts, re-plan candidates and evening days once for the minute, then send in one batch (`PushSender.sendEach`: devices read at send time, never earlier). `job-statements.spec.ts` pins the counts.
- **Moved rules** (detail in `reference.md`): an orphaned photo set (no `file` row) is quarantined by rename into `.trash/<day>/`, never deleted (after a restore it is the only copy), and `--restore-from-trash` restores whole or not at all, never replacing a file. A database restored behind its storage never costs a cutout: the superseded pass deletes a set with a cutout only when every file is day-old and older than the row's set. A new timer joins the stop list (never a hook of its own) and runs inside `metrics.timeJob`; each run is a `runAsJob('cron')` job with its own `job_id`. `maintenance:retrim-thumbs` takes only `ready`/`edited` rows and stops between photos, never inside one. `runCli` checks `requireCurrentSchema` before any CLI runs (the root's never-migrate rule).
