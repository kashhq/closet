# Weather

_Reference, not auto-loaded:_ [`reference.md`](reference.md) holds Cache; Matching; Climate normals.

`src/weather/` (pure) and `src/web/weather/`. **`WEATHER_ENABLED=false`** (default true): `createApp()` builds no service, so there is no `/weather` route (404), no weather on any page or in the profile, no MCP weather tool, and the seed stores no location: nothing is fetched or stored (`weather.spec.ts`, "weather off").

- **Location** (`user_weather`, `drizzle/0015_weather.sql`): a **home** city from the geocoding search (`home_name`, `home_latitude`, `home_longitude`) and the installed app's **"Use my location"** (`here_*`, `here_located_at`), which stands in for home for `HERE_FRESH_HOURS` (12). Every coordinate is rounded to 2 decimals (~1 km) by `roundedLocation` (`src/weather/location.ts`) before it is stored, used as the cache key or sent; the phone rounds too (`views/assets/page/locate.ts`), so a precise position never leaves it. Check constraints keep each group whole and on the globe. One writer per group (`queries.ts`).
- **Provider: Open-Meteo, from the server only** (`open-meteo.ts`): the forecast (16 days: hourly apparent temperature, precipitation chance and weather code; daily high, low, code) requested in the place's zone (`ZonedLocation`: `APP_TIMEZONE` for home and here, a trip destination's own, #678), so its days are that place's calendar days and its hours the occasions' hours (`OCCASION_HINTS`); the answer's echoed `timezone` must canonicalise to the asked one (`canonicalTimeZone`, `src/calendar-date.ts`); plus the geocoding search, whose results carry their `timezone`. Through the outbound fetcher with `hosts` (Request security, Outbound fetches); the request carries the rounded coordinates (or the typed city) and nothing about the user. Answers are checked against TypeBox schemas.
- **Where it shows** (`views.tsx`, one `WeatherLine` and one `WeatherDay`): `WeatherSlot` in the page header (the calendar; the wardrobe has none, #732) loads `GET /weather/summary` once in place (`hx-trigger="load"`, own `hx-indicator`): today's line (icon, range, rain, "take a layer", place, "as of") or, without a location, the link to set one; with `?from=&to=` the calendar's day chips arrive out of band into each day's `WeatherDaySlot` (with `&view=month`, the month grid's compact chips alone: Calendar). **Tab roots never render the forecast themselves**: they must render byte for byte the same while nothing changes (stale-while-revalidate), and an hourly forecast would mark them changed. Today is the exception: network first, it renders `UserWeatherLine` from the read its ideas use (see Today). Offline the worker answers the fragment from its cache (`url|hx`), "as of" saying how old (`test/weather.spec.ts (retired 2026-10-13)`). Settings: `WeatherSettings`, on the profile.
- **Personal offset and units** (`temperature.ts`): °C added to every feels-like, within ±5, moved half a degree by "I was too warm" / "I was too cold" (`nudgeTemperatureOffset`, one SQL statement so quick taps all count). Everything is computed and stored in °C; `temperature_unit` (°F by default; the constant and the migration default must agree) is only display.
- **One place picker** (`src/web/weather/place-picker.tsx`): the search's bounds and `PlaceQuery`, `placeAnswer` (a failure is an answer), `PlaceResults` (each picker brings only its `Form`), `LocationFields`, `PlaceBody`/`LocationBody` and `pickedPlace`/`postedLocation` serve the home and a trip's destination alike; `@place-fields` (guards.conf) fails a coordinate field or bound spelled elsewhere (2026-10-18).
- **Trips**: a trip's forecast is its destination through the same geocoding and `forecastFor`, in the destination's zone (`trip.time_zone`, set with the place; null, a trip located before 0057 or a zone Intl does not know, reads `APP_TIMEZONE`: `zonedIn`), for its days within the 16, and its climate normals past them or where the destination's forecast lacks a day (`tripForecast`; see Trips); `ideasFor` takes the destination as `place`. **Known limit: "today while travelling is home's"** (`docs/decisions.md` 2026-11-14): which days are left, "Wore it" and the horizon follow `APP_TIMEZONE`. `get_weather` stays the user's own location; `get_trip` carries the trip's.
- **Tests never call Open-Meteo**: `test/support/weather-stub.ts` (an HTTP server on 127.0.0.2, admitted by the weather fetcher's own policy) serves the seed's simulated New York weather from today in the requested zone, and the same simulated days for the archive's years (`archiveAnswer`). The harness runs with `WEATHER_ENABLED=false` and refuses to boot a spec that turns it on without the stub; the e2e test server always starts it.
- **The place search is `secretPath`** (the page's, the API's and the trip's), so the typed city never reaches the request log; a failed search is an answer (a message htmx shows), not an error.
- **An htmx answer swaps only the part it changed, never the whole weather section**, which holds the unit's `AutosaveForm` (no other swap may replace one): the location forms answer `#weather-location`, the feedback `#weather-offset`, the unit its status line. The API's twins call the same writers through the same rate-limit checkers (`weatherLimits`).
- **Never logged**: the user or the query on a place search's line, a location on the settings routes' (they name the user), the place or its coordinates as a `weather.*` op field; a refresh names the rounded location and its zone, the fetcher the host only.

## Gotchas

- **Weather is off in the integration harness.** `BASE_ENV` sets `WEATHER_ENABLED=false`; a spec that turns it on must pass `weather: (await startWeatherStub()).options`, or `createTestApp` refuses to boot: a spec must never reach Open-Meteo. The e2e test server always serves the stand-in.
- **Climate normals are a trip's far days' alone.** `WeatherService.normalsFor` is asked only by `tripForecast` and by `ideasFor` for a trip's `place` past the forecast. Today, the calendar, the gallery's own days and the weekly plan and its re-plan must stay forecast-only: a typical day is not a forecast, and the re-plan swaps outfits when the weather changes. A new `normalsFor` caller labels its output as typical.
- **The weather's days and hours are the household's, except a trip's.** The home's forecast is requested in `APP_TIMEZONE`, so "today", the calendar's chips and the occasion windows line up; a trip's is its destination's (#678), so never compare its hours with home's clock; derive them with `todayIn`/`hourIn`, never `toISOString()` or UTC getters. The integration spec pins the clock (`vi.useFakeTimers({ toFake: ['Date'] })`) at 00:30 UTC on a Sunday, still Saturday evening in New York.
- **Routes' rules**: `/weather/summary` is always a fragment, `from` and `to` both or neither, at most 42 days, else a 400. Home and here take `WEATHER_LOCATION_LIMIT` (each is a fetch and a row); "Use my location" re-enables itself and says so when its post fails (`locate.js`). A plain (non-htmx) post is a 303 to `/auth/profile/weather`, which is a 404 with the weather off.
- **Moved rules** (detail in `reference.md`): only a cold miss waits on the provider; a stale answer is served while one refresh per location per process runs, and no timer starts one. A one-shot decision ("Plan my week", route and MCP) reads `{ fresh: true }`, never a stale forecast. A kept answer to another question (`mismatch`: another `timeZone`, other `normalYears`) is never served, not even as the fallback. A background refresh never rejects, and the app's close awaits `WeatherService.settled()` (specs too, never a poll). `userWeather` reads settings and the cache row in one statement. Climate normals never feed Today, the calendar, the plan or its re-plan: a typical day must never swap a planned outfit. A layer is judged on its own too, not only in the sum.
